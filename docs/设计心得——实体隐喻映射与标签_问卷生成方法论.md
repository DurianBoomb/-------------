# 设计心得：实体隐喻映射与标签/问卷生成方法论

> 写于 2026-05-11
> 场景：Coze 工作流提示词迭代 · 确诊文学标签 + 实体问卷生成

---

## 一、问题背景

在"确诊文学"类社交小游戏的标签和问卷生成中，核心创意模式是**实体隐喻**——把一个日常实体（烤肠、仙人掌、手机电量）作为源域，映射到人的状态（性格、情绪、行为模式）作为目标域。

最初的两版提示词能够稳定产出"确诊为烤肠"级别的标签名，问卷也能生成题目。但问卷的质量参差不齐——部分问卷的维度和结果类型出现了"看着像烤肠，品着不像"的问题。

典型表现：

| 问题现象 | 示例 |
|---------|------|
| 维度脱离源域本体 | 给"烤肠"问卷加入"社交媒体活跃度"维度 |
| 结果类型不是源域内的真实子类 | "深夜emo肠"——并非真实肠类，只是人套了个肠字 |
| 选项含义跨实体跳跃 | 同一份问卷内混合了烤肠、夜宵、摇滚歌手三个源域的尺度 |

这些问题不是模型能力不足，而是**提示词缺少结构性约束**。

---

## 二、理论诊断：概念隐喻映射的系统性断裂

### 2.1 Lakoff 概念隐喻理论与不变原则

George Lakoff 和 Mark Johnson 在 *Metaphors We Live By*（1980）中提出：隐喻不是修辞手段，而是**认知机制**——人们通过一个概念域（源域）的结构来理解另一个概念域（目标域）。

随后 Lakoff（1993）进一步提出 **Invariance Principle（不变原则）**：

> 隐喻映射保留源域的认知拓扑结构，即源域的图像-图式结构必须与目标域固有结构保持一致。

翻译成人话：当你说"某人是烤肠"时，**烤肠的属性必须能回推到烤肠本身上**。如果某个属性（如"社交媒体活跃度高"）在烤肠上找不出对应物，这个映射就是断裂的——不是"从烤肠往人的映射"，而是"从人往烤肠的贴皮"。

### 2.2 映射方向决定质量

经诊断，所有质量差的问题都可归结为一句话：

> **映射方向错了。**

正确的方向：

```
源域（烤肠的物理属性） → 筛选可映射特征 → 翻译为人的状态
```

错误的方向：

```
人的状态清单（性格分类） → 遍历 → 给每类套个"肠"字后缀
```

前者是**生长出来的映射**，后者是**贴上去的标签**。后者正是概念隐喻理论中所说的"缺乏源域经验基础的空映射"。

### 2.3 具体映射失效模式

映射失效可分为以下三类：

**类型A：维度脱离源域本体**
- 表现：某个问卷维度在源域实体上没有对应的物理/功能基础
- 示例：烤肠问卷中问"社交媒体活跃度"
- 诊断：该维度并非从烤肠的属性派生，而是直接从人的世界拉过来的

**类型B：结果类型不是源域内的真实子类**
- 表现：结果分类的名词是"源域名词 + 人属性"，而非源域品类谱系中真实存在的类别
- 示例："深夜emo肠"——在烤肠的品类树中不存在"深夜emo"这个亚种
- 诊断：本质上是先有人格分类，后加"肠"字后缀

**类型C：多源域混合**
- 表现：同一份问卷的维度来自两个或以上不同实体
- 示例：一份问卷既有"燥热程度"（烤肠属性），又有"夜宵频率"（吃夜宵的人属性）
- 诊断：违反了映射的"单源域一致性"——一份问卷只能有一个源域

## 三、约束体系

针对以上问题，我设计了一套约束体系。这些约束不是"注意事项"，而是**必须严格执行的生成规则**，每一层都在堵一个特定的映射漏洞。

### 3.1 映射的单源一致约束

> 一份问卷/标签集内，源域有且只能有一个。

这是最基础的约束。如果问卷的源域是烤肠，所有维度、题目、选项、结果类型都必须**只**从烤肠这个实体及其紧密场景（烧烤摊、便利店冷柜、配料）派生。任何引入第二个实体的维度（如"夜宵频率"引入了"吃夜宵的人"这个辅助源域）都是违规。

这条约束的存在是因为：从人类认知角度看，同时维持两个源域的映射结构需要额外的认知成本——语义网络中的"实体跨越"会产生认知冲突。简单说：读者会困惑。

### 3.2 映射的特征筛选约束

> 从源域属性中只选择**可体验化、可行为化、可情绪化**的属性进行映射。

不是所有源域属性都需要映射。目标不是做该实体的"百科全书"，而是做"人的状态隐喻"。因此需要从源域属性中做减法：

| 适合映射的属性 | 不适合映射的属性 |
|--------------|----------------|
| 物理构成→内在特质 | 纯物理度量（净重、尺寸） |
| 外部特征→社交面具 | 化学成分（分子式） |
| 生命周期→人生阶段 | 生产工艺 |
| 典型遭遇→行为模式 | 非日常场景下的属性 |

**筛选标准**：这个属性如果用来形容一个人，别人能不能一秒钟就懂？不能就别用。

### 3.3 结果类型的品类下位约束

> 结果分类必须是源域品类谱系中真实存在的下位类别或公认状态差异。

简单说：结果的名字得是"这个实体本身有的种类或状态"，不能是"把这个实体当成一个词后缀来造词"。

| 源域 | 可用的真实品类/状态 | 不可用（贴皮） |
|------|-------------------|---------------|
| 烤肠 | 纯肉肠、淀粉肠、玉米肠、墨鱼肠、烤爆了的肠、烤成了碳的肠 | 深夜emo肠、社交牛逼肠 |
| 仙人掌 | 食用仙人掌、观赏仙人掌、沙漠野生耐旱种、被浇烂的 | 职场摆烂仙人掌 |
| 手机电量 | 满格、半格、红线、关机、充电中、虚电 | 社交电量满格人 |

**判断标准**：去掉源域名词后，剩下的词能否独立指代该实体真实品类？能→对，不能→贴皮。

## 四、提示词工程方法

理论诊断和约束体系确立后，需要在提示词层面落地。抽象的原则在大模型面前是无效的——模型需要的是**执行步骤**而不是"注意事项"。

### 4.1 四步流程

以下是经过验证的提示词链结构，适用于实体地图生成、问卷题生成、结果分类生成等场景：

```
步骤1：强制提取源域特征表
  ↓
步骤2：筛选可映射通道
  ↓
步骤3：生成维度/题目（通过溯源三问自检）
  ↓
步骤4：结果类型从源域品类树中取
```

**步骤1：特征表**

在生成任何维度之前，先输出一个结构化的实体特征表。该表覆盖以下四类特征：

| 特征类 | 问题 | 示例（烤肠） |
|--------|------|-------------|
| 物理构成 | 用什么做的？成分决定了什么？ | 淀粉含量高低 |
| 外部特征 | 长什么样？颜色、质地、视觉印象？ | 表面焦脆程度、烤痕 |
| 生命周期 | 怎么产生的？经历什么变化？怎么被消耗？ | 从冷冻→解冻→烤→烤爆→烤成碳 |
| 典型场景 | 通常在哪？被怎么对待？和什么搭配？ | 便利店收银台旁边、烧烤摊铁板上、被反复翻面 |

此步骤的关键作用不是"归纳信息"，而是**提供锚点**。后续所有维度都必须能从这张表中找到来源。

**步骤2：筛选可映射通道**

从特征表的"人的映射方向"列中，按以下通道类型筛选：

| 源域特征类 | 优先映射的人类域 |
|-----------|----------------|
| 物理构成 | 内在特质、能力结构、心理能量 |
| 外部特征 | 外在表现、社交面具、情绪防御 |
| 生命周期 | 人生阶段、职业状态、情感进程 |
| 典型场景 | 行为模式、应对压力方式、人际关系 |

筛选标准同 3.2：选能让人一秒共鸣的，舍弃纯百科式属性。

**步骤3：溯源三问（自检机制）**

每生成一个候选维度/题目，必须通过以下三问测试：

1. **本体溯源**：这个维度来自源域实体的哪一个具体属性？
2. **本体必要性**：如果源域没有这个属性，它还是它自己吗？（答案必须为"不是"）
3. **映射可理解性**：把这个维度对应到人时，人是否能秒懂且不越界到其他实体？

这组自检的核心逻辑是 Invariance Principle 的实操版——源域的认知拓扑结构必须被保留。

**步骤4：品类树取结果**

在出结果类型之前，先列出该实体在中文语境下公认的品类/状态清单。结果只能从该清单中选取。禁止自行发明"实体名+状态"格式的新词。

### 4.2 与标签生成的关系

上述四步流程适用于**问卷生成**场景（dimensions + questions + resultTypes 的结构化产出）。

对于**标签生成**场景（纯 name + description 的种子产出），不需要完整的四步流程——那会杀死创造力。标签生成只需要两条轻量级指导：

1. **选实体的三个门槛**：有画面感、有品类分支、能找出 3 个以上可映射属性
2. **一条红线**：去掉实体名后的词能否独立指代该实体品类——不能就是贴皮，重想

原因在于：标签生成是"灵感发散"，问卷生成是"结构收敛"。前者需要空间，后者需要框架。同一套方法论不能生硬套用在不同输出格式上。

## 五、实体标签与非实体标签的分治

在实际业务中，"确诊文学"风格标签包含两种本质不同的子类型。对这二者的混为一谈是最初设计中的一个盲点。

### 5.1 两种标签的区分

| | 非实体标签 | 实体隐喻标签 |
|--|-----------|-------------|
| 定义 | 直接描述人的状态，不通过第三方实体 | 通过一个实体的分类来隐喻人 |
| 示例 | "精神状态良好"、"拖延症晚期"、"讨好型人格" | "确诊为烤肠"、"你是哪种小猫"、"你的精神图腾" |
| 输出逻辑 | 发现已有文化共识中的"状态"并命名 | 从实体属性到人的跨越映射 |
| 占比 | 约 60-70% | 约 30-40% |
| 映射复杂度 | 无映射（直接陈述） | 需要映射（实体→人） |
| 适合的方法论 | 生活观察 + 确诊文学三个零件 | 实体特征表 + 三个门槛 + 红线 |

### 5.2 为什么必须分治

非实体标签的核心风险是"AI 味"——描述像功能介绍、概括人群、太精致。

实体隐喻标签的核心风险是"映射断裂"——维度漂移、结果贴皮、品类错误。

两者需要完全不同的检查机制和风格纠偏。此前把所有标签视为同质类别、用同一套提示词去管，自然管不住实体隐喻标签的特殊问题。

### 5.3 混合集合时的处理建议

如果一次生成任务同时产出两种标签（需求如此），建议在提示词中明确区分两个阶段：

1. 先让模型自由产出（以非实体标签为主力）
2. 在末尾增加一条分支指导，当模型认为"这个方向可以用实体隐喻来表现"时，启用实体标签的灵感方法

这样做的好处是：不让实体的约束淹没主体的创造力，但也确保实体标签不会被粗放对待。

## 六、通用性：框架的迁移能力

这套方法论不局限于"烤肠"或"确诊文学"。它本质上是一个**通用隐喻映射工程框架**，可迁移到任何"用实体隐喻人"的场景。

### 6.1 迁移模板

只需更换实体名，其余逻辑完全不变：

> **通用四步法**
>
> 1. **解构实体**：物理构成 + 外部特征 + 生命周期 + 典型场景 → 特征表
> 2. **提取映射通道**：从特征表中筛选可体验化、可行为化、可情绪化的属性
> 3. **生成内容并通过溯源三问**：每个输出项都要能回答"来自源域的哪个属性"
> 4. **品类树取结果**：结果只能从源域真实品类/状态列表中选取

### 6.2 已验证的实体

烤肠、香蕉、仙人掌、手机电量、电路板、奶茶、落叶、一次性筷子、快递纸箱、充电宝、空气炸锅、地瓜……

凡满足"有画面感 + 有品类分支 + 能找 3 个以上可映射属性"的实体，都能用此框架。

## 七、总结

| 维度 | 教训 | 解法 |
|------|------|------|
| 理论 | 映射方向比映射内容更重要 | 用概念隐喻理论+不变原则诊断方向 |
| 约束 | 抽象原则在 prompt 中失效 | 拆解为可执行的特征表 + 溯源三问 + 品类树 |
| 分治 | 非实体标签和实体标签是两回事 | 不同的风险点+不同的检查机制+不同的灵感方法 |
| 边界 | 标签生成和问卷生成本质不同 | 标签需要灵感空间，问卷需要结构约束 |
| 通用性 | 框架设计时就要考虑迁移 | 通用四步法 + 只需换实体名 |

核心结论只有一句话：

> **让 AI 做好隐喻映射的关键，不是告诉它"不要跑偏"，而是强制它先走一遍源域特征表再动笔。有了锚点，它就不会漂移。**

## 八、实施方案 C：混合管线落地

> 本节写于 2026-05-11
> 第四至七节的方法论（四步约束流程）在理论层面是正确的，但 Coze 底层模型在执行长 JSON 生成时，约束密度过高会导致选择性忽略。经讨论，最终落地形态为**混合方案**——让 Coze 只做发散和翻译，让自家代码做结构检查和规则匹配。

### 8.1 管线全貌

```
Coze 侧
  │
  ├─ [已有] 标签批量生成工作流 → 保持现状，风格约束不变
  │
  ├─ [新增] 实体特征提取工作流
  │   输入: 标签名
  │   输出: 结构化特征表 JSON
  │   说明: 纯描述任务，不涉及任何维度生成，难度极低
  │
  └─ [修改] 问卷生成工作流
      输入: { tagName, featureTable, categories }
      输出: { tag, title, dims, qs, resultTypes }
      要求: 维度从 featureTable 的可映射方向列取
           结果类型从 categories 清单取

校验侧
  │
  ├─ [前端] 结构校验（已有，不变）
  │   检查 dims 数、qs 数、字段完整度 → 不合规则用兜底 mock 数据
  │
  ├─ [本地脚本] 入库校验脚本（新增）
  │   结构校验 + 关键词规则 + 品类白名单匹配
  │   输出校验报告 → 人工确认 → 导入数据库
  │
  └─ [缓存] entity-data.json 库（新增）
      每实体一份 JSON（特征表 + 品类树打包）
      双复用：Coze 问卷生成用 + 校验脚本用

管线流程
  │
  ├─ 步骤1: 有新的标签产生后 → 跑特征提取工作流 → 保存 entity-data.json
  ├─ 步骤2: 跑问卷生成工作流（输入带上特征表和品类树）→ 产出问卷 JSON
  ├─ 步骤3: 跑本地校验脚本 → 扫校验报告 → 人工确认可疑项
  └─ 步骤4: 确认通过 → 导入数据库
```

### 8.2 核心设计：实体档案 JSON

四节中的抽象约束（特征表、品类树）在此被物化为实体档案 JSON。一份数据，两个用途：

```json
{
  "entity": "烤肠",
  "categories": ["纯肉肠", "淀粉肠", "玉米肠", "墨鱼肠", "脆骨肠"],
  "features": {
    "physical": ["淀粉含量高/低", "肉质紧实/松散", "表面焦脆程度"],
    "appearance": ["颜色", "烤痕", "粗细"],
    "lifecycle": ["冷冻→解冻→烤→烤爆→烤成碳"],
    "scenarios": ["便利店收银台", "烧烤摊铁板", "泡面搭档"]
  }
}
```

这份 JSON 既是提示词中的原料（Coze 不需要理解理论，只需照着数据画瓢），也是校验脚本的标尺（遍历维度名，在特征表中查对应条目）。

维护边界极度清晰：新增一个实体 → 加一个 JSON 文件。删一个实体 → 删一个文件。没有耦合。

### 8.3 Coze 侧的实际限制与应对

**特征提取和问卷生成是两次独立的 Coze 对话**，工作流之间默认没有共享上下文。在离线批量模式下，手动搬运一次特征表 JSON 的成本极低，不影响管线效率。具体操作：工作流 A 输出 JSON → 复制 → 工作流 B 输入参数中贴上。

这个"限制"反而成了质量闸口——手动确认过的特征表再喂给问卷生成，天然过滤了不靠谱的原料。

进化到实时在线模式时，需要在后端自建特征表缓存接口，Coze 侧改为 API 调用链。但那是以后的事，当前管线不受影响。

### 8.4 入库校验脚本的职责

放在本地运行（Node.js），作为导入流程的前置步骤：

| 检查项 | 方法 | 示例 |
|-------|------|------|
| 结构完整性 | 字段名、维度数 3-7、题目数 = dims×3 | dims.length < 3 → 直接拒绝 |
| 维度语义告警 | 关键词匹配：维度名含源域无关词，或后缀为"人/兽"等脱离词 | 烤肠维度中出现"社交" → 标黄 |
| 品类白名单 | 结果类型名必须在 categories 数组中 | "深夜emo肠"不在烤肠品类中 → 标红 |
| 多源域混合 | 检查一份问卷内是否出现两个实体关键词 | 烤肠问卷中出现"夜宵" → 标黄 |

输出校验报告（JSON），人工扫一眼可疑项后再确认入库。

前端已有结构校验保持原样，作为最后防线。前后端校验逻辑复用同一套规则。

### 8.5 方案之间的取舍记录

| 被否方案 | 否决原因 | 替代方案 |
|---------|---------|---------|
| 方案 A（全塞进 Coze 提示词） | 约束密度过高，弱模型生成长 JSON 时选择性忽略 | 轻型提示词 + 后端校验 |
| 向量相似度辅助筛查 | 当前 30-50 标签体量下过度设计 | 硬编码品类树 + 关键词规则 + 人工 |
| 特征提取与问卷合并为一次对话 | 认知负载过高，Coze 记不住同时做两件事 | 拆为两次独立对话 |
| 前端语义增强校验 | 离用户近但迭代慢，且交互路径上不该拦截 | 放在本地入库脚本，前端只做结构兜底 |
| 入库校验放在云函数 | 部署更新慢，不符合当前手动导入流程 | 本地脚本 + 复用逻辑至前端 |

### 8.6 长期演进路径

当前管线是"Coze 离线批量生成 + 手动审核入库"模式。如果未来演进到"用户搜索不到 → 看广告 → Coze 实时生成"的在线模式：

- **结构校验**直接迁移到云函数，复用同一套规则，作为实时请求的返回前拦截
- **特征表缓存**从本地 JSON 文件迁移到数据库表，Coze API 调用时从缓存拉取
- **校验不通过的问卷**改为用兜底问卷返回，不阻塞用户体验
- **方案四节的抽象约束**在此场景下不便全量使用（实时场景没有人工审核的机会），校验脚本就是唯一的防线，所以现在离线阶段把校验写扎实是值得的
