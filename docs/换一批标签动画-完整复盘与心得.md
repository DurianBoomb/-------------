# 换一换标签掉落动画——完整复盘与心得总结

> 项目：快乐大狐狸工具集 · 搜索页面 · 分类标签池
> 环境：Vue2 + uni-app → 微信小程序
> 起因：一个"微小的动画需求"折腾了长达几天

---

## 一、需求回顾

手风琴展开后显示 16 个标签，每个标签以 `translateY(-80rpx) → 0` + `opacity: 0 → 1` 的弹性掉落动画入场，每个标签的 `animation-delay` 不同形成交错效果。点击「换一换」按钮重新洗牌取 16 个新标签——**新标签应从头播放掉落动画**。

听起来就是加个 CSS animation 的事，不是吗？

---

## 二、完整的时间线

### 第 1 轮：天真的 CSS 方案

**做了什么：** 写了 `@keyframes dropElastic`，`.tag-inner` 引用它，首次展开完美。

**结果：** 点「换一换」动画不播。标签内容变了，但直接出现，没有入场动画。

**原因：** 微信小程序中，一个已经存在于 DOM 中的元素，你改它的 `animation-delay` 不会重播 animation——因为它根本没有 "unmount 再 mount"。

### 第 2 轮：JS 样式复位（方案 A）

**做了什么：** 先把 inline style 设为 `animation: none !important`，`$nextTick` 后再设回 `animation-delay: Xs`。

**结果：** 失败。因为 `animation-name` 写在 CSS 里，inline style 只改了 delay，元素的 animation-name 没变，所以样式复位不触发重播。

**教训：** CSS animation 在已存在元素上的"复位"，至少需要同时变更 animation-name。只改 delay/时长等参数无效。

### 第 3 轮：`:key` 驱动 DOM 重建（方案 B/C）

**做了什么：** 在 `.tag-grid` 上加 `:key="'grid-' + cat.refreshId"`，每次换一换 `cat.refreshId++`，期望 Vue 销毁旧 grid、重建新 grid，新 DOM 节点的 CSS 动画自然触发。

**测试了两种变体：**
- 纯 `:key`（方案 C）
- `:key` + `animation: none` 复位（方案 A + B 混合）

**结果：** 全部失败。

**原因（非常重要）：** uni-app 编译为微信小程序后，**非 `v-for` 元素上的 `:key` 变化不会导致 DOM 真正销毁重建**。Vue 的 diff 逻辑在编译为 wxml 之后被抹平了——微信小程序渲染层不会因为一个普通 view 的 key 变了就去创建新的原生节点。它在走节点池复用路径。

### 第 4 轮：v-if 拔掉整个网格（第一次修复）

**做了什么：** 引入 `cat.showGrid`，用 `v-if="cat.showGrid"` 控制 `.tag-grid` 容器显隐。每次换一换：`showGrid = false` → 更新数据 → `$nextTick` → `showGrid = true`。

**结果：** 动画能触发了 ✅ **但手风琴会闪烁** ❌——收回去又弹出来。

**原因分析（魔鬼在细节里）：**

```
.accordion-body (max-height transition)
  └── .body-inner (v-if="cat.expanded")
       ├── tag-pool-header (固定 ~80rpx)
       └── .tag-grid (v-if="cat.showGrid")   ← 被拔掉
```

`.tag-grid` 被拔掉 → `.body-inner` 的高度从 ~350rpx 塌到 ~80rpx → `.accordion-body` 的 `max-height` + `overflow: hidden` + `transition` 让这个塌陷**肉眼可见** → 然后重建 grid → 高度弹回来 → 闪烁。

**本质：** 父容器的 `max-height transition` 无法区分"子元素正常消失"和"子元素暂时隐藏"——只要高度变了它就播动画。

### 第 5 轮：v-for :key 驱动单个标签重建（第二次修复）

**做了什么：** 去掉 `.tag-grid` 上的 `v-if`，改到每个 `.tag-wrapper` 上用 `:key="cat.refreshId + '-' + ti"`。

**原理：** `.tag-grid` 始终在 DOM 中 → 容器高度不变 → 不触发父级 transition → 无闪烁。但 16 个 `.tag-wrapper` 的 key 全部变化 → Vue 逐个销毁旧标签、创建新标签 → CSS animation 在新节点上触发。

**结果：** 动画触发 ✅ 无闪烁 ✅

**关键发现：** uni-app 编译为微信小程序后，**只有 `v-for` 的 `:key` 变化才能可靠驱动子 DOM 节点重建**——非 `v-for` 元素上的 `:key` 不生效。这是因为 `v-for` 对应小程序的 `wx:for`，而普通 `:key` 只是 Vue 内部 diff 的提示，编译器不一定透传给小程序渲染层。

### 第 6 轮：发现 `:key` 方案在部分场景仍不可靠 → 引入双 animation-name 兜底

**发生了什么：** 进一步测试发现，`v-for :key` 驱动重建的方案在某些场景下仍然偶发动画不播。写了一个 Figma prompt 求助后，Figma 指出：**v-for 的 `:key` 变化在小程序中的确是走节点池复用而非真正的销毁重建**。Vue 的 unmount/mount 在编译成 wxml 后可能被抹平了。

**最终方案（当前代码状态）：** 保留 `:key` 驱动重建 + **额外引入双 animation-name 交替机制**——维护两个内容完全相同的 `@keyframes dropElasticA` / `dropElasticB`，用 `cat.animFlip` 翻转让类名在 `anim-a` / `anim-b` 之间切换。

```css
.tag-inner.anim-a { animation-name: dropElasticA; }
.tag-inner.anim-b { animation-name: dropElasticB; }
```

切换 animation-name 时，小程序的样式 diff 引擎会认为这是"不同的动画属性全新应用"，从而触发重播。

**最终代码同时保留了两层机制：**
1. `v-for :key` 驱动标签级 DOM 重建（万一节点真的重建了，animation-name 不变也没问题）
2. `animFlip` 双 animation-name 交替（即使节点被复用，animation-name 变了也会重播）

两者互不冲突，形成双重保险。

## 三、核心原理总结

### 微信小程序中触发 CSS animation 重播的方式

| 触发方式 | 可靠度 | 副作用 |
|---------|--------|--------|
| 新 DOM 节点挂载（首次创建） | ✅ 100% | 无 |
| v-if 从 false → true（父级创建） | ✅ 100% | 可能导致父容器高度变化引发 transition 闪烁 |
| v-for 的 :key 变化（同级替换） | ❌ 不可靠 | 小程序可能复用节点池，不重建 |
| 非 v-for 元素的 :key 变化 | ❌ 不可靠 | 同上 |
| 切换 animation-name 类名 | ✅ 可靠 | 需维护两个相同 keyframes |
| JS 复位（animation: none → 恢复） | ❌ 不可靠 | 需变更 animation-name 才有用 |
| 动态注入 @keyframes | ❌ 小程序不支持 | 无完整 DOM API |
| uni.createAnimation | ✅ 可靠 | 工程量大，需逐帧驱动 |

### 最终方案的技术原理

```
换一换按钮
  ↓
refreshId++  →  v-for 的 :key 全部变化  →  期望重建标签 DOM
animFlip = !animFlip  →  切换 anim-a / anim-b  →  触发 animation-name 变更  →  样式 diff 重播动画
  ↓
两个机制并行触发，任意一条路径生效都行
  ↓
CSS animation 在新标签节点上从头播放 ✅
```

## 四、技术之外的教训

### 1. 框架会撒谎，渲染层不会

Vue 的 diff 机制"理论上"做了什么事，和"小程序渲染层实际做了什么事"是两码事。Vue 2 + uni-app 这种编译型框架尤其如此——你在源码层写的 `:key="refreshId"`，经过编译器变成 wxml 后，微信渲染层看到的是 `wx:key="_refreshId"` 或者干脆丢掉了。**你调试的不是 Vue，是编译产物。**

任何时候遇到"理论上应该生效"的 bug，优先怀疑：**编译器有没有把我的代码变成我想要的行为？**

### 2. 两层嵌套的 bug 才是真正的魔鬼

这个问题的曲折核心在于——问题 1（动画不播）和问题 2（手风琴闪烁）在"修复"过程中像诅咒一样绑定在一起：

- 修复动画 → 引入闪烁
- 消除闪烁 → 动画又不稳定
- 两全其美的方案 → 又发现 `:key` 不可靠

**每一层修复都引入了新的约束条件**。最终是靠两层冗余机制（`:key` + 双 animation-name）才同时解决了所有问题。有时候优雅不是目的，**在约束条件下能稳定运行才是真本事**。

### 3. 早用双 animation-name 可能不用走前面 4 轮弯路

回头看，如果一开始就知道"微信小程序中切换 animation-name 是最可靠的重播方式"，前 4 轮弯路全都可以跳过。但是：

- 这是一个平台特有知识，不是通用的 CSS 知识
- 大多数前端教程里不会告诉你"同一份 keyframes 写两遍能解决渲染引擎复用问题"
- 不踩一遍坑，这个知识你记不住

所以这轮辛苦不白费——付出了时间代价，得到了**对微信小程序渲染层底层行为的深刻理解**，这份认知在下一次遇到同类问题时会直接跳到最后一步。

### 4. 小程序是个「伪浏览器」环境

这个项目最大的痛苦来源：**我们一直在用浏览器的直觉去推断小程序的行为**。但小程序不是浏览器——它的渲染层是原生组件，样式系统和 CSS 标准之间有一层映射。

- 浏览器的 CSS animation 规则在小程序上**大部分**适用
- 但"已存在元素的动画重播"这个细分场景，小程序的实现和浏览器不同
- 不要因为 95% 的 CSS 工作正常，就默认剩下 5% 也正常

### 5. 心态层面：不要相信"小问题"

这个需求在业务逻辑上极简单——「换一批重新播动画」，两三行 CSS 的事。但实际上它牵扯到：

- CSS animation 的生命周期管理
- Vue diff 算法与小程序编译器的透传边界
- 微信小程序原生渲染层的节点池复用策略
- `max-height` transition 的物理本质（它不是语义化的"展开/收起"，它就是两个数值之间的动画）

**简单需求 ≠ 简单实现。** 当一个看起来是小问题的东西折腾了你三轮，说明这底下有更深层的机制问题，不要继续硬试，停下来搞明白原理。

## 五、以后遇到类似问题的排查路线图

```
CSS animation 在已存在元素上不重播
  ↓
Q1: 元素是不是全新创建的 DOM 节点？
  ├── 是 → 检查 CSS 定义是否正确（animation-name/duration/fill-mode/timing-function）
  └── 否 → 进入 Q2
  ↓
Q2: 是否可以用 v-if 让父级销毁重建？
  ├── 可以且无副作用 → 用 v-if
  └── 会导致父级 transition 闪烁 → 进入 Q3
  ↓
Q3: 是否可以用 v-for 的 :key 驱动单个节点重建？
  ├── 纯 Vue/Web 环境 → 可靠
  └── uni-app → 微信小程序 → 不可靠，需要双保险
  ↓
Q4: 最可靠的兜底 → 双 animation-name 交替 + v-for :key
```

## 六、最终代码的亮点

当前 `search-page.vue` 中值得记住的代码模式：

1. **双 animation-name 交替** —— 维护两个完全相同的 `@keyframes`，用布尔翻转切换类名
2. **v-for key 加 refreshId 前缀** —— `:key="cat.refreshId + '-' + ti"` 确保每次全部变化
3. **Fisher-Yates 原位洗牌** —— 直接改原数组，不去 splice/随机取
4. **bodySlideIn 动画替代 max-height transition** —— `.body-inner` 用 `animation: bodySlideIn` 而不是父级 `max-height transition`，避免了"子元素变化引发父级闪烁"的问题
5. **防连点锁** —— `cat.refreshing` 字段在异步操作期间阻塞重复点击

---

## 七、一句话总结

> **微信小程序中，让一个已存在元素重播 CSS animation 的最可靠方式不是用 JS 复位或用 `:key` 重建，而是切换它的 `animation-name`——哪怕新旧两个 keyframes 内容完全一样。**

这份经验不只适用于这个项目，以后在任何微信小程序中遇到"动画只播一次就死了"的问题，都可以直接跳到双 animation-name 方案。
