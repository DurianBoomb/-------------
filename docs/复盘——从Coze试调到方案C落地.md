## 前置阶段：项目背景

### 产品定位

"快乐大狐狸工具集"是一个**标签式娱乐答题工具**（非问卷编辑器）。用户浏览标签 → 选一个开答 → 答完出结果（雷达图+结果类型描述）→ 分享。

先生在这个过程中洞察到产品本质是一个**"用户画像引擎"**——所有标签和问卷都在回答同一个问题："我是谁？我在别人眼里是什么样的？"

### 技术栈

- **前端**：Vue 2 + uni-app + 微信小程序（5个页面已全部跑通）
- **后端**：uniCloud 支付宝云（数据库 + 云函数，**尚未接入**）
- **数据**：当前所有数据均为硬编码 mock
- **AI 协作**：Coze 工作流（标签生成 + 问卷生成）

"确诊文学"标签约 30-40%，非实体标签约 60-70%。其中实体隐喻标签（如"确诊为烤肠"）因为涉及"从实体→人的跨越映射"，是质量问题的高发区。

## 阶段 0：试调——在方法论之前先动手跑

**时间**：5月9日 ~ 5月10日  
**核心动作**：直接上手配置 Coze 工作流，用实际跑出来的结果驱动后续的思考和迭代。

### 做了什么

#### 0.1 标签批量生成工作流（第一次跑通）

在 Coze 上配置了标签批量生成工作流，第一次跑通就产出了约 48 个标签。标签质量可用，大部分能打：

| 示例标签 | 质量 |
|---------|------|
| 确诊为烤肠 | ✅ 可用 |
| 搬屎大王 | ✅ 可用 |
| ...（约 46 个更多） | ✅ 大部分可用 |

标签生成的输出格式是 `[{ name, category, emoji, description }]`——4 个字段互相独立，结构简单，Coze 能稳定产出。

**结论**：标签生成 → Coze 能搞定，维持现状。

#### 0.2 问卷生成工作流（第一次试跑）

配置了问卷生成工作流，多次试跑后发现问题严重。问卷的结构比标签复杂得多——包含 tag, title, dims, qs（维度数×3 道题）, resultTypes（含 match 关联），Coze 要在一次输出中维持三层一致性。

#### 0.3 积分试水

一次完整跑通消耗约 1000+ 积分。其中：

| 操作 | 消耗积分 | 备注 |
|------|---------|------|
| 标签批量生成（一次） | 约 300+ | 主要消耗在 LLM 调用 |
| 问卷生成（一次） | 约 400+ | 维度 + 15题 + 结果全部生成 |
| 加两个变量节点 | 277 | 纯属浪费，变量配置不用 LLM 也扣钱 |

变量配置都要吃积分这个发现，直接影响后续对 Coze 配置策略的思考——能省则省。

#### 0.4 提示词初版（以"被朋友拉起来出题的人"为人设）

当时尚未上方法论，先写了第一版提示词。人设是"凌晨三点被朋友拉起来出题的人"，希望用这个接地气的角色驱动 Coze 产出有生活感的题目。当时写的输入格式类似于：

> 要求：根据这个标签名写一套问卷题目  
> 标签名：确诊为烤肠  
> 输出格式：JSON { tag, title, dims, qs, resultTypes }

试跑结果：标签名能对上，但内容开始漂移。

### 试调阶段暴露的问题

1. **Coze 输出跑题**："确诊为烤肠"生成了"摸鱼"的题——标签和内容完全对不上
2. **积分消耗过快**：变量配置都要吃积分（纯 Coze 收费陷阱）
3. **变量机制坑多**：每次清空输出不能增量，不支持动态传入现有数据
4. **一致性差**：tag→dim→qs 三层逻辑关联，Coze 记不住
5. **纯 LLM 节点已够用**：不需要加代码节点、数据库节点、Bot 配置

### 试调阶段的教训

当时把这些问题归为"提示词写得不够好"，于是继续优化提示词。这为阶段 1-2 的深入分析埋下了伏笔——其实问题不在提示词细节，在**结构层面**。

## 阶段 1：发现问题——看着像烤肠，品着不像

**时间**：5月10日  
**核心动作**：先生手动检查了第一批产出的问卷，给出了直观但致命的判断。

### 先生的原话

> "看着像烤肠，品着不像。"

这句话比任何量化指标都精准——它描述了 Coze 产出的问卷在**直觉层面**的问题：表面上有烤肠的壳（标签名、部分词汇），但仔细看内容实际上是另一回事。

### 典型症状

症状分为三类，每一类对应一种不同的"不像"：

#### 症状 1：给"烤肠"问卷塞了无关维度

`dims` 数组中出现"社交媒体活跃度"——问用户发朋友圈频次、点赞习惯。这跟烤肠有什么关系？

**本质**：在烤肠的语境下，问了一个属于"社交人格测试"的问题。源域是烤肠，维度却从人的世界直接拉过来的。

#### 症状 2：结果类型出现了"深夜emo肠"

结果是"深夜emo肠"——在烤肠的品类树中不存在"深夜emo"这个亚种。

**本质**：不是"从烤肠的品类中选了一个结果"，而是"先有一个'深夜emo的人'概念，然后把'肠'字后缀上去"。这就好比把"社恐"改成"社恐肠"就说它是烤肠分类——贴皮行为。

#### 症状 3：同一份问卷混合了烤肠、夜宵、摇滚歌手三个源域的尺度

一份问卷里，有的题目在问"淀粉含量"（烤肠属性），有的在问"夜宵频率"（吃夜宵的人属性），有的在问"躁动程度"（摇滚歌手属性）。

**本质**：Coze 在生成过程中"源头漂移"了——从烤肠漂到与烤肠相关的"夜宵场景"，再从夜宵场景漂到"夜晚躁动的摇滚歌手"。

### 发现问题的意义

先生手动检查这件事本身就是质量控制的关键一环。Coze 不会知道自己跑题了，因为它没有"一致性"的全局视角——它就是一句话接一句话地往外吐。但人一眼就能看出来。

先生发现的问题为后续的理论诊断提供了**具体的病灶**——不是抽象地说"不好"，而是具体到"哪里不对"。这三类症状直接对应了阶段 2 诊断出的三种映射失效模式。

## 阶段 2：诊断根因——映射方向错了

**时间**：5月10日  
**核心动作**：套用概念隐喻理论，用学术框架做诊断。

### 为什么选概念隐喻理论

先生做 AI 提示词优化时的一个关键认知：**如果问题不是能力问题而是逻辑问题，提示词怎么优化都救不了。**

"烤肠塞了社交媒体活跃度"——这不是 Coze 写字的水平不行，是 Coze 在逻辑层面误解了"用烤肠比喻人"到底意味着什么。Coze 理解的"确诊为烤肠"指向的是"人的各类状态，只是名字里带个肠字"，而不是"从烤肠的物理属性中生发出人的对应状态"。

概念隐喻理论（Lakoff & Johnson, 1980）恰好解释了这种差异——它区分了两种不同的映射方向，而其中一种方向必然导致"贴皮式"产出。

### Lakoff 概念隐喻理论 + 不变原则

George Lakoff 和 Mark Johnson 在 *Metaphors We Live By*（1980）中提出：隐喻不是修辞手段，而是**认知机制**——人们通过一个概念域（源域）的结构来理解另一个概念域（目标域）。

随后 Lakoff 提出的 **Invariance Principle（不变原则）**：

> 隐喻映射保留源域的认知拓扑结构，即源域的图像-图式结构必须与目标域固有结构保持一致。

翻译成人话：当你说"某人是烤肠"时，**烤肠的属性必须能回推到烤肠本身上**。如果某个属性（如"社交媒体活跃度高"）在烤肠上找不出对应物，这个映射就是断裂的——不是"从烤肠往人的映射"，而是"从人往烤肠的贴皮"。

### 核心诊断结论：映射方向错了

**正确的方向（Coze 应该做的）：**

```
源域（烤肠的物理属性） → 筛选可映射特征 → 翻译为人的状态
```

**错误的方向（Coze 实际做的）：**

```
人的状态清单（性格分类） → 遍历 → 给每类套个"肠"字后缀
```

前者是**生长出来的映射**，后者是**贴上去的标签**。后者正是概念隐喻理论中所说的"缺乏源域经验基础的空映射"。

### 三种具体映射失效模式

诊断阶段把阶段 1 发现的三种症状系统化为三类失效模式：

| 类型 | 表现 | 示例 | 诊断 |
|------|------|------|------|
| **类型A**：维度脱离源域本体 | 某个维度在源域实体上无对应物理/功能基础 | 烤肠问卷中问"社交媒体活跃度" | 维度非从烤肠派生，直接从人的世界拉来 |
| **类型B**：结果类型不是源域真实子类 | 结果是"源域名词+人属性"而非真实品类 | "深夜emo肠"——烤肠品类树中不存在 | 先有人格分类，后加"肠"字后缀 |
| **类型C**：多源域混合 | 同一份问卷维度来自两个及以上不同实体 | 一份问卷混有烤肠、夜宵、摇滚歌手 | 违反"单源域一致性" |

### 诊断阶段的重要发现

三个失效模式虽然表现形式不同，但**根因完全一样**——都是"映射方向搞反了"导致的。这意味着解决方案不需要分别治三种病，只需要**把映射方向正过来**。

但"正过来"具体怎么做？这就是阶段 3 的约束体系要解决的问题。

## 阶段 3：方案 A——设计约束体系

**时间**：5月10日 ~ 5月11日凌晨  
**核心动作**：基于诊断结论，设计一套可执行的约束规则，写入 Coze 提示词。

### 设计思路

诊断结论是"映射方向错了"，但提示词不能只写"请使用正确方向"——抽象原则对大模型是无效的。模型需要的是**执行步骤**而不是"注意事项"。

所以约束体系的核心逻辑是：**在提示词层面，强制 Coze 走一遍"从源域出发"的流程，不给它从"人的状态"出发的机会。**

### 四个约束

#### 约束 1：映射的单源一致约束

> 一份问卷/标签集内，源域有且只能有一个。

这是最基础的约束。如果问卷的源域是烤肠，所有维度、题目、选项、结果类型都**只**从烤肠及其紧密场景派生。任何引入第二个实体的维度都是违规。

这条约束堵的是 **类型C（多源域混合）**。

#### 约束 2：映射的特征筛选约束

> 从源域属性中只选择**可体验化、可行为化、可情绪化**的属性进行映射。

目的是做减法——不是所有烤肠的属性都适合映射到人。目标不是"烤肠的百科全书"，而是"人的状态隐喻"。

| 适合映射 | 不适合映射 |
|---------|-----------|
| 物理构成→内在特质 | 纯物理度量（净重、尺寸） |
| 外部特征→社交面具 | 化学成分（分子式） |
| 生命周期→人生阶段 | 生产工艺 |
| 典型遭遇→行为模式 | 非日常场景下的属性 |

这条约束堵的是 **类型A（维度脱离源域本体）** 的一个子类——即使维度是从源域拿的，如果选的是"纯百科式属性"，映射到人还是没共鸣。

#### 约束 3：结果类型的品类下位约束

> 结果分类必须是源域品类谱系中真实存在的下位类别或公认状态差异。

判断标准：去掉源域名词后，剩下的词能否独立指代该实体真实品类？能 → 对；不能 → 贴皮。

| 源域 | 可用（真实品类） | 不可用（贴皮） |
|------|----------------|---------------|
| 烤肠 | 纯肉肠、淀粉肠、玉米肠、墨鱼肠 | 深夜emo肠、社交牛逼肠 |
| 仙人掌 | 食用仙人掌、观赏仙人掌、沙漠野生耐旱种 | 职场摆烂仙人掌 |
| 手机电量 | 满格、半格、红线、关机、充电中 | 社交电量满格人 |

这条约束堵的是 **类型B（结果类型不是真实子类）**。

#### 约束 4：溯源三问自检机制

每生成一个候选维度/题目，必须通过以下三问：

1. **本体溯源**：这个维度来自源域实体的哪一个具体属性？
2. **本体必要性**：如果源域没有这个属性，它还是它自己吗？（答案必须为"不是"）
3. **映射可理解性**：把这个维度对应到人时，人是否能秒懂且不越界到其他实体？

这是 Invariance Principle 的实操版——源域的认知拓扑结构必须被保留。这三问就是检验保留程度的工具。

### 四步工作流（对应提示词中的执行步骤）

```
步骤1：强制提取源域特征表
  │  物理构成 / 外部特征 / 生命周期 / 典型场景
  ▼
步骤2：筛选可映射通道
  │  只保留可体验化、可行为化、可情绪化的属性
  ▼
步骤3：生成维度/题目（通过溯源三问自检）
  │  每个候选维度都必须通过三问测试
  ▼
步骤4：结果类型从源域品类树中取
  │  只能从真实品类/状态中选取
```

### 方案 A 的整体结构

- **约束体系**（四个约束）→ 堵三类失效模式
- **执行流程**（四步法）→ 让 Coze 走正确路径
- **写入提示词**（v3 版，即"概念隐喻版"提示词）

## 阶段 4：方案 B 的提出——Coze 管不住自己

**时间**：5月11日凌晨  
**核心动作**：先生指出方案 A 的理论正确但执行不可靠，Coze 底层模型能力有限。

### 先生的判断

先生看过方案 A 后，直接指出了核心问题：

> 方案 A 的理论是对的，逻辑也是通的。但问题不是理论对不对，是 Coze 能不能执行。

具体来说：
- 方案 A 的约束体系把大量逻辑放在 Coze 提示词里
- Coze 底层模型在生成长 JSON 时，面对高密度约束会**选择性忽略**部分规则
- 不是 Coze 不想遵守，是它**真做不到**——模型在生成途中"遗忘"了部分规则
- 给了一堆抽象原则和逻辑约束，它执行的时候还是会漂移

### 方案 B 的思路

> **把 Coze 做不到的约束，挪到自家代码里去做。**

具体来说：

```
Coze 侧 → 只管"发散产出"（脑暴、创意、骨架）
校验侧 → 自家代码来做"结构性校验和修正"（约束、规则、一致性）
```

分工依据来自之前 Coze 能力边界的分析：

| Coze 擅长（Coze 做） | Coze 不擅长（我们做） |
|---------------------|---------------------|
| 脑暴、发散、起名字 | 精确的 JSON 结构输出 |
| 写有趣的文案片段 | 多字段一致性约束 |
| 给出灵感方向 | tag→dim→qs 三层逻辑关联 |
| 有生活感的描述 | 格式合规的完整产品 |

核心原则：**Coze 出框架（灵感/创意/骨架），我们填细节（结构化/格式化/质检入库）。**

### 方案 A 与方案 B 的本质区别

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 约束位置 | Coze 提示词内 | 提示词+自家代码 |
| Coze 角色 | 全程自主生成 | 只做发散+创意 |
| 质量保障 | 靠提示词精准性 | 靠代码规则校验 |
| 理论正确性 | ✅ | ✅ |
| 实际可靠性 | ❌（Coze 执行不了） | ✅（自家代码可控） |
| 缺点 | 质量不可控 | 需要额外开发校验逻辑 |

### 方案 B 的雏形

在 Coze 使用复盘文档中，方案 B 的雏形已经落地为"分两步走"的策略：

**第一步（Coze 做）：** Coze 只输出一个"创意 brief"
```json
标签名：确诊为烤肠
title建议：你是一根什么肠？
dims建议：淀粉含量、社交媒体活跃度、夜宵频率、性价比、抗压能力
每题灵感：（每个维度对应的画面描述）
结果风格：每个维度对应一个有趣的结果身份
```

**第二步（我们做）：** 根据框架手动展开为完整 JSON
- 每个 dim 展开成 3 道题
- 写 resultTypes 的 name/emoji/emojiBg/desc
- 校对 match 字段一致性
- 输出标准 init_data 格式

这种"分两步"的策略把 Coze 的积分消耗从 400+ 降到了约 150/次，同时保证了质量可控。

## 阶段 5：文档沉淀

**时间**：5月11日凌晨 ~ 早上

## 阶段 6：方案 C——混合管线落地

**时间**：5月11日凌晨（与阶段 5 几乎同时完成）  
**核心动作**：综合方案 A 的理论正确性和方案 B 的实际可靠性，设计最终的混合方案。

### 为什么是"混合"？

方案 A 的理论框架（约束体系、四步法）在结构上完全正确，但由于 Coze 的底层模型能力限制，全塞进提示词不可行。

方案 B 的判定（"把约束挪到自家代码"）方向正确，但"分两步走"的纯手动模式不利于规模化。

方案 C 的答案是：**让两者在合适的层级上各司其职。**

### 方案 C 的全貌

```
Coze 侧（只管发散和翻译，不负责逻辑约束）
  │
  ├─ [已有·维持] 标签批量生成工作流
  │   输入：创作方向 + 已有标签列表
  │   输出：[{ name, category, emoji, description }]
  │   风格约束不变，标签够轻量，Coze 完全能搞定
  │
  ├─ [新增] 实体特征提取工作流
  │   输入：标签名
  │   输出：{ categories, features } 结构化特征表 JSON
  │   说明：纯描述任务（"烤肠有哪些品类？有什么物理特征？"）
  │        不涉及任何维度生成或映射，难度极低，Coze 几乎不可能翻车
  │
  └─ [修改] 问卷生成工作流
      输入：{ tagName, featureTable, categories }
      输出：{ tag, title, dims, qs, resultTypes }
      要求：维度从 featureTable 的可映射方向列取
           结果类型从 categories 清单取
      提示词做减法——不再塞四个约束和三套自检，只保留"照着数据画瓢"

校验侧（自家代码做结构性校验和规则匹配）
  │
  ├─ [已有·不变] 前端结构校验
  │   检查 dims 数、qs 数、字段完整度
  │   不合规则则用兜底 mock 数据
  │
  ├─ [新增] 本地入库校验脚本（Node.js）
  │   四项检查：
  │     1. 结构完整性 → 字段名、维度数 3-7、题数 = dims×3
  │     2. 维度语义告警 → 关键词匹配，维度名含源域无关词则标黄
  │     3. 品类白名单 → 结果类型名必须在 categories 数组中
  │     4. 多源域混合 → 检查一份问卷内是否出现两个实体关键词
  │   输出校验报告（JSON）→ 人工确认 → 导入数据库
  │
  └─ [新增] entity-data.json 库（缓存）
      每实体一份 JSON（特征表 + 品类树打包）
      双复用：
        · Coze 问卷生成时作为输入原料
        · 校验脚本时作为品类白名单和关键词库
      维护边界：新增实体→加一个文件，删除→删一个文件，无耦合

完整管线流程：
  步骤1: 新标签产出后 → 跑特征提取工作流 → 保存 entity-data.json
  步骤2: 跑问卷生成工作流（输入带上特征表和品类树）→ 产出问卷 JSON
  步骤3: 跑本地校验脚本 → 扫校验报告 → 人工确认可疑项
  步骤4: 确认通过 → 导入数据库
```

### 核心设计：实体档案 JSON

方法论中的"抽象约束"（特征表、品类树）在此被物化为**实体档案 JSON**——一份数据，两个用途：

```json
{
  "entity": "烤肠",
  "categories": ["纯肉肠", "淀粉肠", "玉米肠", "墨鱼肠", "脆骨肠"],
  "features": {
    "physical": ["淀粉含量高/低", "肉质紧实/松散", "表面焦脆程度"],
    "appearance": ["颜色", "烤痕", "粗细"],
    "lifecycle": ["冷冻→解冻→烤→烤爆→烤成碳"],
    "scenarios": ["便利店收银台", "烧烤摊铁板", "泡面搭档"]
  }
}
```

这份 JSON 既是提示词中的原料（Coze 不需要理解理论，只需照着数据画瓢），也是校验脚本的标尺（遍历维度名，在特征表中查对应条目）。

### 方案 C 与 A/B 的对比

| 维度 | 方案 A | 方案 B | 方案 C（最终落地） |
|------|--------|--------|-------------------|
| Coze 负载 | 高（全量约束） | 低（只出创意 brief） | 中（特征提取+轻量提示词） |
| 代码校验 | 无 | 手动 | 自动化脚本 |
| 质量保障 | 靠提示词精准性 | 靠人审+手动填 | 多层防线组合 |
| 扩展性 | X（换实体改提示词） | △（每实体手动填） | ✅（加实体=加 JSON 文件） |
| 积分消耗 | 400+/次 | ~150/次 | 约 300/次（两次工作流） |
| 可批量化 | 可 | 不可（手动填） | 可 |

### 被否方案的取舍记录

| 被否方案 | 否决原因 | 替代方案 |
|---------|---------|---------|
| 方案 A（全塞进 Coze 提示词） | 约束密度过高，弱模型生成长 JSON 时选择性忽略 | 轻型提示词 + 后端校验 |
| 向量相似度辅助筛查 | 当前 30-50 标签体量下过度设计 | 硬编码品类树 + 关键词规则 + 人工 |
| 特征提取与问卷合并为一次对话 | 认知负载过高，Coze 记不住同时做两件事 | 拆为两次独立对话 |
| 前端语义增强校验 | 离用户近但迭代慢，且交互路径上不该拦截 | 放在本地入库脚本，前端只做结构兜底 |
| 入库校验放在云函数 | 部署更新慢，不符合当前手动导入流程 | 本地脚本 + 复用逻辑至前端 |

### 长期演进路径

当前管线是"Coze 离线批量生成 + 手动审核入库"模式。未来如果演进到"用户搜索不到 → 看广告 → Coze 实时生成"的在线模式：

- 结构校验直接迁移到云函数，复用同一套规则
- 特征表缓存从本地 JSON 文件迁移到数据库表
- 校验不通过的问卷改为用兜底问卷返回，不阻塞用户体验
- 校验脚本就是唯一的防线——所以现在离线阶段把校验写扎实是值得的

## 关键教训总结

### 1. 映射方向 > 映射内容

所有质量问题的根因最终归结为一句：**映射方向错了。** 先把方向正过来，再谈写得好不好。

### 2. 约束不要全塞进提示词

Coze（以及所有基于 LLM 的平台）在生成长 JSON 时无法承受高密度约束。抽象原则在 prompt 层面会选择性消失。需要把"约束"和"发散"分开——Coze 负责发散，代码负责约束。

### 3. 理论框架的价值是对齐认知

概念隐喻理论最大的作用不是"给出答案"，而是**让先生和我的认知对齐**——当我们说"这个映射断裂了"的时候，我们指的具体是什么。有了理论语言，沟通效率提高了一截。

### 4. 标签生成 ≠ 问卷生成，要分治

| 任务 | 输出复杂度 | Coze 能力 | 方案 |
|------|-----------|-----------|------|
| 标签生成 | 低（4 字段独立） | ✅ 完全胜任 | 全 Coze 做 |
| 特征提取 | 低（纯描述） | ✅ 几乎不可能翻车 | Coze 做 |
| 问卷生成 | 高（三层一致性） | ⚠️ 需要多方保障 | 轻量提示词 + 校验脚本 |

### 5. 非实体标签 ≠ 实体隐喻标签，要分治

| | 非实体标签 | 实体隐喻标签 |
|--|-----------|-------------|
| 核心风险 | AI 味——描述像功能介绍 | 映射断裂——维度漂移、结果贴皮 |
| 灵感方法 | 生活观察 + 确诊文学三个零件 | 实体特征表 + 三个门槛 + 红线 |
| 占比 | 约 60-70% | 约 30-40% |

### 6. 核心结论

> **让 AI 做好隐喻映射的关键，不是告诉它"不要跑偏"，而是强制它先走一遍源域特征表再动笔。有了锚点，它就不会漂移。**

而最终落地的方案 C 是对这句话的进一步深化——"强制走一遍源域特征表"不一定非要在提示词里做，也可以在代码层面用校验和原料控制来实现。

## 阶段 7：数量不对问题——拆解生成流程的深层缺陷

**时间**：5月11日清晨 05:00~06:00  
**核心动作**：方案 C 落地后，实际试跑发现题目数量仍然不对——先生反馈"为什么数量还是会不对呢？"

### 触发场景

先生用修改后的合并版提示词（方案 C 提示词）跑"大招蓄力时间"标签（6 维度），产出结果：

| 维度 | 题数 | 状态 |
|------|------|------|
| 蓄力时长 | 4 题 | ❌ 超 1 题（混入了"失败懊恼"的题，应属"空大后摇"） |
| 空大后摇 | 2 题 | ❌ 缺 1 题 |
| 大招后遗症 | 0 题 | ❌ 有对应 resultType 但一道题都没写 |
| 其他 4 维 | 各 3 题 | ✅ |
| **总计** | **15 题** | ❌ 应为 18（6×3） |

### 根因诊断（四个层次）

| 层 | 问题 | 严重程度 |
|----|------|---------|
| **1. 输出模板骨架** | 第八章 JSON 示例只有 5 维/15 题。模型改成 6 维后，qs 部分仍受模板 15 个槽位影响，忘了"6 维应该 18 题" | 高 |
| **2. 创作流程矛盾** | 第五章说"先写题再认领维度"，但第七章要求"每维恰好 3 题"。写题时不跟踪维度计数，分配时必然不均匀 | 中 |
| **3. 事后检查不可执行** | 7.2 节说"遍历 qs 统计 dim 次数，不是 3 次就停止重构"。但 Coze 是左到右生成 token，检测到错误时已经到了 JSON 末尾，不可能回头改 | 高 |
| **4. 最终检查不查数量** | 第九章三条件检查都只查来源和真实性，不查总题数和每维分布 | 低 |

三个问题共同导致：**创作流程（自由发散）→ 分配（事后打标）→ 检查（不可执行）→ 正确率全凭运气。**

### 求助 DeepSeek 专家模式

先生让我写了一段提示词，去问 DeepSeek 专家模式。

**我问的三个方向**：
- A：改创作流程——废"先写题再认领"，改"逐维度写题"
- B：保留创作流程但加占位机制——先列空位表，填一道划一道
- C：改输出模板——用占位符/省略号代替硬编码示例

**DeepSeek 的核心判断**：
1. 方向 A 最可靠——将全局计数转为局部循环中的不变式，从根本上消除分配不均
2. 方向 B 不彻底——空位表只是参考，模型不会真的去"划掉"
3. 方向 C 能改善但不根治
4. 推荐"第四方案：草稿-转写双层生成"——先在 thinking 块里规划，再输出 JSON

### 我的评估和处理

**接受 DeepSeek 的观点**：
- 方向 A 确实是最可靠的——结构本身成了硬约束
- 质量保持的四招（角色+场景、多样性指令、坏例子 vs 好例子、黑名单）可以往里塞

**驳回 DeepSeek 的推荐**：
- 「草稿-转写」方案不适用于 Coze 单次调用——Coze 要求纯 JSON 输出，thinking 块需要额外"提取 JSON"代码节点，多一个故障点
- DeepSeek 自己也承认："如果平台严格限定输出纯 JSON，A 依然是唯一能根除数量错误的方案"

**最终敲定的改动方向（方向 A + 质量保持技巧）**：

| 改动项 | 当前 | 改为 |
|--------|------|------|
| 创作流程 | 先写题→再打 dim 标签 | 确定 dims → 逐维度生成 3 题 → 写完一维再写下一维 |
| 题内多样性 | 无要求 | 第 1 题行为切入、第 2 题情绪切入、第 3 题后果切入 |
| 黑名单 | 只有"别干的事" | 明确禁止"你是否""你认为""你会……吗"开头 |

## 阶段 8：维度漂移——上游结构缺陷暴露（13:00~13:30）

**时间**：5月11日 12:40~13:30  
**核心动作**：用修好题量纪律的新提示词跑"大招蓄力时间"，题量对了，但 dims 完全跑偏。

### 触发场景

先生用刚改好的提示词跑"大招蓄力时间"——这次题量纪律执行完美，每个 dim 都是 3 题，总共 15 题。但 dims 本身变成了：

```
躺平程度、社交活跃度、夜宵频率、性价比、抗压能力
```

——一套完全与"大招蓄力时间"无关的通用人格骨架。之前版本至少 dim 方向是对的（蓄力时长、空大后摇），只是题量分布有问题。现在 dim 本身都错了。

### 第一轮分析：我的错误方向

我最初的分析是"源域分类表没覆盖游戏技能机制"和"系统型模板缺游戏示例"，建议加边界说明和示例。**先生直接叫停——"这是机械地打补丁，只会增加 AI 的刻板性。"**

这个判断是对的。加示例这条路没有尽头——每个标签配一个例子，永远追不完。

### 重新诊断：问题不是分类表，是流程结构

重新审视上游（第 1-4 节），真正的根因浮出水面：

> **第 1-4 步全是"内省型指令"——要求模型'在脑子里想''问自己''心里过一遍'，没有任何必须产出的痕迹。模型可以直接从输入跳到 JSON 模板，毫无阻力。**

具体来说：

| 步骤 | 问题 |
|------|------|
| 第 1 节（你是谁） | "凌晨三点眯着眼写备忘录"的轻松直觉流 → 与"不能跳步"的严肃流程打架 |
| 第 4 节 Step 1 | 分类后没有强制输出 → 模型无声滑过，不做决策锚定 |
| 第 4 节 Step 2 | "脑子里过完才能往下走" → 人话翻译表没有显式产出 |
| 第 4 节 Step 3 | 溯源三问是"问自己" → 不是"写出答案"，容易跳过 |
| 第 8 节输出模板 | 完整的 JSON 示例太诱人 → 模型看到终点就直奔终点，跳过了中间所有工作 |

**用一个比喻总结**：提示词像在说"走到厨房，把菜切了，然后炒熟端上来"——但厨房在哪、冰箱里有什么、砧板在哪，全部默认模型自己知道。模型听到"端菜"就直接从冰箱里拿了一盘现成的。

### 产品层面的发现

在这个阶段先生发现了一个重要事实：之前的"深夜emo肠"问题和现在的"大招蓄力时间"问题其实是同一个病灶——**源域分类不稳**。只是之前分类错误暴露在 resultTypes 上（深夜emo肠），现在暴露在 dims 上（通用人格 dims）。

**同一块地基沉了，只是不同的梁先裂了。**

### 向 DeepSeek 专家模式求助（第二次）

我写了第二份提示词给 DeepSeek，不再问"怎么写"，而是问**"结构有什么病"**。这次方向对了，DeepSeek 给出了决定性贡献：

**DeepSeek 的三个核心洞察：**

1. **来源锚定**（"嵌套管脚"）——不是"加关隘拦模型"，而是"让每个 dim 自带一个必须填的上游引用"。模型写 dim 的时候必须指向一条具体的人话翻译，否则语法上就缺了一块。问题是下游长得太独立（"躺平程度"不需要解剖表就能生成），治本不是锁门，是让每块下游砖都自带一个必须填的上游孔。

2. **角色分级**——"凌晨三点眯着眼写备忘录"贯穿全流程必然打架。需要把流程分成两个阶段，每个阶段挂一个子角色：阶段 A 是"刚喝完咖啡的解剖学者"（冷静精确），阶段 B 切回"深夜被朋友叫起来的备忘录朋友"（直觉放松）。

3. **时序缺陷**——4 个解剖模板出现在第 1 步分类之前，模型还没分类已经看到了所有类型的输出样式，分类沦为"事后追认"。模板应当在分类完成之后才展示。

**这个阶段的关键结论**：治本的改动不是加规则，而是做结构重组。规则降自由度，结构只改路径。

## 阶段 9：最终轮修改——四刀结构落地 + DeepSeek 终审（13:30~19:30）

**时间**：5月11日 13:30~19:30  
**动作**：四道结构性改动落地，然后求助 DeepSeek 做最终审计。

### 四刀改动

#### 刀一：角色分阶段 + 分类确认（第 4 节开头 + Step 1 末尾）

第 4 节开头加"阶段 A——解剖阶段"标记，宣告"还没到动笔出题的时候"。Step 1 末尾加**"确认分类"**——强制模型在进入第 2 步之前明确说出"我把这个标签分为了【X 型】"。

#### 刀二：来源锚定（Step 3，溯源三问之后）

每个 dim 必须标注出处——它来自第 2 步特征表的哪个要素、对应哪条人话翻译。标注格式："蓄力时长 → 要素'状态参数' → '蓄力越长越容易陷入僵直'"。

#### 刀三：阶段 B 标记（第 5 节前）

阶段 A 结束后，在写题之前加"阶段 B——出题阶段"标记，告知模型"解剖完了，现在切换回凌晨三点被朋友叫起来的那个人"。

#### 刀四：角色设定与纪律打架 → 时态切换

解构阶段用一般现在时（"这个实体由什么构成"），出题阶段用一般将来时/过去回忆时（"你会不会……""你有没有过……"）。时态是模型的认知模式开关，比换 prompt 更有效。

### 我最初的一个错误

我意识到自己在阶段 8 第一轮给"逐维度出题铁律"写了一句"用第一章的人话翻译列表里找角度"——但**第 1 节根本没有"人话翻译列表"**（那个在 Step 2 里）。这可能把模型带歪了。修正后改为指向正确的第 4 节 Step 2。

### 关于"提示词臃肿化"的讨论

先生提出一个关键质疑：**"提示词越写越臃肿，越写让 AI 越刻板怎么办？"**

我重新审视了所有改动后发现：

- **规则类改动**（"不能…""必须…""禁止…"）——每加一条，AI 自由度降一格。第一轮的四刀主要是规则类。
- **结构类改动**（重排顺序、改输出格式、分阶段）——不降自由度，只改路径。第二轮的四刀全是结构类。

所以我们制定了一条红线：

> **这一轮改完后，不管下轮跑出来还有没有新问题，先封版不修。跑至少 10 个不同标签观察整体质量，而不是追着单个标签修。单个标签的完美不值得用整体僵化来换。**

先生认同：**"个别问卷不完美没问题，只要不是系统性让所有试卷必然有问题就 OK。"**

### DeepSeek 最终审计

先生要求我组织一份完整的审计报告问 DeepSeek 专家模式——把全部改动、我的诊断、以及"是否应该封版"的判断一起扔过去。

**DeepSeek 审计结论**：

```
这份提示词是目前版本里最成熟的——来源锚定、角色分级、对称验证、中间产物强制四个关键机制全部到位，已经可以挡住绝大部分的"跳步捏造"和"标签硬贴"问题。
```

**三个剩余风险点**（非结构缺陷，是执行层面的边界保护）：

| 风险 | DeepSeek 的诊断 | 修复方案 |
|------|---------------|---------|
| **风险一**：溯源三问砍完可能不足 5 个 dim，模型只能硬凑 | 溯源三问在数量下限压力下会空转 | 加降级规则——不足 5 个就回 Step 2 补分析，不允许硬凑 |
| **风险二**：评分方向规则在阶段 A 尾部，但它的作用域在阶段 B | 阶段 A 时模型只有维度名，没有具体题目内容，无法判断高分方向 | 迁移到阶段 B 写题之后，此时模型知道题目问了什么、高分方向在哪 |
| **风险三**："禁止以下开头句式"用字首匹配太机械 | 导致模型躲进"句句我字打头"的安全区，反而 AI 味更重 | 改成语感判断——判断标准从"以什么字开头"改成"听起来像审问还是像自己说话" |

三个风险全部落地修复。

### 批处理节点配置

Coze 自动参照批处理节点文档生成了批处理节点。测试输入：

### 性能问题：串行 vs 并行

| 问题 | 现象 |
|------|------|
| 单条生成 | ~18 秒 |
| 批处理 2 条 | ~2 分钟 |

原因：Coze 批处理节点的并发数设置是 LLM 内部的请求并发，不是启动多个并行任务。实际执行是**串行 for 循环**——跑完一个才跑下一个。

解决方案：Coze 将批处理改为并行分支模式，耗时从 ~2 分钟降为 ~18 秒。

### 质量验证结果

首次跑：**"确诊为烤肠"跑空**（dims/qs/resultTypes 全空），"社交电池"正常（含 `prompt_version: 2.0`）。

跑空原因：并行模式下 LLM 超时截断，Coze 静默地返回空数据。已让 Coze 在工作流层面添加 `_status` 字段追踪成功/失败，防止未来静默丢数据。

> ⚠️ **后记**：这个 `_status` 字段在后来的数据接入阶段反噬了——它被 `resplit.js` 映射成 `status`，云函数又用 `status: 'active'` 查询，导致字段值对不上，一条数据都查不出来。详见[阶段 11](#阶段-11调试字段反噬_status-的后门陷阱)。教训：调试标记只该记在日志里，不该进入数据结构。

第二次重跑：**两份全部输出正常**，`prompt_version: 2.0` 均已生效。

最终输出样例——"确诊为烤肠"：


### 关键发现：tagDesc 的作用

这次"大招蓄力时间"的 dims 正确了（蓄力启动门槛、蓄力仪式感、蓄力专注度、空大后摇、蓄力环境依赖——5 个，全部在方向上）——但这是在**旧版提示词**下跑出来的。

**结论**：tagDesc 写得好可以部分弥补提示词的不足。这是后续维护中的低成本高回报杠杆——与其反复调提示词，不如调好每条标签的 tagDesc。

## 阶段 11：调试字段反噬——`_status` 的后门陷阱

**时间**：5月12日  
**核心动作**：数据接入云函数时，发现 `getSurveyByTag` 查不到数据——查询条件与数据库实际字段不匹配。

### 触发场景

先生跑通云函数接入流程，调用 `getSurveyByTag` 获取指定标签的问卷——结果集一直为空。排查后发现问题出在 status 字段上：

- **云函数查的是**：`status: 'active'`
- **数据库里存的是**：`_status: 'success'`
- **差距**：`"active"` ≠ `"success"`，一条都匹配不上

### 根因追溯

顺着字段往回追溯，发现了完整的问题链条：

| 环节 | 做了什么 | 结果 |
|------|---------|------|
| **Coze 工作流** | 为调试生成的问卷加 `_status` 字段，值 `"success"` 或 `"failed"` | 这是脚手架——调试追踪不应进入数据库 |
| **resplit.js（数据切分脚本）** | 把 `_status` 映射成 `status`，保留值 `"success"` | 在脚手架上加了个平台 |
| **云函数 getSurveyByTag** | 写查询条件 `status: 'active'` | 承重墙砌上去了 |

### 第一反应（直接修）

大多数开发者看到这个问题后的第一反应是：
- "云函数查错了，改成 `_status: 'success'` 就行"
- 或者 "数据库里把 status 改成 'active'"

但仔细想一下：`_status` 是 Coze 调试阶段留下来的标记，所有入库的问卷都经过了校验，不存在 `_status: 'failed'` 的记录。这个过滤条件本身就没有意义。

### 最终修法

**直接把 `status` 查询条件删掉。**

- 所有入库的问卷都是校验合格后才导入的，不需要二次过滤
- `_status` 是 Coze 调试字段，不是业务字段，不应出现在查询条件中
- `status` 字段本就是 `resplit.js` 映射出来的冗余，数据库里本不该有这个字段

```javascript
// 改前
const res = await surveysCol.where({
  tagName: params.tagName,
  status: 'active'
}).get()

// 改后
const res = await surveysCol.where({
  tagName: params.tagName
}).get()
```

### 核心结论

> **不要把脚手架当成承重墙。**

开发过程中一定会产生临时性的东西——调试标记、mock 数据、中间变量。它们在开发阶段有其合理性，但天然应该被拆除。**最危险的往往不是忘了拆，而是在它上面又盖了新东西。** 一旦有代码依赖了它，脚手架就变成了承重墙——从"可拆可不拆"变成了"拆了就崩"。

每一步单独看都有它的"合理性"：
- Coze 加 `_status` 追踪失败？合理，调试需要
- `resplit.js` 映射成 `status` 统一格式？合理，方便管理
- 云函数用 `status: 'active'` 过滤？合理，只取有效问卷

但累积的结果就是一个调试字段变成了数据库的主查询键。

**底层原则**：每加一行代码前先问——**这个依赖最终会消失吗？如果是，那就不应该有任何东西依赖它。** 调试标记只写在日志里，不该进入数据结构；mock 数据只写在本地文件里，不该进入云函数逻辑。脚手架永远是脚手架，别让它变成房子的一部分。

## 关键教训总结（增补）

### 7. 结构化 > 规则化

这是本次迭代最重要的认知升级：

| 方法 | 效果 | 副作用 |
|------|------|--------|
| 加规则（"不能""必须"） | 短期有效 | 降 AI 自由度，增加刻板性 |
| 改结构（重排/分阶段/改格式） | 长期有效 | 不降自由度，只改路径 |

每次看到问题，先问自己："这是结构问题还是规则问题？"规则问题打补丁，结构问题重设计。

### 8. 角色设定是初始锚点，不是贯穿锚点

"凌晨三点被朋友叫起来写备忘录"的人设写得好——但让这个角色贯穿全流程（从一个轻松的直觉流到严谨的解剖流程）必然导致认知冲突。解法：**分阶段挂载子角色**，不同阶段不同认知模式。

### 9. 中间产物是防跳步的锚

没有强制中间产物的工作流等于不存在。显式产出（输出分类结果、写出人话翻译表、标注维度来源）把每一步变成可验证的关卡。模型要"跳过"一步，就必须留下一个可见的空白。

### 10. tagDesc 是高性价比杠杆

一个好 tagDesc 的效果 ≈ 半套提示词约束。"大招蓄力时间"这次在旧版提示词下也能跑出正确 dims，就是因为 tagDesc 给了足够的方向锚点。与其反复调提示词，不如在 40 条标签生成的时候就把 tagDesc 写好。

### 11. 版本号是线上验证的最后一道保险

添加 `prompt_version` 字段，输出 JSON 自带版本标记。线上出了问题不再需要猜"是不是旧版本还在跑"——看一眼 `prompt_version` 就知道。

### 12. 改到什么时候为止？

> **"个别问卷不完美没问题，只要不是系统性让所有试卷必然有问题就 OK。"**

这条先生的原话应该印在这个项目的任何质量控制文档的开头。它定义了质量标准的下限——不是"每一份都完美"，是"没有系统性偏差"。追着单个标签修到完美 = 提示词的硬化与死亡。

### 13. 脚手架永远不要变成承重墙

临时性字段和调试标记天然应该被拆除。关键是：**不要在它们上面盖新东西。** 当 `_status` 从 Coze 调试字段变成了 `status` 映射字段，又变成了云函数查询条件——每一步单独看都是"合理"的，但累积的结果就是一个调试标记变成了数据库的主查询键。

底层原则：每加一行代码前先问——"这个依赖最终会消失吗？" 如果是，那就不应该有任何东西依赖它。调试标记只写在日志里，不该进入数据库字段。
