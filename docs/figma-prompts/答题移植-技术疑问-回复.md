## 一、Touch 坐标计算

### 原因

我在原指南第 8 章第 33 条写的"`event.touches[0].x/y` 已是相对坐标，无需减 rect"是错误简化，**致歉**。准确地说：

- `touches[0].x / y`：相对于**接收事件的元素**（即绑定了 `@touchstart` 的那个节点）左上角的坐标。如果你把 `@touchstart` 直接绑在 `.o-inner` 上，那 `touches[0].x/y` 确实就是按钮内坐标，可直接使用。
- `touches[0].clientX / clientY`：相对于页面可视区域。
- `touches[0].pageX / pageY`：相对于页面文档。

**关键点**：小程序的 `event.touches[0].x` 不像 Web，它**不需要再减 rect**——前提是事件确实绑在按钮节点上、且事件没有冒泡到父节点。

但有两个坑：

1. 如果你把事件委托到父容器（如 `.opts`），那 `x/y` 是相对父容器的，需要换算。
2. 在 `<button>` 标签（不是 `<view>`）上绑事件，部分基础库版本会把坐标当作相对 page 的 client 坐标返回——**所以 ripple 容器统一用 `<view>` 而非 `<button>` 更稳**。

### 替代方案

- A. 直接用 `e.touches[0].x / y`，事件绑在 `.o-inner` 上（推荐）
- B. 用 `uni.createSelectorQuery()` 取按钮 rect，再用 `clientX - rect.left`（兼容性最稳但有一次 query 异步开销）
- C. 在 wxml/template 上给每个 `.o-inner` 用 `data-idx` 标记，事件统一在父级监听，靠 `currentTarget.dataset` + `pageX - getBoundingClientRect`

### 建议

**首选 A**：事件绑在 `.o-inner`（一定要用 `<view>` 不要用 `<button>`），直接读 `e.touches[0].x` 和 `e.touches[0].y`。这是小程序文档默认行为，所有主流基础库都按这个规则。如果实测发现某机型异常，再降级到 B（createSelectorQuery）兜底。

## 二、CSS animation 重播（digit-roll）

### 原因

小程序中 `:key` 变化不会真重建节点，CSS `animation` 不会自动重播。这是渲染层节点池复用导致的。

### 替代方案

- A. 自增 key（无效，已确认）
- B. JS 手动移除 class → `nextTick` → 加回 class（无效，小程序对 class 切换走样式 diff，但相同 animation-name 复用旧动画实例）
- C. `@animationend` + `animation-play-state`（无效，已有动画不会被"再播"）
- D. **双 animation-name 交替**（这是答题页"换一换"问题的同款方案）
- E. 用 `uni.createAnimation()` 编程式驱动 transform/opacity

### 建议

**D 双 animation-name 交替**。给数字两套同样关键帧但不同名字的 animation，每次切题翻转布尔变量：

```css
.digit-roll.a { animation: digitRollInA 0.45s cubic-bezier(0.34,1.45,0.64,1); }
.digit-roll.b { animation: digitRollInB 0.45s cubic-bezier(0.34,1.45,0.64,1); }
@keyframes digitRollInA { 0%{opacity:0;transform:translateY(28rpx) rotateX(-60deg);} 100%{opacity:1;transform:translateY(0) rotateX(0);} }
@keyframes digitRollInB { 0%{opacity:0;transform:translateY(28rpx) rotateX(-60deg);} 100%{opacity:1;transform:translateY(0) rotateX(0);} }
```

```html
<text :class="['digit-roll', digitFlip ? 'a' : 'b']">{{ idx + 1 }}</text>
```

每次 `idx++` 后 `this.digitFlip = !this.digitFlip`。这是经过验证的小程序兼容写法，无 query 开销、无 JS 节流问题。

逐字浮现的 `char-drop` 也用同样的双名思路。

## 三、CSS 自定义属性在 @keyframes 中

### 原因

`var()` 在 `@keyframes` 内部使用确实在部分老 Android 基础库（< 2.10）有兼容问题——通常表现为变量不解析、只取默认值。微信开发者工具一般正常，真机会翻车。

### 替代方案

- A. 三份硬编码 keyframes（最稳但代码冗余）
- B. JS 驱动 transform，requestAnimationFrame 更新
- C. uni-app 的 `uni.createAnimation` API
- D. 坚持 `var()`

### 最小支持基础库

按当前小程序生态实际情况，**建议设最低支持基础库为 2.20.0**（覆盖率 >99%）。在 2.20 上 `var()` 包括 `@keyframes` 内已稳定。

但**背景光斑是非关键装饰**，没必要为它绑死最低基础库。

### 建议

**A 三份硬编码 keyframes**。这是装饰动画，三份代码合计也就 30 行，换来 100% 兼容，性价比最高。不要用 JS 驱动——三个光斑各 15s 循环、60fps 持续跑 rAF 是浪费，CSS 让 GPU 处理是免费的。

```css
@keyframes orbA { 0%,100% { transform: translate(0,0) scale(1); } 50% { transform: translate(80rpx,60rpx) scale(1.15); } }
@keyframes orbB { 0%,100% { transform: translate(0,0) scale(1); } 50% { transform: translate(-100rpx,80rpx) scale(1.15); } }
@keyframes orbC { 0%,100% { transform: translate(0,0) scale(1); } 50% { transform: translate(60rpx,-80rpx) scale(1.15); } }
.orb-a { animation: orbA 12s ease-in-out infinite; }
.orb-b { animation: orbB 15s ease-in-out -3s infinite; }
.orb-c { animation: orbC 14s ease-in-out -6s infinite; }
```

低端机额外加一个 `wx.getSystemInfoSync().benchmarkLevel < 10` 判断，整层 `display: none` 即可。

## 四、选项数量不匹配（4 个 vs 3 个）

### 原因

设计稿用 4 个是为了 A/B/C/D 的标准化心理量表节奏，让评分粒度更细。但实际产品如果维度模型只需要 3 档（强否定 / 中立 / 强肯定），3 选项就够了。

### 我的回答

1. **3 个完全可以接受**，前提是后端评分模型也是 3 档制。视觉上 3 个选项更克制、点选更快、节奏更轻。
2. **评分逻辑是后端定的**，前端只是渲染。这个选项数取决于试卷数据结构 `question.options.length`。**前端做成数据驱动即可**，不要硬编码 3 或 4。
3. 不同选项数的布局差异：

| | 3 选项 | 4 选项 |
|--|------|------|
| `.o-inner` 高度 | `padding: 40rpx` 自然撑高约 `100rpx` | 同左 |
| 选项间 margin | `28rpx` | `28rpx`（不变） |
| 字母标 | 可省略（3 个时不那么必要） | 强烈建议有（区分度需求） |
| 入场 delay 步进 | `60ms`（n=0,1,2） | `60ms`（n=0,1,2,3） |
| 离场 delay 步进 | `40ms` | `40ms` |
| 闲置呼吸 delay | `0.18s × n` | `0.18s × n` |

### 建议

**保持当前 3 个选项的代码**，把"是否显示字母标"做成 prop 或全局配置开关。后端如果未来出 4 选项题，前端模板因为是 `v-for` 渲染，**零改动支持**。当前阶段把字母标先做出来但默认关闭（设计稿上有，运营可决定要不要打开）。

## 五、Ripple 与 overflow:hidden 的冲突

### 原因

Ripple 需要被圆角裁切，否则会"漏"到圆角外露出方形波纹边缘。但如果裁切层级搞错，按压时的 `scale(0.95)` 反馈会被一起裁掉。

### 各层 overflow 明细

| 元素 | overflow | 理由 |
|-----|---------|------|
| `.o-wrap` | `visible` | 容纳按压反馈外的水波光晕余韵；阴影/光环不应被它裁切 |
| `.o-inner` | `hidden` | **ripple 容器在这层裁切**，圆角生效，波纹从点击位置发散并被圆角削边 |
| ripple 容器 `.ripple` | 不需独立，直接放在 `.o-inner` 内即可 | — |
| 粒子 `.burst-dot` 容器 | 单独一层 `position: absolute; inset: 0; overflow: visible` | **要"漏"出按钮外**，否则迸溅看不到 |
| 描边环 `.ring-pulse` | 同 burst，独立一层 `overflow: visible` | 同上 |

### 建议

```css
.o-wrap   { overflow: visible; }
.o-inner  { overflow: hidden; border-radius: 48rpx; position: relative; }
.o-inner .ripple-circle { /* 在裁切层内，正常发散后被圆角削掉外溢 */ }
.o-inner .burst-layer   { position: absolute; inset: 0; overflow: visible; }
```

注意：`overflow: visible` 的子元素一旦父元素是 `overflow: hidden`，依然会被裁。所以**粒子和描边环不能放 `.o-inner` 内**，应该作为 `.o-wrap` 的兄弟节点用 `position: absolute` 叠加在按钮上方。这是结构上的小调整：

```
.o-wrap (relative, overflow visible)
├── .o-inner (overflow hidden)  ← ripple 在这层
└── .o-fx    (absolute inset 0, overflow visible, pointer-events none) ← burst / ring 在这层
```

## 六、多层 setTimeout 累积误差

### 原因

嵌套 setTimeout 的误差来源是：JS 事件循环排队 + 微任务穿插 + 小程序逻辑层与渲染层通信。三层嵌套累积可能偏移 30–60ms，肉眼边缘可察觉。

### 替代方案

- A. 时间锚点辐射式（一个起点 + 多个独立 setTimeout）
- B. 时间线管理器对象
- C. 接受 ±20ms 误差
- D. CSS animation 接管非交互时序

### 建议

**A + D 组合**：

1. **关键交互节点用 A**：在 `pick()` 入口存 `const t0 = Date.now()`，所有 setTimeout 都用 `setTimeout(fn, target - (Date.now() - t0))` 的方式辐射调用，而不是嵌套：

```js
pick(...) {
  const t0 = Date.now()
  const at = (delay, fn) => setTimeout(fn, Math.max(0, delay - (Date.now() - t0)))

  // 立即态
  cur.sel = i; cur.confirm = i
  uni.vibrateShort({ type: 'light' })

  at(220, () => this.flashVisible = false)
  at(420, () => { cur.confirm = -1 })
  at(420, () => { cur.phase = 'out' })
  at(520, () => this.startNewSlot(next))
  at(740, () => { cur.visible = false; this.locked = false })
}
```

这种写法每个事件都从 t0 算起，**误差不累积、互不影响**，单点误差最多 ±10ms。

2. **纯视觉时序用 D**：粒子、波纹、纸屑、闪光这些都靠 CSS animation 的 delay/duration 自己跑，JS 只负责"添加一次"，时序由 GPU 保证。

C 的"允许 ±20ms"在普通页面没问题，但答题页有"叠加窗口"这种 100ms 级精确需求，会肉眼看到错位。B 写时间线管理器在 5–10 个事件规模下属过度工程。

## 七、edge-glow 规格补全

### 原因

我之前在第 5.9 时序表里提了 edge-glow，但漏写了具体规格。**补全如下**。

### 规格定义

**视觉**：选中瞬间，移动容器（`.frame`）的内边缘喷出一圈橙色光晕，从内向外衰减，0.6s 内自然消失。视觉上像"整个手机壳边缘嗡的一下亮起来"。

**位置**：覆盖在 `.frame` 上的一个全屏 overlay，**`position: absolute; inset: 0`**，与 `.flash-overlay` 同层但效果不同（flash 是从底部往上的径向高光，edge-glow 是从边缘往内的内描边光晕）。

**DOM 位置**：放在 `.frame` 内、紧贴 `.flash-overlay` 之前。

**完整 CSS**：

```css
.edge-glow {
  position: absolute;
  inset: 0;
  pointer-events: none;
  z-index: 55;
  animation: edgeGlow 0.6s ease-out forwards;
}
@keyframes edgeGlow {
  0%   { opacity: 0; box-shadow: inset 0 0 0 0 rgba(249,115,22,0); }
  30%  { opacity: 1; box-shadow: inset 0 0 120rpx 8rpx rgba(249,115,22,0.55); }
  100% { opacity: 0; box-shadow: inset 0 0 0 0 rgba(249,115,22,0); }
}
```

**色彩**：橙色 `rgba(249,115,22,0.55)`，与选中态阴影同色系。

**触发**：每次选项被选中时，`edgeFlashVisible = true` → 600ms 后 `false`。

**注意**：小程序 `inset` 属性 WXSS 支持，但部分老基础库需用 `top:0; right:0; bottom:0; left:0` 替代。

## 八、震动三连在 iOS 上被吞

### 原因

iOS Taptic Engine 有硬件级"震动间隔保护"，连续震动间隔小于约 100ms 会被静默丢弃。这是 iOS 系统层面的限制，不是 `uni.vibrateShort` 的 bug。Android 各家厂商表现不一，但大多数允许密集震动。

### 我的回答

1. **知情**，原指南的"180ms 三连"是按 Android 体验设计的，iOS 上会降级。
2. **可以接受 iOS 降级为只震一次**，因为最后一题的解压感主要靠纸屑 + 跳转结果页的视觉变化承担，震动只是锦上添花。强行做三连不值得为之引入复杂的队列逻辑。
3. 如果产品同学坚持要三连，方案是把间隔拉到 **220ms 以上**，iOS 也能完整触发：

```
T+0ms   vibrateShort('heavy')
T+260ms vibrateShort('medium')   // 从 180ms 改为 260ms
T+520ms vibrateShort('light')    // 从 360ms 改为 520ms
```

总时长从 360ms 拉到 520ms，仍在最后一题的 1100ms 选中态保持内，体验不受影响。

### 建议

**改为 0 / 260ms / 520ms 三连**，iOS / Android 双端一致体验。`uni.createVibrateShort` callback 排队方案我**不推荐**——它会引入异步链复杂度，且 iOS 的限制是硬件级的，回调到达时间也救不回来。

## 九、其他细节确认

| 序号 | 项目 | 我的结论 |
|------|------|---------|
| 9 | 背景 6 色循环 transition | **必须加**。`transition: background-color 0.7s ease-out`。没有 transition 会有突兀跳色，破坏整体顺滑感。 |
| 10 | `.stage` min-height | **以 900rpx 为准**。当前代码 700rpx 是早期 3 选项时的估算值，但加上字母标 + 题目逐字浮现的预留高度后必须 900rpx，否则切题时旧卡离场会把整页高度短暂塌下来 200rpx，触发外层滚动跳动。 |
| 11 | 吐槽文案 | **用设计稿的 6 条**：`["离确诊又近了一步 🤡","嗯…有点东西 👀","你逃不掉的 🙃","这题有点扎心 🫠","最后一击 💥","稳住别慌 🫡"]`。这些是配合"贱贱的"调性精心写的，按 `currentQIdx % 6` 取。 |
| 12 | 进度条渐变 | **改成渐变** `linear-gradient(90deg, #FB923C, #F97316)`。纯色 `#FF8904` 视觉太平，渐变让进度推进有"流动感"，是解压细节之一。 |
| 13 | 进度条缓动 | **改成 0.6s + 弹性曲线**。`0.4s ease-out` 是机械化推进，`0.6s cubic-bezier(0.34, 1.45, 0.64, 1)` 是过冲一点点再回来的"啵"感，对应"答完一题的奖励反馈"。 |
| 14 | 字母标 A/B/C/D | **新增到 DOM**。定位方式：`.o-inner` 设 `position: relative`，字母标 `position: absolute; left: 40rpx; top: 50%; transform: translateY(-50%);` 圆 `56×56rpx`，文字 `24rpx` 居中。选中态背景 `rgba(255,255,255,0.25)`，文字白色。题目文字需相应 `padding-left: 96rpx`（左字母标 56 + 40 间距）避免重叠。 |
| 15 | `.o-index` 数字 vs 圈字母 | **用字母 A/B/C/D 不要圈数字**。①②③④ 在小字号下笔画粘连，且与"心理测试选项"的语义不匹配（选项 A/B/C 是行业惯例）。如果产品坚持要数字，用普通 1/2/3/4 + 圆形背景模拟"圈数字"的视觉，不要用 unicode ①②③④。 |
