## 二、技术细节与注意事项

### 条件编译注意事项
- `#ifdef H5` + `#ifndef H5` 是 uni-app 原生支持的预编译指令
- 只支持平台维度的条件（`H5`/`MP-WEIXIN`/`APP` 等），不支持自定义环境变量
- **效率分析**：H5 条件编译的 debug 代码在 MP-WEIXIN 打包时完整剔除，运行期零开销

### SVG 在微信小程序的兼容性
- 部分微信基础库版本不支持 `<image src=".svg">` 渲染
- 如果模拟器中显示空白，需要将 SVG 转为 PNG 使用
- 目前项目中的 `right.svg`、`left.svg`、`down.svg` 已引用，有问题再转

### ubuntu.png 在 HBuilderX 中的注意事项
- 中文文件名在部分构建工具中可能被编码
- `src="/static/给狐狸.png"` 在微信小程序中需要确认路径解析正确

## 三、经验总结

### 1. uni-app 条件编译的局限
- `#ifdef`/`#ifndef` 只支持平台维度条件（`H5`/`MP-WEIXIN`/`APP` 等），**没有 DEBUG/PRODUCTION 自定义条件**
- 想真正做到"开发版有调试面板、发布版无残留"，只能用 `#ifdef H5` 近似替代——H5 开发时可见，MP-WEIXIN 打包时彻底剔除
- 如果要更精确的控制，需要走 webpack DefinePlugin + 自定义环境变量，但 uni-app 小程序端不支持 `process.env`

### 2. CSS transform 跨元素兼容
- `rotate(180deg)` 对 `<text>` 和 `<image>` 都生效——替换 `▾` → `down.svg` 时，展开/收起的旋转逻辑完全不用改动CSS
- **教训**：批量替换时先确认新元素是否兼容旧 CSS，能省一次改动

### 3. 批量替换的标准化流程
```
grep 定位所有匹配 → 逐一读上下文确认结构 → 一次性替换模板 → 统一补 CSS
```
6 个文件 4 种图标，一次跑完比串行高效很多。关键是 CSS 要同步更新——你只改模板不更新 CSS，图标大小/位置就不对。

### 4. SVG 在小程序中的兼容性风险
- 微信小程序对 SVG 的支持**不保证**——部分基础库版本 `<image src=".svg">` 不渲染
- 这次选了本地 SVG 文件方案，如果出问题，
  - **降级路径 A**：用 `<u-icon name="play-right-fill">`（uview-ui 的 iconfont）
  - **降级路径 B**：SVG 转 PNG 放 `static/`

### 5. iconfont 作为中间方案的教训
- 项目已有 uview-ui 的 iconfont，最初建议用 `<u-icon name="play-right-fill">`
- 用户最终选了本地 SVG，走了三条路：Unicode 字符 → iconfont → SVG
- **结论**：用户对自己的视觉风格有自己的坚持，别过早替用户做最终决定

### 6. 待做事项文档的双轨管理
- `待做事项.md`（描述性） + `待做事项.csv`（结构化） 两套文件需要同步更新
- csv 适合程序读取和排序，md 适合人类阅读；但维护成本翻倍
- **教训**：更新时如果只改一个，另一个就会不一致

### 7. "已标记完成"不等于"已经做了"
- 今天翻了三次车：我说"雷达美化✅" → 用户说没做；我说"选项文本池✅" → 用户说没做；我说"P2 全部✅" → 又撤回
- **根因**：对话历史中用户并没有明确说过这两项已开发完成，是我根据文档标记错误推导的
- **教训**：标记状态前，要么确认功能代码真正存在，要么等用户亲口说"做完了"

### 8. @image 无图问题
- 当前 AI 模型**不支持多模态图片识别**，用户三次发 `@image` 发图都被系统过滤
- 用户以为我能看到截图，实际看不到
- **改进**：下次收到 `@image` 时，直接说明我看不到图，请用户用文字描述

### 9. 搜索页手风琴 `:key` 重建不触发动画
- 多次尝试后确认这个方案做不到：`:key` 重建视图不触发 CSS animation
- 如果未来想解决：改用 `<transition-group>` + `<transition>` + FLIP 动画，或者用 JS 驱动动画
- **结论**：不是配置问题，是技术限制，直接标记"已研究，方案不可行"

### 10. 项目图标管理规范的沉淀
- 今天统一了 4 种图标到 SVG 文件夹，建议以后：
  - 所有 UI 图标用 SVG，放 `static/` 下
  - 品牌/贴图用 PNG，放 `static/` 下
  - 不直接在模板里写 Unicode 字符当图标（`▶` `←` `▾` `🦊`）
  - 图片尺寸统一用 class 控制，不加 inline style

## 六、下午场经验总结

### 1. 微信小程序 `onShareAppMessage` 的 `imageUrl` 坑
- 传空字符串 `''` 或无效路径时，WeChat **不会报错但静默回退到页面截图**
- 调试时无法区分是"图片生成了但路径无效"还是"图片根本没生成"
- **改进**：下次先在控制台打印 `shareImagePath` 确认有值，再用该值做 `wx.previewImage` 验证路径是否有效

### 2. Canvas 在微信小程序中的局限性
- `uni.createSelectorQuery().in(this)` 要求 canvas 必须在当前组件树中
- 放在 `v-if`/`v-else` 内部的 canvas，切换条件后需要重新查询
- `canvasToTempFilePath` 是异步操作，成功回调才拿到路径
- 不能像 H5 那样用 `canvas.toDataURL()` 同步获取

### 3. uniCloud 云函数 500 的排查盲区
- "用户函数代码语法或逻辑异常" 是 uniCloud 的通用报错，不提示具体行数
- `Promise.all` 解构赋值在某些运行时可能不兼容
- 本地修改后需手动上传部署到云端，模拟器用的不是本地代码

### 4. Figma 设计图导入的模型限制
- 当前 AI 模型不支持图片识别，Figma 导出的设计图（`1.png`）无法被读取
- 提供的 Figma MCP 工具需要 fileKey 也无法使用（项目未接入 Figma API key）
- **结论**：分享图功能需要等先生自己根据视觉稿手动调 canvas 参数，或者接入支持多模态的模型再继续

### 5. 功能迭代的最小可行原则
- 分享图功能涉及面广（canvas + 后端 + 分享生命周期 + 时序竞争），一次改动过多，排查时变量太多
- **改进**：先从最简单的方案开始——不加自定义分享图，只用 WeChat 默认的页面截图确认分享链路正常 → 再加 canvas → 再加后端数据
