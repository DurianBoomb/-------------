## 4. 问卷去重办法

### 实际实现（逐行验证）

**Schema 层**：`surveys.schema.json` 索引配置（第 127-147 行）：
```json
"indexes": [
  { "name": "creatorId", "fields": [{ "name": "creatorId", "direction": "asc" }] },
  { "name": "tagName_unique", "unique": true, "fields": [{ "name": "tagName", "direction": "asc" }] }
]
```
→ **tagName 单字段唯一索引**，全局不可重复。

**云函数层**：`generateFromCoze` 冲突检测（第 583-594 行）：
```javascript
const existing = await surveysCol.where({ tagName }).limit(1).get()
if (existing.data && existing.data.length > 0) {
  if (existingSurvey.creatorId === uid) {
    // 同用户 → 删旧建新（放行）
    await surveysCol.doc(existingSurvey._id).remove()
  } else {
    // 不同用户 → 拒绝
    return { errCode: 'TAG_ALREADY_EXISTS' }
  }
}
```
→ 冲突检测是 **单字段 tagName**，不是 tagName + creatorId。

**`getSurveyByTag`**（第 493-512 行）：
```javascript
surveysCol.where({ tagName }).limit(1).get()
// 返回 list[0]，无随机逻辑
```
→ 由于唯一索引保证至多一条，直接取第一条即可。

### 与目标规则的差异

| | 当前规则 | 目标规则 |
|---|---------|---------|
| 唯一性维度 | `tagName` 单字段全局唯一 | `tagName + creatorId` 组合唯一 |
| 不同用户同名 | ❌ 拒绝 | ✅ 允许 |
| 同用户同名 | 删旧建新（覆盖） | 删旧建新（覆盖） |
| `getSurveyByTag` | 基于 tagName 单字段直接定位 | 无法单靠 tagName 定位（可能多个用户都有同名问卷） |

### 目标改动范围（未实施）

| # | 层次 | 改动 |
|---|------|------|
| 1 | `surveys.schema.json` | 唯一索引从 `tagName` 改为 `tagName + creatorId` 联合唯一索引 |
| 2 | `index.obj.js` — `generateFromCoze` | 冲突检测改为 `where({ tagName, creatorId: uid })` |
| 3 | `index.obj.js` — `getSurveyByTag` | 需要新策略处理同名多份问卷的场景 |
| 4 | `answer-quiz.vue` | `getSurveyByTag({ tagName })` 调用方需适配 |
| 5 | `quiz-home.vue` | 同名标签需显示创建者信息区分 |
| 6 | 搜索/标签池 | 所有单靠 tagName 定位问卷的路径需重新设计 |

### 关键难点

> `getSurveyByTag({ tagName })` 是答题入口的核心方法。改为组合唯一后，不能单靠 tagName 定位问卷。标签池、搜索、分享链接路径全部需要同步改造。

### 状态

## 6. 用户名不可以重复

```javascript
async updateNickname(params = {}) {
    const uid = this.uid
    if (!uid) return { errCode: 'AUTH_ERROR', errMsg: '未登录' }
    const nickname = (params.nickname || '').trim()
    if (!nickname) return { errCode: 'PARAM_ERROR', errMsg: '昵称不能为空' }
    // 直接更新，无任何唯一性检查
    await usersCol.doc(uid).update({ nickname })

}
```

## 7. 手工标签公有/私有状态

> **规则**：可见性由稀有度唯一决定——`rarity === 'handmade0'` 为私有（不在标签池和搜索中出现），**其余所有稀有度均为公开**。`searchable` 和 `status` 字段已废弃删除。

### 7a. 设计意图

- 「点击」定义为：外部用户打开 `answer-quiz` 答题页（通过分享链接进入）
- **创建者自己的点击不计入**——只算别人的来访
- **系统预置问卷照常计数**（参与热度排名），但不需要走私有→公有晋升逻辑
- 为什么是「点击」而非「分享」：分享可以被刷（反复转发），但点击代表真实的人类到访，更有含金量

核心流程：

1. 用户通过 Coze 生成手工标签，生成时 `rarity: 'handmade0'`（私有）
2. 标签以 `rarity: 'handmade0'` 存入 `survey-tags`，不在标签池中展示（`getTagList` 过滤 `rarity !== 'handmade0'`）
3. 问卷预览页（`survey-preview.vue`）顶部显示「🔒 私有问卷」Banner + 进度条「被 101 个人点击后即可公开到标签池」
4. 外部用户通过分享链接打开 `answer-quiz.vue` → `onLoad` 中调用 `recordClick({ surveyId })`
5. 云函数 `recordClick` 递增 `surveys.clickCount` + `survey-tags.clickCount`（原子操作）
6. 当 `clickCount >= 101` 时，自动将 `survey-tags` 的 `rarity` 从 `handmade0` 晋升为 `handmade1`，标签进入公共标签池
7. Survey-Preview Banner 切换为「✅ 已公开」+ 稀有度标签

### 7d. 数据架构全貌

#### 两张表的分工

```
surveys 表（问卷数据）              survey-tags 表（标签池数据）
┌─────────────────────┐            ┌─────────────────────┐
│ _id          ←──关联──→ surveyId                      │
│ tagName                    │ name                      │
│ creatorId                  │ creatorId                 │
│ clickCount ← 精确计数      │ clickCount ← 晋升判断用   │
│                            │ rarity ← 可见性唯一开关   │
└─────────────────────┘      └─────────────────────┘
```

**两个 `clickCount` 的关系**：`recordClick` 同时递增两表的 `clickCount`。晋升判断在 `survey-tags` 侧执行（≥101 → `rarity: 'handmade1'` → 自动公开）。

- 预览页通过 `generateFromCoze` 返回值拿到数字，不需要单独查 `survey-tags`
- `getMySurveys` 查 `surveys` 表时可直接拿计数，无需联查
- 若未来一个标签关联多份问卷，每份问卷独立计数，标签维度取总和或最大值

### 7f. `recordClick` 云函数完整设计

#### 接口定义

```
recordClick({ surveyId: string })
→ { errCode: 0, data: { clickCount: number, promoted: boolean } }
```

#### 核心逻辑

```javascript
async recordClick(params = {}) {
    const surveyId = (params.surveyId || '').trim()
    if (!surveyId) return { errCode: 'PARAM_ERROR', errMsg: 'surveyId 不能为空' }
    
    const uid = this.uid  // uniCloud 云对象注入的当前用户 ID
    
    try {
        const db = uniCloud.database()
        const surveysCol = db.collection('surveys')
        const tagsCol = db.collection('survey-tags')
        
        // 1. 查找问卷
        const surveyRes = await surveysCol.doc(surveyId).get()
        const survey = (surveyRes.data || [])[0]
        if (!survey) return { errCode: 'NOT_FOUND', errMsg: '问卷不存在' }
        
        // 2. 创建者自访 → 不计数
        if (uid && uid === survey.creatorId) {
            return { errCode: 0, data: { clickCount: 0, promoted: false, skipped: true, reason: 'self_visit' } }
        }
        
        // 3. 原子递增 surveys.clickCount（所有问卷都计数，包括系统预置问卷）
        const currentCount = (survey.clickCount || 0) + 1
        await surveysCol.doc(surveyId).update({
            clickCount: db.command.inc(1)
        })
        
        // 4. 同步递增 survey-tags.clickCount + 判断晋升（仅 coze 问卷走晋升逻辑）
        const isCozeSurvey = survey.source === 'coze' && !!survey.creatorId
        if (!isCozeSurvey) {
            // 系统预置问卷：只递增 survey-tags 的 clickCount（用于热度排名），不走晋升
            const sysTagRes = await tagsCol.where({ name: survey.tagName, source: 'system' }).limit(1).get()
            const sysTag = (sysTagRes.data || [])[0]
            if (sysTag) {
                await tagsCol.doc(sysTag._id).update({ clickCount: db.command.inc(1) })
            }
            return { errCode: 0, data: { clickCount: currentCount, promoted: false } }
        }
        
        const tagRes = await tagsCol.where({
            name: survey.tagName,
            creatorId: survey.creatorId,
            source: 'user'
        }).limit(1).get()
        
        const tag = (tagRes.data || [])[0]
        let promoted = false
        
        if (tag) {
            const newTagCount = (tag.clickCount || 0) + 1
            
            // 判断是否跨过等级阈值（详见 8c 节）
            const thresholds = [
                { min: 101,  rarity: 'handmade1' },
                { min: 501,  rarity: 'handmade2' },
                { min: 1501, rarity: 'handmade3' },
                { min: 5001, rarity: 'darkgold'   },
            ]
            const newRarity = thresholds.findLast(t => newTagCount >= t.min)?.rarity || 'handmade0'
            const oldRarity = tag.rarity || 'handmade0'
            const rarityChanged = newRarity !== oldRarity
            const firstPublic = rarityChanged && oldRarity === 'handmade0'
            
            await tagsCol.doc(tag._id).update({
                clickCount: db.command.inc(1),
                ...(rarityChanged ? { rarity: newRarity } : {})
            })
            
            promoted = firstPublic  // 首次离开 handmade0 = 晋升为公开
        }
        
        return {
            errCode: 0,
            data: { clickCount: currentCount, promoted }
        }
        
    } catch (e) {
        console.error('[recordClick] error:', e)
        return { errCode: 'DB_ERROR', errMsg: '记录点击计数失败' }
    }
}
```

#### 关键设计决策

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 创建者自访 | `uid === survey.creatorId` → 跳过 | 自己点自己的问卷不计数 |
| 未登录用户 | `uid` 为空 → **照常计数** | 未登录用户也是真实的外部访客，不应排除 |
| 系统预置问卷 | **照常计数**（`clickCount` 递增），但不走晋升 | 参与热度排名（精选发疯池），但不需要私有→公有那套 |
| 同一访客反复点 | **每次都计数** | 不做去重（无 cookie/设备指纹可用）。短期接受少许虚高，长期阈值足够兜底 |
| 递增方式 | `db.command.inc(1)` | 原子操作，避免并发少计 |
| 等级晋升 | `thresholds.findLast` 判断是否跨阈值，跨了则更新 `rarity` | 详见 [8b 节等级表](#8b-等级与点击量对照表) |
| 首次公开 | `oldRarity === 'handmade0'` 时晋升为 `handmade1`，`rarity` 变更后自动进入公共池 | 仅在第一次离开 handmade0 时触发，`getTagList` 自动识别非 `handmade0` |
| 晋升幂等 | `rarityChanged` 守卫 | 同等级不重复写 `rarity` |
| 两表同步 | 分开 `update`，按 surveys → tags 顺序 | uniCloud 无跨表事务，先记数再判晋升 |
| 容错 | 前端 `fire-and-forget` + `.catch(() => {})` | 计数失败不影响答题页加载 |

#### 特殊情况处理

| 场景 | 行为 |
|------|------|
| surveyId 不存在 | 返回 `NOT_FOUND`，前端静默忽略 |
| 问卷已被删除 | 同上 |
| 系统预置问卷 | **计数正常递增**（参与热度排名），但不走晋升逻辑 |
| 创建者自己打开 | `skipped: true, reason: 'self_visit'`——不计数 |
| 标签已被删（survey-tags 中找不到） | surveys 递增成功，tags 跳过 |
| 并发点击 | `db.command.inc(1)` 原子性保证不丢计数 |
| 阈值 101 并发穿透 | 两个请求都 ≥101，都写 `handmade1`——幂等 |

## 8. 标签等级与热度系统

> **规则**：热度 = 纯点击量（`clickCount`），不再使用旧的加权公式。标签等级按累计点击量自动晋升。

### 8a. 设计原则

- **热度简化**：砍掉旧的多因子加权公式（点赞 × 0.5 + 收藏 × 0.4 + 点击 × 0.3 + 分享 × 1.0 - 点踩 × 0.2），**热度 = `clickCount`**，一个数字驱动一切。
- **自增驱动**：`recordClick`（第 7 节）每次有效点击自动递增 `clickCount`，云函数内部判断是否触发等级晋升。
- **handmade0 不进入标签池**：`getTagList` 过滤 `rarity !== 'handmade0'`。外观可有可无，直接套用 `common` 样式。

### 8b. 等级与点击量对照表

| 等级 | clickCount 区间 | 说明 |
|------|----------------|------|
| handmade0 | 0 ~ 100 | 初始状态。外观套用 `common`，不在标签池中出现（`getTagList` 过滤掉了） |
| handmade1 | 101 ~ 500 | 首次晋升。`rarity` 变为 `handmade1`，自动对所有人可见 |
| handmade2 | 501 ~ 1500 | |
| handmade3 | 1501 ~ 5000 | |
| darkgold | 5001 ~ 10000 | 已达最高稀有度，进度条显示「已达最高稀有度」 |

### 8c. 晋升触发逻辑

已在 `recordClick` 云函数中实现（[7f 节](#7f-recordclick-云函数完整设计)），核心要点：

- **thresholds 数组**定义等级边界（101/501/1501/5001），`findLast` 找当前 clickCount 匹配的最高等级
- **首次离开 handmade0** 时，`rarity` 晋升为 `handmade1`，标签自动进入公共池（`getTagList` 识别为非 `handmade0`）
- 系统预置问卷不走晋升逻辑（[7f 关键设计决策](#关键设计决策)第 3 行）

### 8d. `handmade0` 等级外观

### 8e. 前端进度条（经验条）

**展示位置 1**：`my-surveys.vue` 每个问卷卡片。

**展示位置 2**：`result.vue` 最下方（分享按钮区域之下），进度条下方加一行小字「分享助力升级」。


```javascript
computed: {
  rarityLevels() {
    return [
      { rarity: 'handmade0', min: 0,    next: 101 },
      { rarity: 'handmade1', min: 101,  next: 501 },
      { rarity: 'handmade2', min: 501,  next: 1501 },
      { rarity: 'handmade3', min: 1501, next: 5001 },
      { rarity: 'darkgold',  min: 5001, next: null },
    ]
  },
  currentLevel() {
    const cnt = this.clickCount || 0
    return this.rarityLevels.findLast(l => cnt >= l.min) || this.rarityLevels[0]
  },
  nextThreshold() {
    return this.currentLevel.next || '—'
  },
  expPercent() {
    if (this.currentLevel.next == null) return 100
    const range = this.currentLevel.next - this.currentLevel.min
    return Math.min(100, ((this.clickCount || 0) - this.currentLevel.min) / range * 100)
  },
  rarityDisplay() {
    if (this.currentLevel.rarity === 'darkgold') return '已达最高'
    const next = this.rarityLevels[this.rarityLevels.indexOf(this.currentLevel) + 1]
    return next ? `→ ${next.rarity}` : ''
  }
}
```

### 第二步：云函数 `recordClick` 完整实现

#### 步骤 2.1 — 新增 `recordClick` 方法

**文件**：`uniCloud-alipay/cloudfunctions/survey/index.obj.js`

在 `module.exports` 中新增方法，推荐放在 `getSurveyByTag` 之后、`generateFromCoze` 之前：

```javascript
/**
 * 记录外部用户点击，驱动标签等级晋升
 * @param {Object} params
 * @param {string} params.surveyId - 问卷 _id
 * @returns {Object} { errCode, data: { clickCount, promoted } }
 */
async recordClick(params = {}) {
    const surveyId = (params.surveyId || '').trim()
    if (!surveyId) return { errCode: 'PARAM_ERROR', errMsg: 'surveyId 不能为空' }

    const uid = this.uid

    try {
        // 1. 查问卷
        const surveyRes = await surveysCol.doc(surveyId).get()
        const survey = (surveyRes.data || [])[0]
        if (!survey) return { errCode: 'NOT_FOUND', errMsg: '问卷不存在' }

        // 2. 创建者自访 → 不计数
        if (uid && uid === survey.creatorId) {
            return { errCode: 0, data: { clickCount: survey.clickCount || 0, promoted: false, skipped: true, reason: 'self_visit' } }
        }

        // 3. 原子递增 surveys.clickCount
        const currentCount = (survey.clickCount || 0) + 1
        await surveysCol.doc(surveyId).update({
            clickCount: db.command.inc(1)
        })

        // 4. 查对应 survey-tags 记录
        const isCozeSurvey = survey.source === 'coze' && !!survey.creatorId
        if (!isCozeSurvey) {
            // 系统预置问卷：只递增 clickCount 用于热度排名，不走晋升
            const sysTagRes = await tagsCol.where({ name: survey.tagName, source: 'system' }).limit(1).get()
            const sysTag = (sysTagRes.data || [])[0]
            if (sysTag) {
                await tagsCol.doc(sysTag._id).update({ clickCount: db.command.inc(1) })
            }
            return { errCode: 0, data: { clickCount: currentCount, promoted: false } }
        }

        // 5. 用户生成问卷：递增 + 晋升判断
        const tagRes = await tagsCol.where({
            name: survey.tagName,
            creatorId: survey.creatorId,
            source: 'user'
        }).limit(1).get()

        const tag = (tagRes.data || [])[0]
        let promoted = false

        if (tag) {
            const newTagCount = (tag.clickCount || 0) + 1

            const thresholds = [
                { min: 101,  rarity: 'handmade1' },
                { min: 501,  rarity: 'handmade2' },
                { min: 1501, rarity: 'handmade3' },
                { min: 5001, rarity: 'darkgold'   }
            ]
            const newRarity = thresholds.findLast(t => newTagCount >= t.min)?.rarity || 'handmade0'
            const oldRarity = tag.rarity || 'handmade0'
            const rarityChanged = newRarity !== oldRarity
            const firstPublic = rarityChanged && oldRarity === 'handmade0'

            await tagsCol.doc(tag._id).update({
                clickCount: db.command.inc(1),
                ...(rarityChanged ? { rarity: newRarity } : {})
            })

            promoted = firstPublic
        }

        return { errCode: 0, data: { clickCount: currentCount, promoted } }

    } catch (e) {
        console.error('[recordClick] error:', e)
        return { errCode: 'DB_ERROR', errMsg: '记录点击计数失败' }
    }
}
```

**关键设计决策**：

| 决策 | 做法 | 理由 |
|------|------|------|
| 创建者自访 | `uid === survey.creatorId` → 跳过 | 自己点自己不计数 |
| 未登录用户 | `uid` 为空 → 照常计数 | 也是真实外部访客 |
| 系统预置问卷 | 递增 `clickCount` 但不走晋升 | 参与热度排名但不需要私有→公有那套 |
| 同一访客反复点 | 每次都计数（不去重） | 无 cookie/设备指纹可用，接受少许虚高 |
| 递增方式 | `db.command.inc(1)` | 原子操作，并发安全 |
| 首次公开 | `oldRarity === 'handmade0'` 时晋升 | 仅第一次离开 handmade0 触发，幂等 |
| 晋升幂等 | `rarityChanged` 守卫 | 同等级不重复写 `rarity` |
| 两表同步 | surveys 先记 → tags 再判 | uniCloud 无跨表事务 |

## 10. 后台生成 + 双页面结果回传

> **目标**：用户点击"生成问卷"后不强制离开，自由留在搜索页或回到主页或做其他问卷。Coze 后台静默生成，用户进入主页或搜索页时自动检测并弹窗通知。

### 10.1 现状问题

- `search-page.vue` 的 `doGenerate()` 调用 Coze API 时用户只能盯着页面干等（`common/loading.js` 的 `showLoading` 是空函数）。
- 生成耗时通常 3~8 秒，体验差。

### 10.2 方案

**核心思路**：点击生成后 **不强制返回主页**——发起后台请求，有广告则先进广告，广告结束（或无广告时直接）弹出叙事层 Toast 告知「已加入队列」。结果通过 `uni.setStorageSync` 的**任务队列**回传。**主页和搜索页的 `onShow` 都检测队列**，已完成的弹窗通知，失败的报错，还在跑的底部浮层显示进度。

```
任务数据结构：
{
  id: '时间戳',          // 唯一标识，用于回调时定位
  status: 'queued',      // queued → generating → done / failed
  tagName: '标签名',
  tagDesc: '标签描述',
  data: null,            // 完成后塞入问卷数据
  errCode: null,         // 失败时塞入错误码
  errMsg: null,          // 失败时塞入错误信息
  createdAt: 时间戳       // 任务创建时间（用于超时判断）
}

用户点击生成（搜索页）
  → 关闭自定义弹窗
  → 往 uni.setStorageSync('_taskQueue') 的数组尾部追加 { status: 'queued' }
  → 发起 backgroundGenerate（async IIFE）
    → 请求发出后 status → 'generating'，更新存储
    → 回调成功：status → 'done'，data 塞问卷数据
    → 回调失败：status → 'failed'，errCode/errMsg 塞入
  → 如果有广告 → 立刻进入广告
  → 广告结束（或无广告时直接）→ Toast 叙事层文案，告知已加入队列
  → 用户留在搜索页，可自由浏览、回主页、做问卷

主页 onShow / 搜索页 onShow
  → 读取 _taskQueue
  → 遍历队列：
    - done → 弹窗：「「XXX」已生成！查看 →」→ 跳 survey-preview，点完后该任务从队列移除
    - failed → 弹窗：根据 errCode 显示对应错误文案，点确认后移除
    - generating/queued → 不弹窗，底部浮层显示「正在生成 X 个…」
  → 如果 done 的任务有多个，弹窗排队逐个弹出
  → 超过 60 秒仍 generating 的任务 → 标 failed，提示生成超时
```

**多次生成的冷却机制**：正式版需要看广告才能生成，每次生成间隔 >= 30 秒。前端在搜索页做按钮冷却，后端无需额外限制。

### 10.3 技术可行性

1. **`uniCloud.callFunction` 是 HTTP 请求，页面销毁不会中断它**。Promise 回调在请求完成后由网络层触发，不依赖页面存活。
2. **`uni.setStorageSync` 是全局同步 API**，不依赖组件 `this`，回调中纯调 API 无问题。
3. **`onShow` 是 uni-app 生命周期**，每次页面展示都会触发（包括从其他页面返回），两个页面都挂载检测，保证无论用户在哪个页面都能收到结果通知。
4. **队列状态机只有 4 个状态**：`queued → generating → done/failed`。状态切换逻辑简单，回调时根据任务 ID `findIndex` 定位并更新即可。

### 10.5 边界情况

| 情况 | 处理 |
|------|------|
| 用户生成后留在搜索页 | 搜索页 `onShow` 检测队列并弹窗；每次从其他页面切回搜索页也会触发检测 |
| 用户生成后回到主页 | 主页 `onShow` 检测队列并弹窗 |
| 用户生成后去了其他页面（如答题页） | 回到主页或搜索页时 `onShow` 检测队列并弹窗 |
| 生成失败 | 对应任务的 `status` 标 `failed`，存 errCode + errMsg，弹对应错误 |
| 用户连续多次生成（队列中有多个任务） | 新任务尾部追加。回调按 ID 匹配更新，互不覆盖 |
| 已完成的问卷用户暂不查看 | 不清理，下次 `onShow` 继续弹 |
| 用户点进队列浮层 → 关闭 → 不去查看 | 不清理对应任务，下次 `onShow` 继续弹 |
| 预览页 URL 参数过长 | 用 storage 传数据（预览页从 storage 读取并即时清理） |
| 生成中的任务 → 小程序被杀 → 重新打开 | `generating` 态的任务已发出的 HTTP 请求不受影响，回调照常触发更新 storage。如果 Coze 已经返回但小程序在后台被销毁，重新打开时队列中该任务可能仍是 `generating`——在 `onShow` 时对超过 60 秒仍 `generating` 的任务标 `failed` 并提示超时 |
| 用户在搜索页触发弹窗 → 正好切到主页 → 主页也触发同一弹窗 | 弹窗前检查任务是否还在队列中且状态为 done/failed。弹窗后立即从队列移除，避免重复弹出 |

### 10.6 队列 UI 规格

**底部浮层**：固定在页面底部，当队列中有 `generating` 或 `queued` 状态的任务时显示（主页和搜索页各自渲染）。

- 默认收起态：一行文案「正在生成 X 个…」
- 点击展开：列出每个任务的标签名 + 状态图标（排队中 / 生成中）
- 无生成中任务时自动隐藏

**弹窗**：逐条弹出。如果有多个 `done` 任务，弹完一个用户点查看/关闭后，下一个立即弹出。

### 步骤 1：search-page.vue — `backgroundGenerate` 方法

**新增方法**，放在 `doGenerate()` 之后。职责：在后台发起 Coze 生成，通过 `_taskQueue` 回传结果，不阻塞用户操作。

```javascript
// ========== 后台生成（不阻塞页面） ==========
backgroundGenerate(tagName, tagDesc) {
    // 队列容量上限检查
    const currentQueue = uni.getStorageSync('_taskQueue') || []
    if (currentQueue.length >= 10) {
        uni.showToast({
            title: '标签机手头的活太多了，先清一批再来',
            icon: 'none',
            duration: 2000
        })
        return
    }

    const taskId = String(Date.now()) + '_' + Math.random().toString(36).slice(2, 8)
    const task = {
        id: taskId,
        status: 'queued',
        tagName,
        tagDesc,
        data: null,
        errCode: null,
        errMsg: null,
        createdAt: Date.now()
    }

    // 追加到队列尾部
    currentQueue.push(task)
    uni.setStorageSync('_taskQueue', currentQueue)

    // 异步 IIFE，不 await
    ;(async () => {
        try {
            // 更新状态：queued → generating
            this._updateTaskStatus(taskId, 'generating')

            const survey = uniCloud.importObject('survey')
            const res = await survey.generateFromCoze({ tagName, tagDesc })

            if (res.errCode === 0) {
                this._updateTaskStatus(taskId, 'done', {
                    data: res.data
                })
            } else {
                this._updateTaskStatus(taskId, 'failed', {
                    errCode: res.errCode,
                    errMsg: res.errMsg || '生成失败'
                })
            }
        } catch (e) {
            console.error('[backgroundGenerate] error:', e)
            this._updateTaskStatus(taskId, 'failed', {
                errCode: 'NETWORK_ERROR',
                errMsg: '网络异常，请稍后重试'
            })
        }
    })()
},

// 工具方法：更新队列中某个任务的状态
// 同时刷新底部浮层 UI（解决后台 IIFE 状态变更后 UI 不响应的问题）
_updateTaskStatus(taskId, status, extra = {}) {
    const queue = uni.getStorageSync('_taskQueue') || []
    const idx = queue.findIndex(t => t.id === taskId)
    if (idx === -1) return
    queue[idx].status = status
    if (extra.data !== undefined) queue[idx].data = extra.data
    if (extra.errCode !== undefined) queue[idx].errCode = extra.errCode
    if (extra.errMsg !== undefined) queue[idx].errMsg = extra.errMsg
    uni.setStorageSync('_taskQueue', queue)

    // ★ 关键：立即刷新底部浮层，确保后台状态变更 UI 能响应
    this._updateQueueFloat()
},
```

**关键点**：
- `taskId` 用 `Date.now() + '_' + Math.random()` 组合，消除同毫秒碰撞风险。
- `backgroundGenerate` 开头检查队列上限 10 条，超出直接拒绝 + Toast。
- `_updateTaskStatus` 末尾调用 `this._updateQueueFloat()` —— 这是解决「后台 IIFE 改了状态但浮层 UI 不刷新」的关键。`_updateQueueFloat` 会重新读 storage 并更新 `queueActiveList`。
- `_updateTaskStatus` 通过 `taskId` 精准定位，互不覆盖。

```javascript
_checkTaskQueue() {
    let queue = uni.getStorageSync('_taskQueue') || []
    if (queue.length === 0) return

    const now = Date.now()
    const ONE_DAY = 24 * 60 * 60 * 1000
    const ONE_HOUR = 60 * 60 * 1000

    // 0. 清理过期任务（先清理再处理，减少无效弹窗）
    const before = queue.length
    queue = queue.filter(t => {
        const age = now - t.createdAt
        if (t.status === 'done' && age > ONE_DAY) return false
        if (t.status === 'failed' && age > ONE_HOUR) return false
        return true
    })
    if (queue.length < before) {
        uni.setStorageSync('_taskQueue', queue)
    }

    // 1. 超时兜底：超过 60s 仍 generating 的标 failed
    const staleGenerating = queue.filter(
        t => t.status === 'generating' && (now - t.createdAt) > 60000
    )
    staleGenerating.forEach(t => {
        this._updateTaskStatus(t.id, 'failed', {
            errCode: 'TIMEOUT',
            errMsg: this._getErrMsg('TIMEOUT')
        })
    })

    // 重新读队列（超时标记会改写 storage）
    queue = uni.getStorageSync('_taskQueue') || []

    // 2. 处理已完成的任务（逐个弹窗，优先级最高）
    const doneTasks = queue.filter(t => t.status === 'done')
    if (doneTasks.length > 0) {
        this._popNextDone(doneTasks)
    }

    // 3. 处理失败的任务（只有没有 done 时才弹）
    const failedTasks = queue.filter(t => t.status === 'failed')
    if (failedTasks.length > 0 && doneTasks.length === 0) {
        this._popNextFailed(failedTasks)
    }

    // 4. 更新底部浮层
    this._updateQueueFloat()
},
```

**`_popNextDone`（权威版——storage 传数据 + complete 回调 + 二次检查）**：

```javascript
_popNextDone(tasks) {
    if (tasks.length === 0) {
        // done 弹完 → 检查是否有 failed 待处理
        const queue = uni.getStorageSync('_taskQueue') || []
        const failed = queue.filter(t => t.status === 'failed')
        if (failed.length > 0) this._popNextFailed(failed)
        return
    }
    const task = tasks[0]

    // 二次检查：任务是否还在队列中且状态仍为 done（防止双页面重复弹窗）
    const currentQueue = uni.getStorageSync('_taskQueue') || []
    const stillThere = currentQueue.find(t => t.id === task.id && t.status === 'done')
    if (!stillThere) {
        // 已被另一边处理 → 跳过，弹下一个
        const remaining = tasks.slice(1)
        this.$nextTick(() => { this._popNextDone(remaining) })
        return
    }

    uni.showModal({
        title: '生成完成',
        content: `「${task.tagName}」已生成！`,
        confirmText: '查看',
        cancelText: '稍后',
        success: (res) => {
            if (res.confirm) {
                this._removeTask(task.id)
                const q = task.data?.questionnaire
                if (q) {
                    // 通过 storage 传大体积数据，避免 URL 过长截断
                    uni.setStorageSync('_previewData', task.data)
                    uni.navigateTo({
                        url: '/pages-tools/survey-preview/survey-preview?' +
                            'tag=' + encodeURIComponent(task.tagName) +
                            '&surveyId=' + encodeURIComponent(task.data.surveyId || '') +
                            '&from=queue'
                    })
                }
            }
            // 点「稍后」→ 任务保留，下次 onShow 继续弹
        },
        complete: () => {
            // 不管用户怎么操作，继续弹下一个 done 任务
            const remaining = tasks.slice(1)
            this._popNextDone(remaining)
        }
    })
},
```

```javascript
    if (tasks.length === 0) return
```

### 技术细节 B：`_popNextDone` 弹窗递归的并发安全

问题：`showModal` 是异步的，前一个弹窗还没关闭时用户切到另一个页面，另一个页面的 `onShow` 也会触发 `_checkTaskQueue`，可能弹出同一任务的 Modal。

解决方案（已内置在步骤 3 的权威版 `_popNextDone` 中）：

1. **弹窗前二次检查**：`getStorageSync` 确认任务仍在队列且状态仍为 `done`，已被消费则直接跳过。
2. **`complete` 替代 `$nextTick`**：不管用户点哪个按钮（或安卓返回键关闭），`complete` 最终都会触发下一个任务的弹窗，不会卡住队列。

## 条目 4 实施方案（已确认：2026-05-29）

> **策略**：索引改为 `tagName + creatorId` 联合唯一，`getSurveyByTag` 新增可选 `surveyId` 参数做双模式查询。能拿到 `surveyId` 的地方用 `surveyId` 精准定位，拿不到的退回到 `tagName` 查询（保证向后兼容）。
>
> **原则**：改动最小化。不做架构级重构，不引入新表/新方法，只改现有路径的传参方式。

### 方案概述（通俗版）

- **现在**：标签名是「全球独一份」——数据库硬约束 `tagName_unique` 保证全局不可重名。
- **目标**：不同用户可以用同一个标签名。张三的「猫」和李四的「猫」同时存在。
- **怎么解决定位问题**：不用标签名找人，用身份证号（`_id`/`surveyId`）找人。`surveyId` 不是新属性——每份问卷自诞生起 MongoDB 就自动生成了 `_id`，`generateFromCoze` 返回时也带着 `surveyId`。只是一直没被充分利用。

### 后端改动（3 处）

| # | 文件 | 改动 | 说明 |
|---|------|------|------|
| 1 | `surveys.schema.json` | 删除 `tagName_unique` 单字段索引，新增 `tagName_creatorId_unique` 联合唯一索引 | 物理层约束从「全局不可重名」变为「同一人不可重名」 |
| 2 | `survey/index.obj.js` — `generateFromCoze` | 冲突检测从 `where({ tagName })` 改为 `where({ tagName, creatorId: uid })` | 配合新索引，只检查本人是否用过此标签名 |

```json
  { "name": "creatorId", "fields": [{ "name": "creatorId", "direction": "asc" }] },
  { "name": "tagName_creatorId_unique", "unique": true, "fields": [
```

```javascript
async getSurveyByTag(params) {
  const { tagName, surveyId } = params || {}
  if (!tagName && !surveyId) return { errCode: 'PARAM_ERROR', errMsg: '参数不能为空' }
  try {
    let res
    if (surveyId) {
      res = await surveysCol.doc(surveyId).get()
    } else {
      res = await surveysCol.where({ tagName }).limit(1).get()
    }
    const list = res.data || []
    if (list.length === 0) return { errCode: 'NOT_FOUND', errMsg: '未找到问卷' }
    return { errCode: 0, data: list[0] }
  } catch (e) {
    return { errCode: 'DB_ERROR', errMsg: '问卷查询失败' }
  }
}
```

**目标代码**：
```javascript
async updateNickname(params = {}) {
    const uid = this.uid
    if (!uid) return { errCode: 'AUTH_ERROR', errMsg: '未登录' }
    const nickname = (params.nickname || '').trim()
    if (!nickname) return { errCode: 'PARAM_ERROR', errMsg: '昵称不能为空' }
    try {
        const usersCol = db.collection('uni-id-users')
        // 冲突检测：昵称是否已被其他用户占用
        const existing = await usersCol.where({ nickname }).limit(1).get()
        if (existing.data && existing.data.length > 0 && existing.data[0]._id !== uid) {
            return { errCode: 'NICKNAME_TAKEN', errMsg: '该昵称已被使用' }
        }
        await usersCol.doc(uid).update({ nickname })
        return { errCode: 0, data: { nickname } }
    } catch (e) {
        console.error('[updateNickname] error:', e)
        return { errCode: 'DB_ERROR', errMsg: '昵称修改失败' }
    }
}
```

**改动要点**：

- 在 `doc(uid).update()` 之前插入 `where({ nickname }).limit(1).get()` 检查
- 若存在且 `_id !== uid`：返回 `NICKNAME_TAKEN`（允许用户自己改成和当前相同的昵称）
- 若不存在或查到自己：继续正常更新
- uni-id-users 表 nickname 无唯一索引，该检查依赖应用层逻辑，会有微小竞态窗口但可接受

**边界情况**：
- 用户 A 把昵称从「张三」改成「李四」→ `where({ nickname: '李四' })` 查到用户 B → 拒绝 ✅
- 用户 A 不改昵称再次保存「张三」→ 查到自己，`_id === uid` → 放行 ✅
- 两个用户同时改成同一昵称 → 极小概率竞态，不做分布式锁处理，可接受

**目标代码**：
```javascript
async getSurveyByTag(params) {
    const { tagName, surveyId } = params || {}
    if (!tagName && !surveyId) {
        return { errCode: 'PARAM_ERROR', errMsg: '标签名和问卷ID至少提供一个' }
    }
    try {
        let res
        if (surveyId) {
            // 精准定位：通过 _id 直查（O(1)，排除同名歧义）
            res = await surveysCol.doc(surveyId).get()
        } else {
```

|------|---------|------|
| `surveyId` 存在 | `doc(surveyId).get()` — O(1) 精准 | 标签池点、分享链接、预览跳转 |
| 仅 `tagName` | `where({ tagName }).limit(1)` — 兜底 | 旧分享链接（不带 surveyId） |

##### 3.3a：增强返回 — 附带 `clickCount` + `rarity`

`getSurveyByTag` 查完 `surveys` 表后，顺手查 `survey-tags` 表拿点击数和等级，一并返回。**不新增接口、不新增网络请求**——调用方一次调用拿齐所有需要的数据。

```javascript
async getSurveyByTag(params) {
    const { tagName, surveyId } = params || {}
    if (!tagName && !surveyId) {
        return { errCode: 'PARAM_ERROR', errMsg: '标签名和问卷ID至少提供一个' }
    }
    try {
        let res
        if (surveyId) {
            res = await surveysCol.doc(surveyId).get()
        } else {
            res = await surveysCol.where({ tagName }).limit(1).get()
        }
        const list = res.data || []
        if (list.length === 0) {
            return { errCode: 'NOT_FOUND', errMsg: '未找到该标签的问卷' }
        }
        const survey = list[0]

        // 顺带查 survey-tags 拿 clickCount + rarity
        let clickCount = 0
        let rarity = 'handmade0'
        try {
            const tagRes = await tagsCol.where({
                name: survey.tagName,
                source: survey.source === 'coze' ? 'user' : 'system',
                ...(survey.creatorId ? { creatorId: survey.creatorId } : {})
            }).limit(1).get()
            const tag = (tagRes.data || [])[0]
            if (tag) {
                clickCount = tag.clickCount || 0
                rarity = tag.rarity || 'handmade0'
            }
        } catch (_) { /* survey-tags 查失败不阻塞，用默认值 */ }

        return {
            errCode: 0,
            data: {
                ...survey,
                clickCount,
                rarity
            }
        }
    } catch (e) {
        return { errCode: 'DB_ERROR', errMsg: '问卷查询失败' }
    }
}
```

**关键设计**：
- survey-tags 查询用 `try/catch` 包裹——查失败了不阻塞主流程，用默认值兜底
- `source` 自动推导：coze 来源对应用户标签，否则对系统标签
- 返回的 `clickCount` / `rarity` 直接挂在问卷数据上，前端无需额外处理

### 阶段四：端到端验收

完整流程测试清单：

```
1. 用户名去重：
   □ 用户 A 设置昵称「测试用户」→ 成功
   □ 用户 B 设置昵称「测试用户」→ 弹窗「该昵称已被使用」
   □ 用户 A 再次保存「测试用户」→ 成功（允许同用户不改名保存）

2. 标签生成 + 入池：
   □ 用户 A 生成标签「端到端测试」→ 成功
   □ 返回标签池首页 → 标签池中出现「端到端测试」，橙色 handmade1 样式，带 @用户A
   □ 点击标签 → 进入答题页，URL 含 surveyId

3. 问卷去重（核心）：
   □ 用户 A 再次生成「端到端测试」→ 成功（覆盖旧问卷，重新生成）
   □ 用户 B 生成标签「端到端测试」→ 成功（允许同名，与旧方案不同！）
   □ 用户 B 再次生成「端到端测试」→ 成功（覆盖 B 自己的旧问卷）

4. 答题 + 分享（精准定位）：
   □ 用户 A 点击自己的「端到端测试」→ 进入 A 的问卷（非 B 的）
   □ 用户 A 答题完成 → 结果页 -> 收藏/点赞
   □ 用户 A 分享 → 用户 B 点开分享链接 → 进入 A 的问卷（通过 surveyId 精准定位）

5. 向后兼容：
   □ 用旧分享链接（仅 tagName，无 surveyId）→ 兜底查询，不报错
   □ 多个同名标签时，旧链接返回 limit(1) 第一条（行为降级但不断裂）
```
