## 1. 当前基线

### 1.1 已有基础设施

| 系统 | 现有实现 | 粒度 |
|------|----------|------|
| 点赞/点踩 | `voteTag({ tagName, type })` → 写入 `survey-votes` | 标签级 |
| 收藏 | `toggleFavorite({ tagName })` → 写入 `survey-favorites` | 标签级 |
| 分享 | `survey-tags.schema.json` 已有 `shareCount` 字段 | 标签级（但无云函数方法，无人写入） |
| 问卷详情 | `getSurveyDetail({ surveyId })` | 问卷级 |
| 数据表 | `survey-answers`（答题记录）、`survey-favorites`（收藏）、`survey-votes`（投票） | — |

### 1.2 重要背景

- **标签与问卷目前是一一对应的**（至少 ID 层面一一对应）
- 用户实际上**无法**在标签池为标签点赞
- 因此 `voteTag`/`toggleFavorite` 在标签级的存在与阶段二不冲突——我们直接新建问卷级方法，两套各自独立

## 2. 已确认决策

### 决策 A：问卷级独立方法 ✅ 已确认

**方案：A1 — 新增独立问卷级方法，标签级保持不动**

- 新增 `likeSurvey`、`dislikeSurvey`、`toggleFavoriteSurvey`、`recordClick`、`recordShare`
- 热度算法只读问卷级计数
- 不改动现有 `voteTag`/`toggleFavorite`

### 决策 B：每日热度实现方式 ✅ 已确认

**方案：B2 — 增量法**

- 每个问卷 5 个每日增量字段：`dailyLikeCount`/`dailyDislikeCount`/`dailyClickCount`/`dailyFavCount`/`dailyShareCount`
- 每次操作同时 +1 总量和日量
- 阶段三实现零点定时任务清零日量

### 决策 C：shareCount 归属 ✅ 已确认

**方案：C3 — 平时只写 `surveys.shareCount`，达到 100 时反写 `survey-tags`**

- 避免每次分享写两个表
- 阈值触发时同步 `shareCount` 值到 `survey-tags` 并升级稀有度

### 决策 D：点击防刷 ✅ 已确认

**方案：复用 `survey-answers` 表，查当日答题记录**

```javascript

const exists = await answersCol.where({
```

可行性依据：

### 3.3 新增集合：survey-heat-records

专用于点赞/点踩防刷：

```jsonc

  "createdAt": { "bsonType": "timestamp", "defaultValue": { "$env": "now" } }

```

索引：

```jsonc
"indexes": [

    "name": "userId_surveyId",
```

唯一索引保证同一用户对同一问卷只有一条记录。

## 4. 云函数新增方法

> 所有新方法加在 `uniCloud-alipay/cloudfunctions/survey/index.obj.js`。该文件已有 `answersCol` 等引用可直接复用。

### 4.1 `likeSurvey({ surveyId })` 和 `dislikeSurvey({ surveyId })`

```
likeSurvey:
  1. 查 survey-heat-records 是否有 { userId, surveyId }
  2. 无记录 → 写入 type=like → surveys.likeCount +1, dailyLikeCount +1
     返回 { liked: true, disliked: false, likeCount, dislikeCount }
  3. 有记录且 type=like → 取消点赞 → 删除记录 → surveys.likeCount -1, dailyLikeCount -1
     返回 { liked: false, disliked: false, likeCount, dislikeCount }
  4. 有记录且 type=dislike → 切换 → 改 type=like → surveys.dislikeCount -1, likeCount +1, daily 同步调整
     返回 { liked: true, disliked: false, likeCount, dislikeCount }

dislikeSurvey: 对称逻辑，返回 { liked, disliked, likeCount, dislikeCount }
```

> 注意：步骤 2~4 是「检查 → 写入」两步操作，存在并发竞态。当前用户量小可接受，后续量大时用 `db.command.inc()` 原子操作 + 单独查记录状态来规避。

### 4.2 `recordClick({ surveyId })`

```
  1. 查 survey-answers 当日是否有 { userId, surveyId }
  2. 无 → surveys.clickCount +1, dailyClickCount +1
     返回 { counted: true }
  3. 有 → 不计数，返回 { counted: false }
```

前端调用点：`answer-quiz/answer-quiz.vue` 的 `onLoad` 中，不阻塞页面渲染（fire-and-forget）。

### 4.3 `toggleFavoriteSurvey({ surveyId })`

```
  1. 查 survey-fav-records 是否有 { userId, surveyId }
  2. 已收藏 → 删除记录 → surveys.favCount -1, dailyFavCount -1
     返回 { favorited: false, favCount }
  3. 未收藏 → 新增记录 → surveys.favCount +1, dailyFavCount +1
     返回 { favorited: true, favCount }
```

注意：不使用现有的 `survey-favorites` 表（该表 `tagName` 为 required 且无 `surveyId` 字段）。使用新建的 `survey-fav-records` 集合。

### 4.4 `recordShare({ surveyId })`

```
  1. 原子递增 surveys.shareCount +1, dailyShareCount +1
  2. 读当前 shareCount，若 >= 100：
     a. 查 surveys 获取 tagName（surveys.tagName 对应 survey-tags.name）
     b. 查 survey-tags 是否有 { name: tagName } 的记录
     c. 若无 → 创建 { name: tagName, source: "user", rarity: "handmade1", searchable: true, status: "published" }
     d. 若有且 rarity < handmade1 → 升级为 handmade1，同步 shareCount
     e. 若有且已 >= handmade1 → 跳过
  3. 返回 { shareCount: 新值, published: boolean }
```

> `surveys.tagName` 与 `survey-tags.name` 对应。需要先查一次 `surveys` 才能拿到 tagName 去匹配 `survey-tags`。多一次 DB 读，但只在 >=100 阈值路径触发，不影响热门路径性能。

### 4.5 `getSurveyDetail` 返回值扩展

原方法仅返回问卷结构数据。阶段二扩展：追加热度计数 + 当前用户状态。

```diff
返回新增：
+ likeCount, dislikeCount, clickCount, favCount, shareCount   // 全量计数
+ hasLiked, hasDisliked, hasFavorited                          // 当前用户状态（查 survey-heat-records + survey-fav-records）
```

一次请求拿到所有数据，result 页无需额外调接口获取按钮初始状态。
