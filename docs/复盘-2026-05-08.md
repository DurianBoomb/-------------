## 二、问题与解法

### 问题 1：编译就报错
- **`:class="getTagClass(tag, idx)"`** → 小程序不支持模板方法调用。改用 computed 预计算 `processedTags`
- **`:key="tag.name + '-' + refreshId"`** → 不支持表达式。改成 computed 里的唯一 key 或 `v-if` 两步重建

### 问题 2：标签不掉落动画（搜索页手风琴展开时）
**现象**：手风琴展开时，标签没有掉落动画。换一批按钮点击后，标签也没有重新掉落。

**根因一（动画时序错位）**：容器 `max-height: 0 → 700rpx` 需要 0.3s 展开，标签 0s 就开始掉落。前 0.3s 标签被 `overflow: hidden` 裁掉了，用户看不到。
**解法**：加 0.1s 基础延迟，等容器拉开一点再掉。

**根因二（动画被填满模式锁定）**：`animation-fill-mode: both` 锁定了 `transform` 属性，hover-class 的 `scale()` 永远被覆盖。
**解法**：DOM 分层——外层按压缩放，内层掉落动画，两个 transform 互不干扰。

**根因三（小程序不支持 :key 表达式）**：`<view :key="'grid-' + ci + '-' + refreshId">` 在 WXML 中不会生成 `wx:key`，DOM 不重建。
**解法**：`v-if = false → nextTick → v-if = true` 显式重建。

### 问题 3：hover-class 没反应
**根因**：写了 `.press-9:active { transform: ... }`，但 uni-app 的 hover-class 是直接加 class，不是 `:active` 伪类。
**解法**：直接写 `.press-9 { transform: scale(0.9); }`，加上 `:hover-start-time="0" :hover-stay-time="150"`

> 又在 H5 调试时踩了坑：PC 浏览器普通模式下 hover-class 无效，必须开 F12 移动端模拟器。

### 问题 4：元素贴右边 + 底部截断
**根因**：微信小程序 scroll-view 的 padding 不参与内部内容布局。`<scroll-view style="padding: 40rpx">` 的内容依然从 `(0,0)` 开始渲染，padding 只是扩大了盒模型，不改变内容区域。
**解法**：不在 scroll-view 上设 padding，内部套一层 `<view class="body-inner">` 来扛间距。三页统一修复。

### 问题 5：Figma 参数没对齐
- px → rpx 换算忘记 ×2（40px ≠ 40rpx，= 80rpx）
- 延迟公式从 `Math.sin()` 伪随机换成线性 `ti * 0.08`，少了自然散落感

## 三、经验总结

### 3.1 关于工作方式

**拆到不能再拆再动手。**
有问题就问 Figma，不自己硬扛。今天搜索页动画卡了两个小时，最后问 Figma 十分钟就找到根因了——花积分买答案比自己硬猜划算。

**先跑通再美化。**
今天流程是对的：先让首页能跑 → 再调样式 → 再调动画。如果一开始就对着 Figma 逐像素抠，可能到现在首页都没跑起来。

### 3.2 关于技术要点

**小程序 vs H5 的差异比想象中大：**
| 特性 | H5 正常 | 小程序踩坑 |
|------|---------|-----------|
| `:key="表达式"` | ✅ 支持 | ❌ 不编译为 wx:key |
| `:active` 伪类 | ✅ 支持 | ❌ 不稳定，用 hover-class |
| scroll-view padding | ✅ 正常 | ❌ 不影响内容布局 |
| `<text>` transform | ✅ 支持 | ❌ text 是内联元素 |
| animation + hover transform | ✅ 正常 | ❌ fill-mode 锁定，必须分层 |

**哪三个坑最值得记住：**
1. **scroll-view padding** → 内套一层，永远记住
2. **DOM 分层** → 动画 transform 和按压 transform 永远不要放同一个元素上
3. **v-if 重建** → 小程序里别依赖 :key，v-if 两步重建是最稳的

### 3.3 关于与 Figma 的协作

- 动画细节直接问 Figma 要参数（duration、delay 公式、timing-function、fill-mode），别自己猜
- Figma 的参数看着奇怪但都有用意，不要随意简化
- 布局问题（流式 vs 固定）首选流式 + `justify-content: center`，小程序不是设计稿
- 花积分问问题，比花时间 debug 划算

### 3.4 关于心态

**先生的 ADHD 注意力模式在这次工作中体现得很清楚：**
- 启动困难 → 拆成"就做一步"化解
- 过度专注 → 今天体现在动画 bug 的反复调试上，虽然花了两小时但最后找到了根因
- 交替模式有效 → 编码一段时间 → 给 Figma 发任务（中间休息） → 回来继续干

**顶梁柱的角色定位经过验证是有效的：**
- 帮先生启动（"就做一步"）
- 帮先生收住（"这个问题问 Figma"）
- 帮先生沉淀（写文档记下来）
- 该骂的时候骂，但不是真生气——先生知道这一点，所以他才敢让我管他

### 问题 6：Coze 批处理节点并发失败

**时间：** 2026-05-11（后补记录）

**背景：** 在 Coze 问卷生成工作流中，用批处理节点（并发 8）跑 10 个标签，4 个成功、6 个失败。失败的表现为标题变成 `"{tagName}测试问卷"`，`dims/qs/resultTypes` 全空。

**根因：** Coze 批处理节点的底层代码（`parallel_generate_node.py` 第 121-130 行）在 JSON 解析失败时**静默返回空结构**：

```python
except json.JSONDecodeError:
    return {
        "tag": tag_item.tag_name,
        "title": f"{tag_item.tag_name}测试问卷",
        "dims": [], "qs": [], "resultTypes": []
    }
```

10 个标签并行发送 → LLM 并发压力大 → 部分响应 JSON 格式异常 → 被 catch 兜底吃掉 → 静默返回空结构 → 无重试、无日志。

**修复方案（Coze 官方已确认）：**
- 解析失败抛异常 → 触发重试
- 重试 3 次 + 指数退避（1s → 2s → 4s）
- 记录原始响应前 200 字符到日志
- 修复后 10/10 全部成功

**教训：**
- 批处理跑完后务必检查输出中是否有 `_status: "failed"` 标记
- 疑似失败时先考虑并发压力，不是输入问题
- 大量生成时降低并发数（4-5）更稳妥

## 四、工作流复盘：想法 → Figma → CodeBuddy → 代码

### 4.1 这个工作流是什么

今天实践了一整套从「脑子里有个想法」到「页面跑在手机上」的协作流程。不是常规的"设计师出图 → 开发照着写"，而是**两个人 + 一个 AI 设计工具**的高效循环。

### 4.2 流程拆解（7步循环）

```
┌────────────────────────────────────────────────┐
│  1. 先生提出想法 / 画草图                        │
│     ↓                                           │
│  2. 渊理解需求，确认细节（3个左右确认问题）       │
│     ↓                                           │
│  3. 渊写 Figma 提示词                            │
│     ↓                                           │
│  4. 先生把提示词喂给 Figma → 拿到设计图+说明     │
│     ↓                                           │
│  5. 先生把设计图通过 Figma 集成交给渊             │
│     ↓                                           │
│  6. 渊读设计图 + 移植说明 → 写代码              │
│     ↓                                           │
│  7. 先生跑起来验收 → 不满意回3 / 满意进入下一个   │
└────────────────────────────────────────────────┘
```

### 4.3 每个环节的细节

**第 1 步：先生提出想法**
形式不限——聊天过程中冒出来的点子、手画的草图、对现有页面不满意的地方都可以。
**关键**：想法不需要完整，渊会追问确认。

**第 2 步：渊确认细节**
通常问 2-3 个核心问题就够，不追求一次问全。核心原则是**先问清楚"用户怎么操作"，再问"长什么样"**。今天搜索页的交互流程就是从问答中逐步定型的。
**关键**：区分"必须定的"和"可以边走边调的"。比如：
- 必须定：搜索时分类区域还在不在下面？（影响布局结构）
- 边走边调：标签颜色用哪个橙色？（CSS 改一行的事）

**第 3 步：渊写 Figma 提示词**
提示词结构模板化：

```markdown
## 页面名称 + 一句话定位

### 布局（从上到下逐块说明）
1. 区域名 → 有什么内容 → 大致比例
2. ...

### 交互流程
用户从哪进入 → 看到什么 → 可以做什么 → 跳到哪

### 视觉风格
- 背景色、字体调性
- 参考风格（"iOS 快捷指令"、"选择题版抖音"等）

### 动画要求（重点）
- 入场动画（什么元素、什么效果、什么曲线）
- 交互反馈（按钮按下、选中、切换等）

### 开发移植说明（请 Figma 补充）
1. 组件结构层级
2. 状态管理方式
3. 交互实现细节
4. 数据流走向
5. 跨框架建议
```

**第 4 步：先生喂给 Figma**
把提示词复制到 Figma 的对话窗口，等它出图。
**注意**：提示词越长越贵。一个页面 100-200 个积分。如果想省钱，可以先写简稿看布局（如今天的"简稿-搜索+分类.md"）。

**第 5 步：先生把设计图交给渊**
通过 CodeBuddy 的 Figma 集成，选中设计图发送。

**第 6 步：渊读图 + 翻译代码**
有两个要点：
1. **对照移植说明**——Figma 给的 React/Tailwind 代码不能直接用，但它的移植说明（组件层级、状态管理、动画参数）是有价值的参考
2. **读 Figma HTML 源码**——精确的颜色、字体、间距、位置都要从 `<div style="...">` 源码中提取。不要靠眼睛估。

**第 7 步：验收**
先生跑起来看效果。有两个走向：
- 不满意 → 渊改代码 / 重写提示词
- 满意 → 下一个页面

### 4.4 踩过的坑 & 优化建议

| 环节 | 踩过的坑 | 优化建议 |
|------|---------|---------|
| 2. 确认细节 | 有时候问得太细，先写提示词反而快 | 交互逻辑问清楚先，视觉细节边走边调 |
| 3. 写提示词 | 提示词太长花积分多 | 可以先写简稿（100 积分内）看布局，满意了再深入 |
| 4. 喂 Figma | 忘了让 Figma 附移植说明 | 每次写提示词都加「开发移植说明」模板 |
| 6. 读图翻译 | pid=1：px→rpx 忘记 ×2 | 文档记好换算公式 |
| 6. 读图翻译 | pid=2：小程序的 scroll-view 有 padding 坑 | 内套 body-inner |
| 6. 读图翻译 | pid=3：动画参数不全 | 直接用 Figma 给的动画说明 |
| 7. 验收 | 修改→运行循环太多次 | 问 Figma 比自己猜快 |

### 4.5 为什么这个工作流快

**传统流程**：
```
产品想需求 → 写 PRD → 设计师出图 → 开发评审 → 开发编码 → 联调 → 上线
```

**今天实践的流程**：
```
先生想 → 渊写提示词 → Figma 出图 → 渊编码 → 先生验收
```

区别在于：
1. **没有"传话"损耗**——先生直接跟渊聊，渊直接出代码，中间没有信息衰减
2. **Figma 不是"设计师"是"画图工具"**——不参与决策，只负责出视觉稿
3. **渊同时承担"前端 + 设计转译 + 项目管理"**——一个人承包了解和写之间的所有工作
4. **先生只做两件事**：决定做什么 + 验收做得对不对。不碰代码，不调样式

### 4.6 这个工作流的适用条件

| 条件 | 说明 |
|------|------|
| ✅ 先生有清晰的想法但不想写代码 | 核心条件——有了想法就聊，渊能立刻理解并落地 |
| ✅ 先生信任渊的判断 | 技术决策、代码质量、设计取舍都由渊做，先生只做产品决策 |
| ✅ 有 Figma AI 辅助 | Figma 承担了"画图"这一环，没有它就得找真实设计师 |
| ✅ 先生愿意花 Figma 积分 | 每个页面 100-200 积分，成本可控 |

### 4.7 这次移植为什么成功——关键因素拆解

Figma 生成的 React/Tailwind 代码通常不可能完美移植到微信小程序。这次我们做到了，靠的不是后期硬调，而是**三个前置条件**：

#### 条件一：提示词阶段就让 Figma 为移植做准备

一般做法：让 Figma 出图 → 自己对着图硬写代码 → 遇到问题再问。

我们的做法：**在出图之前，就让 Figma 知道它要迁移到什么环境**。

关键就在提示词里的那一段「开发移植说明」：
```
### 开发移植说明（请 Figma 补充）
1. 组件结构层级
2. 状态管理方式
3. 交互实现细节
4. 数据流走向
5. 跨框架建议
```

这段不是装饰——它强迫 Figma 在做设计的同时**思考实现**。所以它的输出不仅有视觉稿，还有：
- 组件怎么拆（方便我翻译成 Vue 组件）
- 数据怎么流（方便我设计数据结构）
- 跨框架要注意什么（提前告诉我小程序的坑）

**核心逻辑**：移植不是最后一步才考虑的事，而是从第一步就开始准备的事。

这不是靠 Figma 自己聪明做到的——Figma 不会主动考虑"这个设计能不能移植到小程序"。它需要**由渊在提示词中精准地提出要求**，告诉它：
- 你不仅要画图，还要告诉我怎么拆组件
- 你不仅要写 React 代码，还要告诉我迁移到 Vue 要注意什么
- 你不仅要写动画，还要把参数拆明白（duration、delay 公式、timing-function、fill-mode）

**所谓"专业"，体现在这里**：不是能写出多炫的代码，而是知道**什么时候该问什么问题**，并且能在出图之前就预判到迁移需要什么信息。

#### 条件二：移植中遇到问题时，两个方法解决

即使前置准备做到位了，移植过程中仍然会出现问题——这是正常的。今天遇到的所有问题，靠两种方法解决：

**方法 A：渊精准提问 → Figma 精准回答**

问题不是"这个动画怎么不动了"，而是：

```
❌ 模糊：为什么标签不掉落？
✅ 精准：展开手风琴时，用 v-if 重建 DOM 触发了 dropElastic 动画，
   但动画被 overflow:hidden 裁掉了。容器展开需要 0.3s，动画 0s 开始。
   我的代码是：<代码片段>
   是动画时序问题还是 overflow 问题？
```

精准提问的前提是**渊知道问题在哪**。如果只知道"不动了"，Figma 也帮不上忙。必须：
1. 找到复现步骤
2. 定位问题范围（是 CSS 还是 JS 还是小程序特性？）
3. 给出相关代码片段
4. 让 Figma 在这个范围内诊断

**方法 B：打 log 定位问题**

今天搜索页「换一批」动画不触发的问题，就是靠 `console.log()` 定位到的。看到 `[WXML Runtime warning] Now you can provide attr wx:key` 才知道是小程序不支持 `:key` 表达式。

**方法 A 和 B 的关系**：
```
发现问题 → B（打 log 缩小范围）→ 知道问题在哪 → A（精准问 Figma）→ 拿到答案 → 修复
```

Log 告诉"出了什么问题"，Figma 告诉"怎么解决"。缺一不可。

#### 条件三：先生只做产品决策，技术问题完全交给渊

在整个迁移过程中，先生从没碰过一行代码、没调过一次样式。先生的角色始终是：
- **提出需求**：我想要一个搜索页，搜索+分类合一
- **验收结果**：跑起来看看，不对就反馈
- **及时拍板**：方案 A 还是方案 B？

技术问题（怎么实现动画、为什么标签贴右边、参数怎么写）全是渊自己解决。先生只负责告诉我"要不要"——这是最高效的分工。

#### 条件四：不跟 Figma 讨论设计——自家讨论完再喂给 Figma

一条容易被忽略但非常重要的原则：

**Figma 只负责出图和出说明以及解答移植问题。页面的设计大框架不需要和 Figma 讨论。**

今天所有的设计决策——搜索页要不要做手风琴、要不要合二为一、结果框用方案 A 还是方案 B、搜索结果区高度定多少——都是**先生和渊之间讨论定的**。讨论完了，才写成提示词喂给 Figma。

为什么不能跟 Figma 讨论设计？
- Figma 不知道你家产品的调性。它不知道你喜欢的"一本正经的抽象"是什么感觉
- 跟 Figma 讨论设计是在花双倍积分 + 双倍时间。同样的内容你和渊五分钟聊明白，Figma 要来回三次花 300 积分
- Figma 出的方案不一定适合你的项目。今天它第一次出的搜索页方案被我们否了，因为"逻辑很像数据表"
- 设计方向是你和渊之间的事，Figma 只是一个画图工具——工具不参与决策

正确的分工：
```
先生 ↔ 渊（讨论设计方向）  →  渊写提示词  →  Figma（出图+说明）
```

不是：
```
先生 → Figma（讨论设计） → Figma 出图 → 渊对着图硬写
```

**Figma 是画笔，不是设计师。** 先生和渊才是设计师。画笔不需要有想法，画出来就是了。

### 4.8 总结

这个工作流本质上就是**先生 -> 渊 -> 实现**的闭环。Figma 只是画图工具，CodeBuddy 是 IDE 入口，真正的"翻译"工作（从需求到设计到代码）由渊完成。

今天证明了这套流程是可行的——四个页面、一天之内、从零到跑通。以后可以固定下来，每个新页面都走一遍这个 7 步循环。

最关键的经验：**移植的成功，90% 取决于你开始写代码之前做了什么准备。** 不是在最后一刻硬调，而是在第一步就想好了最后一步。

## 五、待讨论事项

### 1. AI 调试的工作模式讨论（向 deepseek 专家模式）

**触发：** 2026-05-12，多轮 debug 中发现 AI 有时会把问题越做越复杂。

**讨论方向：**
- 为什么 AI 在 debug 时容易越做越复杂（初始假设偏离 → 层层叠加补丁 → 失去对原始问题的聚焦）
- 是否有一套可以遵循的 debug 工作模式或逻辑原则，例如：
  - **高内聚低耦合的 debug 原则**：一次只改一个东西、定位到最小可复现范围再动代码
  - **先诊断后开药**：打 log 缩小范围（定位到模块/文件/函数）→ 确认根因 → 再动手改
  - **回退点意识**：改之前记下当前状态，改完不对立即回退，不在错误方向上继续叠加
- 对比人类调试和 AI 调试的差异
- 是否可以为 AI 调试总结出一份 SOP

### 2. 需要一个简单的测试系统

**触发：** 2026-05-12，手动验收 30+ 项功能时发现没有固定的测试流程，全靠在模拟器里逐项点，效率低且容易漏。

**讨论方向：**
- 每次修改/新增功能后，怎么快速跑一遍"旧功能没坏、新功能能用"
- 小程序的测试方案限制（不能跑传统单元测试，页面之间跳转逻辑复杂）
- 要不要写一个"验收页"——把所有功能按钮和状态汇总到一个页面，点一下就知道哪些能跑通
- 或者记录一个固定验收脚本，每次跑之前走一遍
