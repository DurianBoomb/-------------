## 通用测试方法

所有阶段通用的测试方法，先记住：

| 方法 | 说明 |
|------|------|
| **HBuilderX 云对象本地运行测试** | 右键云对象 → 本地运行 → 手动传参调试。这是最快的单步验证方式 |
| **DB schema 本地运行** | 右键 schema → 本地运行，测试 CRUD 权限和字段校验 |
| **数据库控制台** | `uniCloud 控制台 → 数据库` 直接查/改数据，验证写入是否正确 |
| **真机/模拟器预览** | 微信开发者工具，前端联调用。**注意热更新缓存 bug**（修改 .vue 后需要删除 unpackage 文件夹再重新运行） |
| **定时云函数测试** | HBuilderX 中右键定时云函数 → 本地运行（手动模拟触发，不用等定时器） |

### 每阶段做完后做两件事

1. **本阶段验收 checklist**：该阶段新增的功能跑通
2. **快回归(3-5分钟)**：调一下前序阶段的核心接口，确保没被改坏

## 阶段零A：数据库 + 配置 + 迁移

**本阶段产出**：4 个 schema + config + counter 初始化 + 用户扩展 + 迁移脚本

### 需要测什么

#### 0A.1 Schema 权限验证

逐个在 HBuilderX 中对 DB schema 右键"本地运行"，测试 CRUD：

| `counter.schema.json` | ① 插入初始文档 `{ _id: 'careerArchiveSeq', seq: 0 }` |

**测试方式**：HBuilderX → DB schema → 右键"本地运行" → 传 JSON 参数测试 CRUD

#### 0A.2 config.json 读取验证

- [ ] 在 HBuilderX 中临时写一个测试云函数，`require('uni-config-center')({ pluginId: 'pin-system' }).config()` 是否能正确读到参数列表

### 风险提示

**这是整个系统的地基。如果这个阶段出了问题，后面所有阶段的 bug 都可能是假象（看着像代码 bug，实际是数据没写对）。所以这个阶段的测试请做彻底。**

> **容易踩的坑：** uni-id-users.schema.ext.json 语法错误 → 用户登录都崩。先在本地测试环境确认没问题再上正式环境。

## 阶段一：入池核心

**这是真正的分水岭阶段，核心路径最多 bug。**

本阶段产出：`enterPool`、`queueToPool`（入池逻辑）、`handleAdReward` 骨架路由

### 需要测什么

#### 1.1 槽位检查

| 场景 | 预期 |
|------|------|
| 用户 0 条流转中 → 调 `enterPool` | 正常通过，占用 slot[0] |
| 用户 1 条流转中 → 调 `enterPool` | 正常通过，占用下一个空闲 slot |
| 用户 2 条流转中 → 调 `enterPool` | 正常通过，占用最后一个空闲 slot |
| 用户 3 条流转中（全满） → 调 `enterPool` | 返回"已达上限"错误，**不写入任何数据** |
| 广告播放期间槽位被释放 → 调 `enterPool` | 能正常通过（广告前检查和入池时再次检查之间的窗口期） |

> **特别注意**：3 条占满的边界情况。测试时手动在 DB 里把某个用户的 slots 填满 3 条，然后发起置顶请求。

#### 1.2 绿色通道（Lv.0 跳过池满线）

- [ ] 用户资历 Lv.0 → 无论池满线是否触达，都直接入池
- [ ] 入池文档的 `isGreenChannel = true`
- [ ] 用户资历 Lv.1+ → 不走绿色通道，走池满线判断

#### 1.3 池满线判断

- [ ] 池中问卷数 < 池满线 → 直接入池（`isGreenChannel = false`）
- [ ] 池中问卷数 ≥ 池满线 → 进入候场区（写入 `survey-queue`）
- [ ] 池满线读取的是 config.json 中的配置值（**测试方式**：临时改 config.json 池满线为 0，观察所有非 Lv.0 用户是否都进候场区）

#### 1.4 直接入池（绿色通道 + 池未满）

写入 `pin-pool` 的文档字段验证：

- [ ] `_id` 格式：`pin_时间戳_4位随机数`
- [ ] `userId` = `this.uid`
- [ ] `surveyId` = 传入值
- [ ] `surveyTitle` / `surveyCover` 正确冗余写入
- [ ] `weight` 不为空（阶段一先用固定随机值占位）
- [ ] `createdAt` ≈ 当前时间（误差 < 2秒）
- [ ] `expireAt` = `createdAt + 13分钟`
- [ ] `senioritySnapshot` = 入池前 `exposureCount` 值
- [ ] `haloActive = true`
- [ ] `isGreenChannel` 根据路径正确

#### 1.5 资历累加

- [ ] 入池成功后 `exposureCount + 1`（查 DB 确认）
- [ ] 入池失败（槽位满等）→ `exposureCount` 不变
- [ ] 进入候场区 → `exposureCount` **不变**（只有最终入池才 +1）

#### 1.6 槽位状态流转

- [ ] `enterPool` 成功 → 对应槽位状态从 `idle` → `active`，`pinId` 写入
- [ ] `enterPool` 进入候场区 → 对应槽位 `idle` → `queuing`，`queueId` 写入

#### 1.7 handleAdReward 路由

- [ ] `scene === "first_pin"` → 正确路由到 `enterPool`
- [ ] `scene === "queue_accel"` → 正确路由到 `executeAccel`
- [ ] 非法 scene 值 → 返回错误
- [ ] 返回结构符合设计文档 §8.4（code、message、action、greenChannel、queueData/pinData）

#### 1.8 queueToPool 独立入口

- [ ] 检查 `survey-queue` 记录是否存在（脑图路径 A/B 安全）
- [ ] 写入 `pin-pool` + 资历累加 + 删除候场记录 + 槽位更新，四步顺序执行
- [ ] 重复调用（两次相同 queueId）→ 第二次不执行任何写入

#### 1.9 并发安全（重要）

- [ ] 同一个用户几乎同时发起两路置顶 → 槽位独立可用，互不干扰
- [ ] 恰好第二个槽位只剩一个空闲位置 → 先到先得，后者返回"已满"

### 快回归

- [ ] 阶段零C 的两页面是否还能正常路由（不受本阶段新增逻辑影响）

## 阶段二：权重与抽取

本阶段产出：`calculateWeight`、`draw`

### 需要测什么

#### 2.1 calculateWeight 四层验证

**层级一：登场光环**
- [ ] `haloActive = true` → 返回光环固定高权重（如 10000）
- [ ] 光环中的问卷不参与后续任何层级计算

**层级二：归属分层**
- [ ] 自己的问卷权重区间 [300~500] vs 他人 [1~200]，两区间不重叠
- [ ] 多条自己的问卷 → 都在高区间
- [ ] 多条他人的问卷 → 都在低区间
- [ ] 自己的权重永远 > 所有他人（边界测试：自己的最低权重 300 > 他人的最高权重 200）

**层级三：内部排序（自己的问卷之间）**
- [ ] 自己入池时间越晚 → 权重越高
- [ ] 光环中的自己问卷走光环，不参与此层

**层级四：反向补偿（他人的问卷之间）**
- [ ] `senioritySnapshot` 越小 → 权重加成越多
- [ ] 各资历档位的系数比符合 config.json 中的配置（Lv.0 最高，Lv.3 最低）

#### 2.2 draw 抽取

| 场景 | 预期 |
|------|------|
| 池中 ≥ 5 份有效问卷 | 返回 5 份，不重复 |
| 池中 < 5 份有效问卷 | 返回全部 |
| 池中 0 份有效问卷 | 返回空数组 `[]` **（边界测试，易出 bug）** |
| 光环中的问卷 | 抽取结果中自然高概率出现 |
| 自己的问卷 | 抽取结果中自然高概率出现 |

- [ ] 返回列表按 weight 降序排列（`result[0]` 权重最高）
- [ ] 每条返回项包含：`surveyId`、`surveyTitle`、`surveyCover`、`isMine`、`haloActive`
- [ ] `surveyTitle`/`surveyCover` 读取的是 pin-pool 中的冗余字段（不需要 join 问卷表）

#### 2.3 新入池时旧问卷 weight 更新

- [ ] 用户自己已有第 1 条非光环问卷在池中，新增第 2 条 → 第 1 条的 weight 被重新计算降低（因第 2 条更新，旧问卷内部排序权重削减）
- [ ] 光环中的权重不被重算覆盖

#### 2.4 超时文档过滤

- [ ] `expireAt < now` 的过期文档不会被抽取出来
- [ ] 即使定时云函数还没清理，`draw` 也能自然过滤过期数据（这是兜底机制，**一定要测**）

### 快回归

- [ ] 阶段一的入池功能是否正常（先入池，再抽取，抽到了刚入池的问卷说明入池和抽取配合正常）
- [ ] `getSeniority` 仍然正常

## 阶段三：定时云函数（过期清理）

本阶段产出：`pin-expiry/index.js` 完整实现

### 需要测什么

#### 3.1 过期文档清理

- [ ] 手动将一条 `pin-pool` 文档的 `expireAt` 改为已过期时间 → 运行定时云函数 → 该文档被删除
- [ ] 多条过期文档批量删除（> 20 条是否按预期分批次处理）
- [ ] 非过期文档（`expireAt > now`）→ 不被处理

#### 3.2 战绩单生成触发

- [ ] 过期文档被清理时，`career-records` 中同步生成一条档案记录
- [ ] 档案数据完整性：surveyId、surveyTitle、userId、careerNumber 等字段是否正确

#### 3.3 槽位状态更新

- [ ] 过期文档对应的用户槽位状态从 `active` → `claimable`
- [ ] `hasUnread = true` 被设置
- [ ] `unreadCareerIds` 被更新

#### 3.4 幂等性（重要）

- [ ] 两次运行定时云函数，对同一文档不会生成两条战绩单
- [ ] 条件删除 + 条件更新的原子性保障

#### 3.5 异常处理

- [ ] 单条文档处理失败 → 不会阻塞其他文档的处理
- [ ] 失败文档保留在 `pin-pool` 中，等待下轮重试

#### 3.6 候场区兜底清理

- [ ] 超时候场记录（`enterAt + 30分钟 < now`）被正确处理
- [ ] 槽位仍为 `queuing` → 调用 `queueToPool`
- [ ] 槽位已不是 `queuing` → 直接删除候场记录

### 快回归

- [ ] 前阶段入池一条问卷 → 手动修改 expireAt 为过去 → 定时云函数跑一次 → 入池的问卷从池中消失 → `draw` 不再返回该问卷（**这个回归非常重要，关乎三个阶段的联动**）

### 4.1 calcPhaseImpl 阶段推进算法验证（通过 mock 页操作验证）

#### 4.1.2 加速跳跃算法验证

加速跳跃 index = `acceleratedCount × accelJumpMap[seniorityLevel]`，与自然推进 index 取最大值。

**验证场景：** enterAt = 2分钟前（自然推进为 queuing，phaseIndex=0）

| exposureCount | 资历档位 | accelJumpMap | 操作 | 预期 phaseIndex | 预期 currentPhase |
|-------------|---------|-------------|------|----------------|------------------|
| 1 (Lv.1) | Lv.1 | 3 | 0 加速 | 0 | queuing |
| 1 | Lv.1 | 3 | 1 次加速 → accelIdx=1×3=3 → min(3,3)=3 | 3 | ready（加速到位） |
| 6 (Lv.2) | Lv.2 | 2 | 0 加速 | 0 | queuing |
| 6 | Lv.2 | 2 | 1 次加速 → accelIdx=1×2=2 | 2 | pushing |
| 6 | Lv.2 | 2 | 2 次加速 → accelIdx=2×2=4 → min(4,3)=3 | 3 | **第三次加速自动入池** |
| 21 (Lv.3) | Lv.3 | 1 | 1 次加速 → accelIdx=1×1=1 | 1 | inspecting |
| 21 | Lv.3 | 1 | 2 次加速 → accelIdx=2×1=2 | 2 | pushing |
| 21 | Lv.3 | 1 | 3 次加速 → accelIdx=3×1=3 → min(3,3)=3 | 3 | **第三次加速自动入池** |
| 0 (Lv.0) | Lv.0 | 4 | 1 次加速 → accelIdx=4 → min(4,3)=3 | 3 | Lv.0 一次加速到位 → **自动入池** |

> **注意**：accelIdx 被 `Math.min(accelIdx, phaseMap.length-1)` 限制在 [0,3] 范围内，所以第三档位 Lv.0 一次加速直接满。

## 高风险区域标注

以下几个区域是 **最容易出 Bug、最隐秘、最难排查** 的，请格外关注：

### 🔴 红色（致命风险）

| 区域 | 为什么高风险 |
|------|------------|
| **槽位双路径竞争** | 首页弹窗已阅 vs 历史页签收，两个入口并发操作同一个槽位。如果没有原子条件更新（`status: claimable → idle`），可能重复释放或数据错乱 |
| **资历累加条件更新** | `queueToPool` 中资历累加用的是条件更新（`where exposureCount === senioritySnapshot`），如果过程中资历被另一路径推高，条件不成立则不累加。这个逻辑一旦写错，资历数据全歪 |
| **定时云函数幂等性** | 条件删除 + 条件更新必须同时生效，否则同一文档可能生成两条战绩单或多条多余写入 |

### 🟡 黄色（高风险）

| 区域 | 为什么高风险 |
|------|------------|
| **三次加速自动入池的时序** | executeAccel 内部调用 queueToPool，而 queueToPool 又会操作 slot + 删除候场记录 + 资历累加。如果在加速完成的同时自然 ready 也到了，两个入口同时处理同一候场记录怎么办 |
| **候场区兜底清理 + 前端手动操作** | pin-expiry 检测到超时候场记录时调用 queueToPool，如果与此同时前端也正在操作同一记录，可能发生双写入 |
| **后端计算主导的日志推进** | getQueueStatus 内部的阶段推进算法用了复杂的时间计算 + 加速跳跃计算，边界条件容易写错（如 elapsed = 5.0 分钟如何取整） |
| **核弹级：hot reload 不刷新** | 微信小程序的热更新缓存 bug（修改 .vue 文件后模拟器不刷新），排查问题时永远先考虑"是不是缓存"。改前端必删 unpackage |
