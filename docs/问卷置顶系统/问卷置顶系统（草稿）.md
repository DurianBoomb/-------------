## 1. 核心概念与术语表

### 2.2 模块关系
系统包含五个核心模块，数据流关系如下：
text
```plaintext
[模块一：曝光资历系统]
  提供：用户资历查询
    ↓ 被调用
[模块二：置顶池] ←→ [模块三：候场区]
  提供：入池、权重计算、  提供：排队状态管理、
        抽取、过期清理          广告加速处理
    ↓ 输出抽取结果
[模块四：置顶栏（首页展示）]
  提供：卡片展示、视角诡计落地、
        轮播与换一批交互
    ↓ 到期移出时触发
[模块五：战绩单]
  提供：即时战报生成、历史战绩页、
        分享长图
```
模块间依赖简述：
- 曝光资历系统：独立模块，为置顶池入池判断、权重计算、候场区加速效率、战绩单数据浮动提供统一的资历查询服务。
- 置顶池：核心存储与算法模块。接收来自候场区或直接入池的问卷，维护权重排序，响应置顶栏的抽取请求，并在问卷到期时通知战绩单模块。
- 候场区：独立于置顶池技术容量的人工排队层。接收不满足直接入池条件的用户，管理进度条状态与广告加速，达标后调用置顶池入池接口。
- 置顶栏：纯展示与交互模块。依赖置顶池抽取接口获取数据，依赖视角诡计规则（归属标记、光环标记）进行差异化渲染。不直接写入任何数据。
- 战绩单：异步触发的后置模块。监听置顶池的过期移出事件，生成即时战报并持久化历史战绩数据。依赖曝光资历信息调整数据浮动系数。
### 2.3 技术栈建议
系统目标运行环境为微信小程序，以下为建议技术选型：
- 小程序前端：使用小程序原生框架或 Taro/uniapp 等跨端框架（视团队技术栈而定）。置顶栏动画可使用 CSS 过渡或小程序动画 API 实现。
- 后端服务：推荐 Node.js（如 Egg.js/Nest.js）或 Go/Python，提供 RESTful API。需具备 Redis 和数据库访问能力。
- 缓存与实时数据：Redis，用于置顶池 Sorted Set 存储、候场区临时状态、高并发权重查询缓存。
- 持久化数据库：MySQL/PostgreSQL 或 MongoDB，用于用户资历、历史战绩、问卷基础信息等需要持久化和复杂查询的数据。
- 广告回调：对接微信小程序激励视频广告组件，服务端需提供一个回调接口用于广告观看验证和业务处理。
- 长图生成：可选用服务端渲染方案（如 Puppeteer 渲染 HTML 生成图片）或前端 Canvas 绘制后上传，视性能需求而定。
> 注：以上选型为建议，非强制约束。具体技术栈由开发团队根据现有基础设施和人员技能最终确定。本系统核心逻辑无冷门依赖，常规技术栈均可承载。
## 3. 模块一：曝光资历系统
### 3.1 概述
曝光资历是贯穿整个置顶系统的核心用户属性，用于量化用户使用置顶功能的历史深度。它是反向补偿机制的决策依据——资历越浅，系统给予的隐性优待越多。
该属性对用户完全不可见，仅作为后端权重计算和候场区加速效率的输入参数。
---
### 3.2 数据模型
定义：曝光资历是一个整数，记录用户历史上累计成功完成置顶的次数。
累加规则：
- 累加时机：用户的问卷成功进入置顶池的那一刻（即广告看完、通过绿色通道或候场区后，系统将问卷写入置顶池的操作完成时）。
- 累加逻辑：用户的曝光资历字段值+1，此操作与问卷入池在同一事务或流程内完成，确保不会出现入池成功但资历未累加的情况。
- 注意：此处累加的是“入池成功”的次数，而非“看完广告”的次数。用户在候场区看广告加速但尚未入池时，资历不增加。只有最终进入置顶池的那一刻，资历才+1。
与问卷的关系：
- 每次入池的问卷会记录该时刻用户的曝光资历快照值，作为后续权重计算的依据。
- 同一用户在短时间内依次置顶多份问卷时，每份问卷携带的资历快照不同（后入池的资历更深），因此权重也不同。
---
### 3.3 资历分档
为了便于算法设计和运营调整，曝光资历被映射到四个档位。档位的具体数值边界将在后期参数设计阶段确定，此处仅定义档位概念：
|档位|含义|说明|
|-|-|-|
|Lv.0|新人/稀客|几乎未使用过置顶功能，享受最强反向补偿|
|Lv.1|偶发者|偶尔使用，享受中等偏上的反向补偿|
|Lv.2|常客|定期使用，作为权重计算的基准锚点|
|Lv.3|老面孔|频繁使用，反向补偿力度最弱|

### 3.4 查询接口需求
系统需提供查询用户曝光资历的能力，供各模块调用。
调用方：
- 置顶池入池流程（判断绿色通道资格）
- 权重算法（获取资历档位以计算权重系数）
- 候场区加速计算（获取资历档位以决定跳跃距离）
- 战绩单生成（获取资历档位以调整浮动系数）
入参：用户唯一标识
出参：
- 当前曝光资历数值】
- 所属档位
- （可选）距离下一档位还需多少次
该接口为高频调用接口，需考虑缓存策略。缓存刷新时机为用户资历累加时。具体缓存方案在技术实现阶段确定。

## 4. 模块二：置顶池
### 4.1 概述
置顶池是整个系统的核心存储，存放所有当前有效的置顶问卷。它是一个无硬性容量上限的集合，问卷入池后获得15分钟生命周期，到期自动移出。置顶栏展示和战绩单生成均依赖此模块提供数据。
置顶池在技术上可同时容纳海量问卷而不影响抽取性能。池满线和候场区是人为架设的体验层，与置顶池本身的技术能力无关。
---
### 4.2 数据模型
存储选型
置顶池采用 Redis Sorted Set（有序集合）作为主存储结构。选择理由：支持按权重排序、支持高效随机采样、支持按时间范围清理。
成员与分值
- Member：问卷唯一标识
- Score：该问卷当前的综合权重值，由权重算法实时计算并写入。分值越高的问卷在加权随机抽取时被选中的概率越大。
成员附属信息
除 Sorted Set 中的 Score 外，每条问卷还需关联以下字段，建议使用 Redis Hash 存储，Key 为问卷标识：
|字段|说明|
|-|-|
|所属用户标识|用于归属分层判断|
|入池时间戳|精确到秒，用于15分钟生命周期判定和内部排序|
|入池时的曝光资历快照|入池瞬间用户的资历值，固化用于后续权重计算|
|是否处于登场光环|布尔标记，光环期间权重计算走特殊逻辑|
|光环已服务刷新次数|计数器，用于光环退场判定（累计两次刷新后失效）|
|是否为绿色通道入池|标记，用于数据分析和战绩单反向补偿参考|

### 4.3 生命周期管理
入池
问卷完成入池条件判断（绿色通道 或 候场区冲线）后，系统执行以下操作：
1. 计算该问卷的初始综合权重（含登场光环加成），写入 Sorted Set。
2. 记录入池时间戳、曝光资历快照、光环标记等附属信息至 Hash。
3. 累加用户的曝光资历值+1。
在池期间
- 权重刷新：每次置顶栏发起抽取前，系统重新计算池中所有（或采样范围内）问卷的权重。登场光环在服务两次刷新后自动退场，之后权重回归正常。
- 附属信息更新：光环退场时更新标记位和计数器；用户有新问卷入池时可能影响其已有问卷的相对内部排序权重。
到期移出
- 生命周期固定为15分钟，从入池时间戳起算。
- 移出时机：在每次抽取前或定期清理任务中，检查问卷入池时间戳，超过15分钟的从 Sorted Set 和 Hash 中删除。
- 移出触发：移出操作同时触发“战绩单生成”流程，将必要数据传递给战绩单模块。
---
### 4.4 权重算法
权重算法的核心目标是：为置顶池中每条问卷计算一个综合权重值，决定它在置顶栏抽取时的相对优先级。权重体系共四层，从高到低依次叠加。
层级一：登场光环
- 判定条件：问卷的“是否处于登场光环”标记为真，且“光环已服务刷新次数”小于2。
- 规则：光环期间，问卷的综合权重被设置为一个极高的固定值（远大于正常权重范围），确保在加权随机抽取时几乎必定入选，且在栏内排序时强制进入前三位。
- 退场：每次置顶栏抽取（换一批）时，若该问卷因光环被选中且展示，光环计数器+1。计数器达到2后，光环标记置为假，权重恢复由后续层级计算。
- 特殊说明：光环计数器统计的是“被选中并展示”的次数，而非用户手动刷新的总次数。若用户刷新时该问卷未被抽中，不计入次数。这确保了光环的实际效果——用户两次刷新内必定能看到它在前三。
层级二：归属分层
- 判定条件：抽取请求携带当前用户标识，与池中问卷的所属用户标识进行比对。
- 规则：自己拥有的问卷，在归属分层中获得一个基础权重加成。该加成量级需确保自己的问卷在加权排序时，权重始终高于任何非自己的问卷（即使后者因反向补偿获得较高系数）。
- 实现思路：为“自己的问卷”和“他人的问卷”设置两个权重区间，两区间不重叠。自己的问卷权重落于高区间，他人的落于低区间。
层级三：内部排序（自己的问卷之间）
- 判定条件：当前用户在池中有多条问卷时生效。
- 规则：按问卷的入池时间先后排序，越早进入池子的问卷权重加成越多。原因：早进入的问卷诞生时用户的曝光资历更浅，理应获得更多曝光。
- 例外：登场光环中的问卷不参与常规内部排序，光环退场后才归入此层。
层级四：全局反向补偿（他人的问卷之间）
- 判定条件：所有非当前用户的问卷之间排序时生效。
- 规则：按问卷入池时记录的曝光资历快照值反向加权。资历越浅（数值越小），权重加成越多。同一用户的多份问卷因携带不同资历快照，权重各自独立计算。
- 锚点：以资历Lv.2（常客）的权重系数为基准1.0，Lv.0获得最高倍率，Lv.3获得最低倍率。具体倍率在全局参数中定义。
综合权重计算流程
每次需要计算一条问卷的权重时，按以下顺序执行：
1. 检查登场光环状态 → 若在光环中，返回光环固定高权重，结束。
2. 判断归属 → 确定基础权重区间（自己的高区间 / 他人的低区间）。
3. 若为自己的问卷 → 在基础区间内，根据入池先后顺序进行内部排序加成。
4. 若为他人的问卷 → 在基础区间内，根据曝光资历快照进行反向补偿加成。
5. 返回最终权重值，写入 Sorted Set 的 Score。

### 4.5 入池逻辑
完整判断流程
用户看完广告后，系统按以下顺序依次判断：
1. 绿色通道检查：查询用户当前的曝光资历档位。若为 Lv.0，跳过候场区，直接进入置顶池。入池时携带登场光环。
2. 池满线检查：获取当前置顶池的问卷数量，与池满线阈值比较。
    - 若池数量 < 池满线 → 直接进入置顶池，携带登场光环。
    - 若池数量 ≥ 池满线 → 进入候场区，启动“置顶之路”排队流程。
3. 候场区完成：用户在候场区通过自然等待或广告加速走完进度条后，从候场区进入置顶池，携带登场光环。
池满线动态计算【需要想】
- 池满线不是固定值，而是根据当前小程序活跃程度动态浮动。
- 计算逻辑：取当前在线用户数（或近5分钟活跃用户数）的一个比例，并设置上下限。比例和上下限值在全局参数中定义。
- 设计意图：活跃用户多时，池子自动扩容，让更多人直接进入；活跃用户少时，池子适当缩小，维持“排队”的稀缺感和仪式感。
入池接口
该接口由广告回调触发，执行完整的入池判断流程，并返回结果状态：
- 入参：用户标识、问卷标识
- 出参：
    - 结果状态码（直接入池成功 / 已进入候场区）
    - 若入池成功：返回登场光环生效的确认信息
    - 若进入候场区：返回候场区初始状态（当前路程、自然前进速度、首次加速可达距离等）
---
### 4.6 抽取逻辑
置顶栏每次需要展示或刷新时，调用本模块的抽取接口，从置顶池中获取指定数量的问卷。
抽取方式
采用加权随机采样。池中每条问卷被选中的概率与其综合权重（Sorted Set 的 Score）成正比。权重越高，被抽中的概率越大。
抽取数量
每次抽取5份问卷，对应置顶栏5张卡片。若池中问卷数不足5份，则返回全部。
特殊处理
- 去重：同一次抽取中不可重复返回同一问卷。若加权随机抽到重复项，跳过并继续采样。
- 兜底：极端情况下池中无任何问卷，返回空列表，置顶栏展示占位引导内容（如“还没有问卷在置顶，快来看广告抢占C位”）【空的情况下要注意测试】。
抽取接口
- 入参：当前用户标识、抽取数量（固定5）
- 出参：问卷列表（含问卷标识、标题等展示所需字段），列表中每条问卷附带其最终栏内排序位置。排序位置同样由权重决定——权重越高的问卷排在越靠前的位置。
调用频率
该接口为高频接口，每次用户进入首页、下拉刷新、或点击“换一批”时都会调用。需做缓存或限流考虑，具体策略在技术实现阶段确定。
---
### 4.7 过期清理
清理策略
采用惰性删除 + 定时任务双保险。
- 惰性删除：每次抽取前，遍历候选问卷的入池时间戳，将超过15分钟的问卷即时移出，不参与本次抽取。
- 定时任务：以固定间隔（如每30秒）扫描置顶池，批量清理过期问卷。此任务同时负责触发战绩单生成——移出前将问卷数据推送给战绩单模块。
清理流程
1. 获取问卷的入池时间戳。
2. 若当前时间 - 入池时间戳 ≥ 15分钟，标记为过期。
3. 从 Sorted Set 和 Hash 中删除该问卷。
4. 将该问卷的关键数据（用户标识、问卷标识、入池资历快照、在池期间的曝光统计等）打包，发送给战绩单模块进行处理。
5. 战绩单生成异步执行，不阻塞清理主流程。
异常处理
若因系统故障导致过期问卷未能及时清理（如超过15分钟仍在池中），惰性删除环节会兜底拦截，确保不会展示过期内容。战绩单生成逻辑需做幂等处理，避免同一份问卷重复生成多份战报。

## 5. 模块三：候场区（系统监控终端）
### 5.1 概述
候场区是用户无法立即进入置顶池时的中间等待层。它与置顶池的技术承载能力无关——置顶池本身可容纳海量问卷——而是为了制造仪式感、差异化优待和插队快感而主动架设的体验设计。
在叙事层，候场区被包装为一个虚构的“系统监控终端”界面。用户提交置顶请求后，不再是看到一条干巴巴的进度条，而是进入一个黑底绿字的等宽字体终端屏幕，旁观系统对自己的问卷进行“含梗量检测”“舆情预测”“推送分发”等一本正经的荒诞处理。每一行滚动的日志都是进度本身——日志滚完，意味着处理完毕，问卷进入置顶池。
对内，候场区是一个不维护全局真实队列顺序的“黑盒”表演系统。用户看到的排队人数、跳过人数、处理阶段均由算法基于其个人状态参数实时生成，不与任何真实队列精确挂钩。
与战绩单的叙事关系：候场区是“系统正在处理你”，战绩单是“系统已完成认证”。两者同属一个虚构世界观——监控中心负责处理问卷，名气管理局负责签发档案。候场区日志里的“含梗量检测”在战绩单里变成“含梗量宗师”荣誉称号，同一套语言体系，首尾呼应。
### 5.2 数据模型
存储选型
规格书相关依据：后端为 uniCloud 支付宝云，数据库为 MongoDB 5.0 兼容的文档型数据库，云函数为 Node.js 环境。现有业务已大量使用云数据库存储状态（答题记录、收藏、点赞等）。
建议方案：使用云数据库新建一个集合（如 survey-queue）存储候场区状态。理由：
- 与现有技术栈完全统一，无需引入 Redis
- 候场区并非高频写入场景——用户每分钟自然前进更新一次、看广告时跳跃一次，MongoDB 完全能承载
- 文档型结构天然适合存储用户维度的候场状态（单文档包含所有字段）
- 可利用云数据库的 TTL 索引实现兜底清理（设置 expireAt 字段自动过期）
若后续用户量暴增需要更高性能，可再引入 Redis 缓存层，但 MVP 阶段直接用云数据库足够。
字段定义

- 完成：当前处理阶段到达就绪阶段，或已加速次数达到3时触发第三次加速必定完成，用户进入置顶池，候场记录删除。
- 兜底清理：候场记录设置最大有效期（如60分钟），超时自动清理，避免僵尸数据堆积。

### 5.3 终端日志机制（原进度条算法）
候场区呈现为一个虚构的“系统监控终端”界面：黑底，等宽字体，日志逐行滚动。用户在此旁观系统对自己的问卷进行“含梗量检测”“舆情预测”等一本正经的荒诞处理。日志的推进节奏本身就是等待进度，不需要额外进度条。
日志推进逻辑
日志内容分为若干阶段（排队→质检→舆情→推送→就绪），按时间线依次滚动。后端根据用户当前状态（自然等待时长、已加速次数）决定当前应展示到哪个阶段。
- 自然推进：即使用户不操作，日志也会随时间推进自动滚动新内容。推进速率在全局参数中定义，确保自然走完全程约30-50分钟。
- 阶段间停顿：日志在每个阶段之间有自然停顿，模拟真实系统的处理间隔。停顿本身构成等待体验的一部分。
- 实现方式：前端根据“当前时间 - 进入时间”和已加速次数，结合阶段推进曲线计算当前日志位置，无需后端每秒推送。后端在查询候场状态时返回当前应展示的日志段。
广告加速
- 触发：用户在终端界面点击“加速”按钮，观看激励视频广告。
- 视觉表现：广告结束后，日志中插入一条VIP通道记录（如 [VIP] 检测到加速请求，正在开启绿色通道...），随后日志快速推进多个阶段。
- 推进跨度：根据用户曝光资历档位决定。资历越低，一次加速推进的阶段越多，新人可能直接跳到接近完成。
- 插队转换为日志语言：原本的“你超越了XX人”被替换为日志中的自然表述，如 [VIP] 绿色通道已开启，你的问卷跳过 342 人，提前进入处理队列。此数字由系统生成，不反映真实队列。
- 跳跃后已加速次数+1。
第三次加速必定完成
- 判定：已加速次数当前为2，且用户再次触发广告加速。
- 规则：无论当前日志推进到哪个阶段，直接跳到最终阶段，日志显示处理完毕、正在切换至置顶池。
- 视觉呈现：日志滚动加速后，终端界面显示 [系统] → 你的问卷已进入置顶池，开始曝光！，随后自动跳转或提示用户返回首页。
- 例外：如果用户在第三次加速前已通过自然等待走完全程，则自然完成，不强制消耗广告。
新人绿色通道（日志表述）
- 曝光资历为 Lv.0 的用户进入候场时，日志直接显示绿色通道记录，跳过大量排队阶段：
    text
    ```plaintext
[系统] 检测到新用户，根据《互联网新人保护法》第3条，自动获得优先曝光权
[新人] 绿色通道已开启，你的问卷跳过 512 人
```
池满提示（日志表述）
- 用户进入候场时的首行日志：
    text
    ```plaintext
[系统] 当前置顶池已满，你已进入候场区
[系统] 预计等待时间：约一首歌的时间
[系统] 你可以等待自然入场，或者看广告加速（最多3次）
```

### 5.4 候场区接口
接口一：查询候场状态
- 调用时机：用户进入候场终端界面或返回查看时调用。
- 入参：用户标识
- 出参：
    - 是否在候场中
    - 当前应展示的日志文本（完整日志内容或当前阶段标识，由前端渲染滚动效果）
    - 已加速次数（0/1/2）
    - 当前所处的处理阶段标识（用于判断是否可触发加速、是否接近完成）
    - 若看一次广告加速，预计可达的阶段预览（如“将跳过质检环节，直接进入推送阶段”）
    - 自然推进的当前速率（供前端控制日志滚动速度）
接口二：执行加速
- 调用时机：用户在候场终端界面看完激励视频广告后，由广告回调触发。
- 入参：用户标识
- 出参：
    - 加速结果状态码（正常推进 / 已完成入池）
    - 本次加速后新增的日志内容（供前端追加滚动）
    - 加速后的当前处理阶段
    - 若已完成入池：返回登场光环确认信息，以及入池后首次抽取的置顶栏数据（便于前端立即跳转展示）
不需要的功能
- 放弃排队：不做。用户不关注即视为挂机，候场记录在超时后自动清理。
- 暂停排队：不做。用户离开终端界面后日志仍在后台推进，下次打开时已自动更新到最新阶段。

## 6. 模块四：置顶栏（首页展示）
### 6.1 概述
置顶栏是首页顶部的核心展示区，也是整个置顶系统对用户唯一可见的“舞台”。它由5张问卷卡片组成，数据来源于置顶池的加权随机抽取。置顶栏承载了视角诡计的落地——每个用户看到的置顶栏内容因归属分层而不同，自己的问卷总是以极高概率出现在显眼位置。
置顶栏的交互包括自动轮播、手动“换一批”刷新，以及登场光环期间的强保证展示。
---
### 6.2 展示规则
卡片数量
固定展示5张问卷卡片。若置顶池中问卷总数不足5张，则展示全部可用问卷，剩余位置显示占位引导卡片（如“虚位以待，看广告抢占C位”）。
自动轮播
- 置顶栏支持自动轮播，每隔一定时间自动切换展示的卡片组合。
- 轮播频率在全局参数中定义，建议预设为每5-8秒轮换一批。
- 轮播时调用抽取接口重新获取5张卡片，而非仅在已有结果中调换排序。这确保了每次轮播都是一次全新的加权随机，权重机制持续生效。
- 自动轮播可被用户手动“换一批”打断，打断后重新计时。
“换一批”交互【动画效果再说】
- 用户可随时点击“换一批”按钮，手动触发置顶栏刷新。

### 6.3 视角诡计实现
视角诡计是整个置顶系统的核心体验设计。其实现原理是：抽取接口接收当前用户标识作为入参，服务端在权重计算时执行归属分层，确保用户自己的问卷获得压倒性权重。前端仅需做展示层面的辅助处理。
前端区分“自己的问卷”与“他人问卷”
- 抽取接口返回的问卷列表中，每条问卷附带一个“是否为当前用户所有”的布尔标记字段。
- 前端根据此标记，对自己的问卷卡片应用差异化视觉样式（如边框微光、右上角“我的”角标、卡片底色微暖等）。视觉差异需克制，以“暗示这是我的”而非“强行高亮”为度。【动画效果再说】
- 此标记仅用于前端展示区分，不参与排序逻辑——排序已由服务端权重决定。
刷新时自己问卷的展示逻辑
- 服务端保证：因归属分层的权重区间设计，自己的问卷在任何一次抽取中，权重均碾压他人问卷。在5张卡片的加权随机采样中，自己的问卷被选中的概率极高（接近但不等同于必然）。
- 前端不强制固定位置：自己的问卷不锁定在第一位。每次抽取结果中，它可能出现在第1-3位的任何位置，偶尔甚至排到第4-5位。这种“几乎总在前面但不绝对钉死”的表现，比强制第一位更显真实。
- 前端辅助逻辑：在极少数情况下，若抽取结果中自己的问卷未被选中（归属分层的权重优势使其概率极低但非零），前端不做补偿插入。让这种“偶尔不在”自然发生，反而增强了系统的可信度。用户会想“刚才还在的，刷新一下又回来了”，这种动态感比永远死钉在第一位更有生命力。
登场光环期间的特殊处理【需讨论】
登场光环要求“两次刷新内必在前三”。经与服务端架构评估，采用方案一（服务端保证排序 + 前端纯展示特效），理由：与现有云对象服务端排序逻辑一脉相承，前端保持“拿到什么渲染什么”的纯粹性，且规避了前端二次排序可能引发的动画冲突（项目已知存在 DOM 重排导致的动效异常）。
方案一：服务端保证排序 + 前端纯展示特效（采纳方案）
服务端职责：
1. 抽取接口正常执行加权随机采样，得到结果列表。
2. 检查当前用户是否有生效中的登场光环问卷。
3. 若光环问卷已在结果中但未进入前三位：将其提至前三位（优先第1位）。
4. 若光环问卷未被本轮抽中：替换掉结果中排位最低的一张他人问卷，插入前三位。
5. 扣减该问卷的光环剩余刷新次数（初始为2，每次刷新-1，归零后光环退场）。
6. 返回结果中附带光环标记字段，供前端做视觉特效。
前端职责：
- 完全按服务端返回的顺序渲染，不做任何二次排序。
- 检测光环标记，对对应卡片施加纯视觉特效（发光边框、登场角标等）。
- 特效作为纯视觉组件，异常时不影响核心展示，顶多特效不显示而排序仍正确。
实现评估：
- 服务端新增逻辑约15-20行，在云函数内完成，数组操作规模很小（通常不超过50条），无性能隐患。
- 与现有 survey 云对象的服务端排序逻辑一致，不引入新架构模式。
- 前端可直接复用现有换一批动效，不会触发因前端二次排序导致的 DOM 重排或动画异常。

### 6.4 视觉反馈【动画效果再说】
自己的问卷卡片样式
- 与其他卡片有细微视觉区分：如微弱的金色描边、卡片左上角或右上角一个轻量角标。
- 登场光环期间，该卡片可增加更明显的登场特效（如光晕扫过、短暂放大动画），光环退场后特效消失，回归常规“我的问卷”样式。
- 视觉设计原则：让用户一眼能认出“这是我的”，但不至于在5张卡片中显得突兀或喧宾夺主。
换一批动效
- 5张卡片同步执行飞入飞出动画：旧卡片向上滑出并淡出，新卡片从下方滑入并淡入。
- 用户的问卷卡片（若在新结果中）在切换动画中保持位置不动或仅轻微缩放，强化“我的稳固”心理暗示。
- 动画时长控制在0.3-0.5秒，流畅不拖沓。
空状态与加载状态
- 置顶池无任何问卷时：展示占位引导卡片，文案引导用户“看广告，让你的问卷抢占C位”，点击跳转广告入口。
- 抽取接口响应延迟时：展示骨架屏或加载动画，避免白屏。抽取结果返回后平滑过渡。
## 根据新的叙事设计，战绩单不再是一份“战报”，而是由虚构机构**“15分钟名气管理局”**签发的一份官方档案。以下是对原技术文档的全面改写：

### 7.1 概述
战绩单是置顶体验的情绪闭环，由虚构机构“15分钟名气管理局”颁发。用户在15分钟置顶结束时，不是无声消失，而是收到一份正经到离谱的官方档案——用公文格式认证了用户在过去15分钟内“被看见”的事实。
战绩单分为即时档案（单次结束触发）和历史档案页（持久化回顾）。数据生成包含反向补偿和数据暴击机制，让新人感受更好，同时偶尔制造惊喜。
与候场区的关系：候场区是同一套系统的“监控终端”，战绩单是该终端处理完毕后吐出的“最终档案”。同一套语言体系，同一个虚构世界观，首尾呼应。

### 7.2 即时档案
#### 7.2.1 触发时机
触发源来自置顶池的过期清理流程。
- 当一条问卷在置顶池中满15分钟，被惰性删除或定时清理任务移出时。
- 移出操作完成后，系统将该问卷的关键数据打包，发送给战绩单模块。
- 战绩单模块生成完整的档案数据并存储。
前端获取通知的方式：
- 用户下次打开首页或刷新时，查询是否有未读的新档案。
- 若有，在首页置顶栏区域或固定位置弹出提示卡片。文案示例：“15分钟名气管理局：你的临时名人档案已生成”。
- 点击进入全屏档案页面。
关键设计：不通过服务端主动推送打扰用户。用户自然回流时看到，符合“收到一份意外的官方文件”的心理。
#### 7.2.2 数据生成算法
所有数据均基于置顶期间的实际表现，经放大和修饰后呈现。生成的每个数值都需经过一致性校验，避免逻辑错误。档案中的数值被替换为更文绉绉的表述（见文案映射表）。

驻足注视（原曝光量）
- 基础值：取问卷在池期间，每个抽取周期被呈现在他人屏幕上的理论次数。可由活跃用户数 × 该问卷的全局权重占比估算。
- 浮动系数：在基础值上乘以一个浮动系数，使数字更好看。系数值在全局参数中定义，预设范围如1.5～3.0。
- 反向补偿融入：曝光资历越浅的用户，浮动系数取上限的概率越大。
- 零头修饰：将最终数值加上或减去一个微小随机数，使结果有零有整（如2847而非2800），增强真实感。
好奇打开（原点击量）
- 换算逻辑：好奇打开 = 驻足注视 × 点开率。
- 点开率：在预设范围内随机浮动（如5%～15%）。反向补偿可暗中提高新人的点开率浮动下限。
- 修饰：同样进行零头修饰。
决定存档（原收藏量）
- 换算逻辑：决定存档 = 好奇打开 × 存档转化率。
- 存档转化率：预设范围（如5%～20%），反向补偿影响浮动。
- 保底：设定一个最低值（如不低于1），避免出现“无人存档”的尴尬。
数据暴击（破格授予）
- 触发概率：每次生成档案时，以一定概率（建议10%～20%）触发。
- 暴击效果：选中一个数据维度（优先驻足注视，其次好奇打开），将该数值乘以暴击倍数（如1.5～2倍）。
- 联动：暴击触发后，荣誉称号和档案附注需对应升级。荣誉称号变为更夸张的版本，附注包含“本局特此破格授予”等措辞。
- 注意事项：暴击后仍需通过一致性校验。
数据一致性校验
生成全部数值后，强制检查：
- 好奇打开 ≤ 驻足注视。
- 决定存档 ≤ 好奇打开。
- 所有数值为正整数。
- 无逻辑矛盾。
    若校验失败，回退调整参数重新生成，或直接向下修正异常数值。
#### 7.2.3 荣誉称号与档案附注
荣誉称号（原头衔）匹配规则
- 系统预置一个荣誉称号池，每个称号与数据特征挂钩。
- 匹配逻辑：根据本次档案的驻足注视、好奇打开、决定存档的相对高低组合，映射到一个称号。
- 规则表结构示意（具体称号和阈值在全局参数/配置表中定义）：
    - 驻足注视极高而点开率低 → “人群中的灯塔”（被很多人看到但少有人点开）
    - 点开率高 → “万众瞩目者”
    - 存档率高 → “档案馆宠儿”
    - 驻足注视较低但点开率极高 → “冷门黑马”
    - 数据暴击触发 → 专属暴击称号（如“破格流量获得者”）
    - 新人首秀 → 可包含“首次认证”类特殊称号
- 反向补偿融入：新人等弱势用户，匹配到稀有或高价值称号的概率暗中提高。
档案附注（原评价语料库）设计
- 档案附注由系统从语料库中抽取并组合生成，以“本局鉴定”或“系统点评”的口吻呈现。
- 语料库设计原则：
    - 按场景分类（如驻足型、点开型、存档型、暴击型、时段型、新手首秀型）。
    - 每个场景包含多条候选句子，随机或轮选使用。
    - 支持变量插入，如时段、数值（“数据表明：该问卷在深夜23点至凌晨1点之间的社交价值达到峰值”）。
    - 所有附注必须保持档案的公文语气，冷峻中带着荒诞，无负面暗示。
    - 档案末尾统一附上免责声明：“本档案由 15分钟名气管理局 自动生成。数据在真实基础上做了微量艺术加工。如有疑问，请勿联系，因为我们不存在。”
- 【待讨论】语料库规模与存储方式：初期建议预设30-50条覆盖主要场景，存储为配置文件或数据库表均可，便于运营随时补充。后续若量级增大，可迁移至独立内容管理系统。

## 8. 全局依赖与配置
### 8.1 概述
置顶系统的多个模块共享一组可调节的常量与阈值。这些参数集中管理，便于运营阶段根据实际数据快速调优，避免硬编码散落各处。
本节定义参数的类别、作用范围以及调整原则。具体数值将在后续的“全局参数设定”阶段统一分配。
---
### 8.2 可调常量分类
所有参数按功能域归类如下：
时间与周期类
- 置顶池生命周期（问卷在池中的有效时长）
- 候场区最大存在时间（超时自动清理）
- 自动轮播间隔（置顶栏自动刷新的频率）
- “换一批”冷却时长（手动刷新的最小间隔）
- 战绩单生成延迟（到期后多久触发，一般即时）
- 光环退场所需刷新次数（当前设计为2次）
权重与概率类
- 登场光环的基础权重值（需远高于常规区间上限）
- 归属分层的权重区间分隔值（确保自己与他人问卷不交叠）
- 内部排序的衰减系数（后入池问卷相对于首条的权重下降比例）
- 全局反向补偿各资历档位的权重系数（Lv.0至Lv.3的倍率锚点）
- 加权随机采样算法中的随机扰动因子（若有）
候场区进度类
- 总路程单位（当前固定100）
- 自然前进基础速率（单位/分钟）
- 前进速率的阶段变化点及对应速率
- 各资历档位的单次广告跳跃距离
- 每次跳跃对应的虚拟超越人数转换比例
池满线动态计算类
- 池满线计算所基于的活跃用户统计窗口（如近5分钟）
- 池满线比例（活跃用户数的百分比）
- 池满线上限值、下限值（绝对数量约束）
战绩单数据生成类
- 曝光量浮动系数范围（下限与上限，按资历分档可不同）
- 点击率随机范围（基准区间）
- 收藏转化率随机范围
- 收藏量保底最小值
- 数据暴击触发概率
- 暴击倍数范围
- 数据零头修饰规则（如取整方式）
反作弊与风控类
- 单用户每日最大置顶次数（软限制或硬限制）
- 广告观看最短有效时长（防止秒关）
- 同一设备或IP的请求频率限制
---
### 8.3 参数管理方式
建议采用集中配置表（如配置中心、云端开关或本地常量文件），支持动态下发与热更新，无需发版即可调整运营数值。初期可写死一组默认值，待上线后根据真实用户行为迭代。
---
### 8.4 广告回调接口通用设计
用户观看激励视频广告后，广告SDK（如微信小程序广告组件）会触发回调。系统需提供一个统一的广告回调处理端点，根据业务场景执行不同后续逻辑。
回调接口入口
- 请求方：小程序客户端，在广告播放完毕并确认有效后调用
- 入参：
    - 用户标识
    - 业务场景编码（区分“首次置顶”“候场区加速”“其他可能的广告入口”）
    - 关联的业务数据（如“候场区加速”场景需传入候场记录标识，首次置顶需传入问卷标识）
    - 广告平台返回的校验凭证（用于服务端二次验证，防止伪造回调，视广告平台能力而定）
处理流程
1. 校验用户标识与凭证有效性。
2. 根据业务场景编码路由至对应处理模块：
    - 场景“首次置顶”：调用置顶池入池逻辑（含绿色通道、池满线判断）。
    - 场景“候场区加速”：调用候场区执行加速逻辑。
3. 处理完成后返回结果，包含后续动作指示（如“刷新置顶栏”“播放冲线动画”等）。
4. 记录广告观看日志，用于对账和数据分析。
返回结构
- 状态码（成功/失败/需重试等）
- 结果描述（用户可读提示，如“置顶成功！”“已加速，还差一步即可登场”）
- 后续动作指令（客户端据此决定UI行为）
- 可选：最新的置顶栏数据（便于客户端立即刷新）
---
### 8.5 广告观看次数的防刷与风控策略
> 【待讨论】 由于小程序广告收入依赖真实观看，防刷是商业健康的关键。目前尚未深入讨论具体策略，仅列出设计要点供后续专项讨论：
需要防范的风险
- 脚本自动播放广告并伪造回调
- 用户使用插件或外挂快速批量完成广告观看
- 同一用户短时间内异常高频置顶（非正常娱乐需求）
- 通过切换账号或设备伪造新用户身份套取绿色通道福利
可供选择的技术手段
- 服务端二次校验广告平台回调凭证（优先依赖广告平台能力）
- 广告观看最短时长限制（客户端侧计时，低于阈值视为无效）
- 单用户每日置顶次数软帽（超过后强制冷却或降低权重，而非硬拒绝）
- 基于行为序列的异常检测（如观看间隔、操作轨迹）
- 设备指纹与账号关联分析，识别批量注册
建议
此部分需与广告平台技术对接人、后端开发及运营共同制定详细规则。初期可先上线基础频率限制，上线后根据数据逐步完善。
