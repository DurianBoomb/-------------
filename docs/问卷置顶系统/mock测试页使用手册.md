# Mock 测试页使用手册

> 路径：`/pages-tools/pin-test/pin-test`
> 副标题：阶段一·入池 / 阶段二·权重抽取 / 阶段三·过期清理 / 阶段四·候场区 / 阶段五·首页集成 / 阶段六·战绩单 / 阶段七·迁移与防刷

---

## 概述

测试页面覆盖置顶系统全部七个阶段的核心功能验证，共 14 个区块（含 Auto Run 自动化测试 + 防刷风控测试）+ 1 个附录。每个区块可以独立调用，也可以按业务流程串联测试。

---

## Section 1 — 连通性测试 ping

**目的**：验证 pin-system 云对象是否已正确部署、可以连通。

**操作**：点「调用 ping」。

**预期**：返回 `{ errCode: 0 }`。如果失败说明云函数未部署或 token 失效。

---

## Section 2 — 资历查询 getSeniority

**目的**：验证 `getSeniority` 方法正确读取用户的 `exposureCount` 并计算出资历档位。

**操作**：
1. 点「查询资历」查看当前资历
2. 用下方快速按钮 `[0] [1] [5] [6] [20] [21]` 或自定义输入修改 `exposureCount`
3. 再次查询验证档位变化

**预期**：展示当前档位标签（Lv.0 ~ Lv.3）、exposureCount、下一档差额。

**资历档位对照**（详见页底附录）：

| exp | 档位 |
|-----|------|
| 0 | Lv.0 · 新人 |
| 1~5 | Lv.1 · 偶发者 |
| 6~20 | Lv.2 · 常客 |
| 21+ | Lv.3 · 老面孔 |

**额外功能**：「重置三槽位」会清空你在 pin-pool 中的所有记录并重置 career.slots，用于测试前后的状态清理。

---

## Section 3 — 缓存验证

**目的**：验证 `getSeniority` 的 **内存缓存机制**（`this._seniority`）是否生效。

**操作**：
1. 先点「查询资历」查询一次
2. 去 uniCloud 后台直接修改 DB 中的 `exposureCount`
3. 回到页面点「再查一次」

**预期**：如果缓存生效，第二次返回旧值（未重新查 DB）；如果缓存失效，返回新值。当前阶段该缓存有效，是正确行为。

---

## Section 4 — 方法测试（已实现 / 空壳分离）

**目的**：验证哪些方法已实现、哪些仍为空壳（返回 `NOT_IMPLEMENTED`）。

**操作**：
- 「测试已实现」：一次性调用 `getQueueStatus`、`executeAccel`、`getSlotStatus`
- 「全部测试」：调用三个空壳方法 `generateCareer`、`checkCareerStatus`、`markCareerAsRead`

**预期**：已实现方法通过（errCode=0），空壳方法返回 `NOT_IMPLEMENTED`。如果空壳方法返回其他值说明该方法的实现代码已被引入但行为不正确。

---

## Section 5 — 未登录测试

**目的**：验证无 token 时云对象是否正确拦截并返回 `NOT_AUTH`。

**操作**：点「模拟无 token 测试」→ 前端临时清除 `uni_id_token` → 调用 `getSeniority` → 恢复 token。

**预期**：返回 `{ errCode: 'NOT_AUTH', errMsg: '用户未登录' }`。

---

## Section 6 — 入池测试（核心）

**目的**：完整验证 `handleAdReward` / `enterPool` / `queueToPool` 的入池逻辑，包括绿色通道、池满进候场、候场转置顶。

**操作**：

| 场景 | 前置条件 | 操作 | 预期 |
|------|----------|------|------|
| 绿色通道直入 | exposureCount=0 | 填写 surveyId → 点「调 enterPool」 | 返回 `direct_entry` + `greenChannel: true` |
| 池未满直入 | exposureCount≥1，池未满 | 同上 | 返回 `direct_entry` + `greenChannel: false` |
| 池满进候场 | exposureCount≥1，池满 | 同上 | 返回 `enter_queue` + 自动填充 queueId |
| 候场转置顶 | 已有候场记录 | 填写 surveyId + queueId → 点「调 queueToPool」 | 返回 `pool_entry` + pinData |

**使用提示**：下方「场景对照」提示框详细说明了每种情况的前置条件和判断依据。

---

## Section 7 — 抽取测试 draw（阶段二·权重算法）

**目的**：验证加权随机抽取的逻辑正确性，包括光环权重 10000、自己的问卷 300~500、他人问卷的反向补偿。

**操作**：
1. 先去 Section 6 入池造几条数据（自己的+他人的 mock）
2. 填写抽取数量 → 点「调 draw」
3. 查看结果列表

**预期验证**：
- 光环问卷权重显示 `10000`，标黄
- 自己的问卷权重在 `300~500`，绿底
- 他人的问卷权重在 `1~250`（取决于反向补偿系数），灰底
- 排序：光环 > 自己的 > 他人的，每层内随机洗牌

---

## Section 8 — 池子内容查看 getPoolContents

**目的**：查看 pin-pool 集合中所有有效（未过期）记录，验证数据写入正确性。

**操作**：点「查看池子」→ 列出所有有效卡片，按权重降序排列。

**验证项**：
- 总数是否正确
- 每条卡片的权重、剩余时间、光环标记
- 「剩余 ≤ 2 分钟」标红

**辅助功能**：「重置+清池」一键清空你的所有池子记录和槽位。

---

## Section 9 — 候场区测试（步骤流）

**目的**：分步验证候场区的完整生命周期——进候场、查状态、加速、模拟时间推进、自动入池。

**操作流程**：

```
⓪ 生成候场 → ① 查询状态 → ② 加速/入池 → ③ 模拟时间
```

| 步骤 | 操作 | 预期 |
|------|------|------|
| ⓪ | 填写 surveyId → 点「→ 进候场」。需要先开启「强制候场」开关（非 Lv.0 用户）或先设 exposureCount≥1 | 返回 `enter_queue` + queueId |
| ① | 点「🔍 查询状态」 | 显示当前阶段 + 日志 |
| ② | 点「⚡ 执行加速」，可重复 | 每次加速跳跃 N 个阶段（Lv.0 跳 4 档，Lv.1 跳 3 档，……），第三次加速自动入池 |
| ③ | 选时间按钮（2min/8min/15min/25min）修改 enterAt | 回到步骤①刷新可看到阶段随设置的时间推进 |

**关键验证**：
- 加速跳跃步数：Lv.0 → 4 步/次、Lv.1 → 3 步/次、Lv.2 → 2 步/次、Lv.3 → 1 步/次
- 自然推进 + 加速跳跃取较远者
- 第三次加速自动调 `queueToPoolImpl`
- ready 阶段自动兜底入池

## Section 10 — 过期清理测试（阶段三·定时云函数）

**目的**：验证 `pin-expiry` 定时云函数能否正确检测过期数据并生成战绩单。

**操作流程**：

```
① 造测试数据 → ② 调 pin-expiry → ③ 查看战绩单 → ④ 清理数据
```

| 步骤 | 说明 |
|------|------|
| ① | 创建过期 pin-pool 文档（1 分钟前过期）+ 超时候场记录（35 分钟前） |
| ② | 调用 `pin-expiry` 云函数（需先部署到云端） |
| ③ | 查询 `career-records` 看是否生成了战绩单 |
| ④ | 清除所有 `isTest: true` 标记的数据 |

**注意**：`pin-expiry` 云函数需手动部署到云端后才能被前端调用，模拟器内无法测试。

## Section 11 — 阶段五·首页集成测试

**目的**：验证首页 `pin-topbar` 组件的数据链路完整——draw 返回字段、卡片模拟渲染、事件回调结构。

### Panel A — draw 字段明细

**测试目标**：保证 `draw` 接口返回的每个 item 包含 `surveyAuthor` / `surveyCover` 等前端所需字段。

**操作**：
1. 先去 Section 12 注入他人模拟数据，或 Section 6 正常入池
2. 填写数量 → 点「调 draw」
3. 结果以 **逐字段展开** 的卡片列表展示

**验证项**：
- `surveyAuthor` 有值时标绿 "有值"，为空时标黄 "为空"
- `surveyCover` 同上
- 每条卡片显示 `_id`、`surveyTitle`、`weight`、`expireAt`

### Panel B — 首页卡片模拟渲染

**测试目标**：验证 `pin-topbar` 组件的 UI 渲染效果——卡片样式、橙色角标、光环动画、标题截断、封面图/兜底图标。

**操作**：
1. 在 Panel A 调 draw（自动填充到此处）
2. 水平滚动查看所有卡片

**验证项**：
- 有封面图 → 显示图片，无封面图 → 📋 图标
- 自己的卡片 → 橙色圆形"我"角标
- 光环卡片 → 金框脉冲动画
- 标题超出显示省略号
- 作者为空时显示"匿名"

### Panel C — 事件回调模拟

**测试目标**：验证首页 `index.vue` 的 `onPinned` / `onGreenChannel` 事件处理函数与后端返回的数据结构兼容。

**操作**：点三个按钮模拟不同场景：

| 按钮 | 验证内容 |
|------|----------|
| 模拟 direct_entry | `pinData` 5 个字段完整性、`expireAt` 可被 Date 解析 |
| 模拟 enter_queue | `queueData` 6 个字段完整性、首页行为（不刷新置顶栏，跳转 career-history） |
| 模拟 greenChannel | `pinData` 字段完整性、首页全链路（flash → dismiss → refresh） |

## Section 12 — 模拟数据管理器

**目的**：自主配置他人用户及其问卷，一键注入 pin-pool 用于 draw 测试。解决"刷不出别人卡片"的问题。

### 操作流程

```
配置用户 → 注入池子 → 切到 Section 11 验证
```

### 预置数据（打开页面即有）

| 用户 | userId | 昵称 | exp | 问卷数 |
|------|--------|------|-----|--------|
| 张三 | mock_user_a | 张三 | 0 (Lv.0) | 2 份 |
| 李四 | mock_user_b | 李四 | 5 (Lv.1) | 1 份 |
| 王五 | mock_user_c | 王五 | 20 (Lv.2) | 2 份 |

### 编辑方式

- 点用户卡片 → 展开编辑区
- 可改：`userId`、`昵称`、`资历`（0/1/5/20 快捷按钮 + 自定义输入）
- 问卷列表：可改 `surveyId`、`标题`，点 `[+ 问卷]` 新增，点 `✕` 删除
- 点用户右侧 `✕` 按钮删除该用户

### 测试场景对照

| 场景 | 配置方法 | 去 Section 11 验证 |
|------|----------|-------------------|
| 看他人卡片正常渲染 | 把张三的 userId 改成跟自己不同的字符串 → 注入 | Panel B 看张三的问卷没有"我"角标 |
| 资历影响权重 | 张三 exp=0、李四 exp=20 → 注入 | 调 draw → 张三卡片权重大于李四（补偿系数 2.5 > 0.6） |

| 自己+他人混合 | 先去 Section 6 正常入池 → 再注入他人数据 | Panel B 看自己的卡片有角标+光环，他人的没有 |
| 多条数据抽取 | 给王五加 10 份问卷 → 注入所有 | 调 draw → 他人卡片按权重排序，不重复 |

### 清理

点 `[🗑 清空]` 删除所有 `isTestMockData: true` 标记的数据，不污染真实池子。

## Section 14 — 阶段七 · 迁移 / 防刷 / 风控

### Panel A — 老用户 career 字段迁移

**目的**：一键补全所有缺少 `career` 字段的老用户。写入默认槽位 + `exposureCount=0`。

**操作**：点「▶ 执行迁移」。

**预期**：返回 `迁移完成，已为 X 个老用户补全 career 字段`。

---

### Panel B — 四道防线一键测试

**目的**：串行验证阶段七实现的所有防刷风控逻辑是否正常工作。测试前自动清理残留数据。

**操作**：点「▶ 四道防线测试」。

**测试清单**：

| # | 测试项 | 说明 | 预期 |
|---|--------|------|------|
| ① | 频率限制（_before RATE_LIMIT） | 连续 ping 6 次 | 第 6 次被 `RATE_LIMIT` 拦截（受限于冷启动可能不触发） |
| ② | 广告时长校验 | adDuration=5s（< 15s 阈值） | 拦截：返回 `AD_TOO_SHORT` 或抛异常 |
| ③ | 每日次数软帽 | 自动清空槽位后调 enterPool | 返回 0（入池成功）或 `DAILY_CAP_SOFT`（已达上限） |
| ④ | 正常时长放行 | adDuration=20s（>= 15s 阈值） | 不拦截，时长校验通过后走向入池逻辑 |
| ⑤ | isEnded 等价 | adDuration=0（未完整观看） | 跳过时长校验，走正常入池逻辑 |

**已知**：
- ① 可能因 **云函数冷启动** 不触发（`_rateLimitTimestamps` 挂在 `this` 上，冷启动后重置），这是 uniCloud 特性而非 bug。需要持久化限流可后续引入 Redis。
- ② 云对象可能以 `throw` 或 `return errCode` 两种方式报错，测试逻辑会兼容处理两种形式。
