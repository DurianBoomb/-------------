# 问卷置顶系统 - 技术开发文档
## 1. 核心概念与术语表
|术语|定义|
|-|-|
|置顶栏|首页顶部展示5张问卷卡片的区域，是整个置顶系统对用户可见的唯一"舞台"。数据来自置顶池的加权随机抽取。|
|置顶池|存放所有当前有效置顶问卷的无硬性上限集合。每条问卷入池后保留固定生命周期（15分钟），到期自动移出。是置顶栏抽取数据的唯一来源。|
|候场区|用户无法立即进入置顶池时的中间等待层。呈现为"置顶之路"挂机进度条，支持自然前进和广告加速两种方式。本质是人为架设的体验设计，非技术必需。|
|池满线|触发候场区的置顶池问卷数量阈值。MVP 阶段为固定值（暂定 1000，最终值待确认），后续可改为基于操作频率的动态版本。当池中问卷数≥池满线时，新用户需经过候场区方可入池。|
|曝光资历|用户历史累计成功置顶总次数。是反向补偿机制的核心依据——资历越浅，系统给予的隐性优待越多。对用户完全不可见，仅作后端计算输入。|
|登场光环|问卷进入置顶池后在整个生命周期（15分钟）内享有的最高权重状态。光环期间权重被拉至极高值，使得加权随机采样下该问卷极大概率被抽中并在前三出现——"两次刷新内大概率在前三"是概率锚点描述，非硬性保证。光环随问卷15分钟到期出池自然终结，无提前退场机制。|
|归属分层|权重体系的第二层规则：当前用户自己的问卷在抽取时获得远高于他人问卷的基础权重区间，确保"我的问卷"总在显眼位置。是视角诡计的技术实现核心。|
|视角诡计|利用归属分层和登场光环，让每个用户在自己的屏幕上几乎总能看见自己的问卷排在置顶栏高位，从而产生"我的问卷正被精选推荐"的主观体验。不同用户看到的置顶栏内容彼此独立，互不冲突。|
|绿色通道|曝光资历极浅（Lv.0）的用户享有的特权：无视池满线，直接进入置顶池，跳过候场区。是反向补偿在入池环节的具体体现。|
|反向补偿|贯穿系统全局的设计原则：曝光资历越浅的用户，在权重、加速效率、绿色通道、战绩单数据等方面获得越多隐性优待。目标是让"从未上过"的人比"天天在上"的人更容易获得曝光，形成自然轮换。|
|数据暴击|战绩单生成时的小概率惊喜机制。触发后某项数据（曝光量/点击量）获得额外倍率加成，同时匹配更稀有的头衔和评价。为战绩单增添意外之喜和分享冲动。|
|换一批（已取消）|原设计的手动刷新交互，因性能考虑在MVP阶段取消。用户仅通过回访首页（onShow）和下拉刷新触发置顶栏更新。|

**重要设计说明：**
- 用户同时最多 **3 条问卷** 在系统中流转（覆盖候场→置顶→待签收全生命周期）。三条满时不可发起新的置顶，需等其中一条走完腾出空位。
- 用户不再需要独立候场页面。所有实时状态展示（候场日志、置顶倒计时、待签收入口）全部集成在**历史档案页（career-history）** 的三槽位管理台中。用户任何时候进此页面即可查看/操作三个槽位的问卷，无需重新看广告。
### 2.2 模块关系
系统包含五个核心模块，数据流关系如下：
```plaintext
[模块一：曝光资历系统]
  提供：用户资历查询
    ↓ 被调用
[模块二：置顶池] ←→ [模块三：候场区]
  提供：入池、权重计算、  提供：排队状态管理、
        抽取、过期清理          广告加速处理
    ↓ 输出抽取结果
[模块四：置顶栏（首页展示）]
  提供：卡片展示、视角诡计落地、
        回访刷新交互
    ↓ 到期移出时触发
[模块五：战绩单 & 三槽位管理台] ←（新增）三槽位状态同步
  提供：即时战报生成、历史战绩页（含三槽位管理台）、
        分享长图
```
模块间依赖简述：
- 曝光资历系统：独立模块，为置顶池入池判断、权重计算、候场区加速效率、战绩单数据浮动提供统一的资历查询服务。
- 置顶池：核心存储与算法模块。接收来自候场区或直接入池的问卷，维护权重排序，响应置顶栏的抽取请求，并在问卷到期时由定时云函数同步生成战绩单。
- 候场区：独立于置顶池技术容量的人工排队层。接收不满足直接入池条件的用户，管理进度条状态与广告加速，达标后调用置顶池入池接口。
- 置顶栏：纯展示与交互模块。依赖置顶池抽取接口获取数据，依赖视角诡计规则（归属标记、光环标记）进行差异化渲染。不直接写入任何数据。
- 战绩单：由定时云函数在问卷到期时同步生成的后置模块。生成即时档案并持久化历史战绩数据。依赖曝光资历信息调整数据浮动系数。
### 2.3 技术栈（本项目实际栈）

本项目运行在 uniCloud 支付宝云生态中，以下为实际技术选型：

- **前端**：uni-app（Vue 2），编译到微信小程序。置顶栏动画使用 CSS 过渡 + uni-app 动画 API 实现。
- **用户认证**：统一使用 uni-id 的 `_before` 中间件模式。云对象 `pin-system` 的 `_before` 方法中调用 `uniCloud.getCurrentUserInfo()` 获取当前用户标识注入 `this.uid`，所有前端可调用的方法从 `this.uid` 获取用户标识，**不允许前端手动传 userId**。具体做法参考项目中 `survey` 云对象的 `_before` 实现。`draw` 等方法的入参中不再包含 `currentUserId`，服务端从上下文自动注入。
- **后端**：uniCloud 支付宝云云对象（Node.js），无状态函数。不提供传统 RESTful API——前端通过 `uniCloud.importObject('xxx').method()` 直接调用云对象方法。
- **数据库**：MongoDB 5.0 兼容（uniCloud 云数据库），用于所有数据存储：
  - 置顶池 → `pin-pool` 集合（文档型，weight 为字段）
  - 候场区状态 → `survey-queue` 集合
  - 曝光资历 → `uni-id-users` 表扩展字段（通过 schema.ext.js 扩展，不可直接修改内置 schema.json，否则 uni_modules 更新会覆盖）
  - 战绩单 → 新集合 `career-records`
  - 未读档案标记 → `uni-id-users` 表扩展字段 `career.hasUnread`（布尔，快速判断）+ `career.unreadCareerIds`（String[]，存储当前所有未读档案 ID 列表）
- **配置管理**：uni-config-center，将全局参数维护在 `uni-config-center/pin-system/config.json` 中，集中管理且支持热更新。
- **广告回调**：**无服务端广告回调接口**。微信小程序激励视频广告播放完毕后通过 `wx.createRewardedVideoAd().onRewarded()` 客户端事件触发，前端在确认后调用云对象方法执行业务逻辑。防刷依赖客户端侧频率限制 + 服务端频率兜底，**不存在广告平台二次验证的API可用**。
- **长图生成**：客户端 Canvas 实时绘制。项目已有 Canvas 2D 经验（结果页雷达图），无需服务端 Puppeteer 渲染。
- **缓存策略**：MVP 阶段无需引入独立缓存。数据量级评估：同时活跃置顶问卷最多数百张（MongoDB 全量查询毫秒级），候场区用户最多数千人（按用户单文档存储）。如后续用户量暴增可引入 Redis 作为查询缓存层，但当前架构不依赖 Redis。
- **冷启动**：uniCloud 云函数存在冷启动问题（首次调用约 1-2 秒）。置顶池抽取接口为高频调用，冷启动影响明显。建议将 pin-system 云对象保持常驻或通过定时健康检测降低冷启动频率。

> 注：以上为现行技术栈的约束。如需切换到 Egg.js/Nest.js + Redis + MySQL 的通用后端架构，需重建整个后端体系，与本项目的 uniCloud 生态不兼容。
## 3. 模块一：曝光资历系统
### 3.1 概述
曝光资历是贯穿整个置顶系统的核心用户属性，用于量化用户使用置顶功能的历史深度。它是反向补偿机制的决策依据——资历越浅，系统给予的隐性优待越多。
该属性对用户完全不可见，仅作为后端权重计算和候场区加速效率的输入参数。
---
### 3.2 数据模型
定义：曝光资历是一个整数，记录用户历史上累计成功完成置顶的次数。
累加规则：
- 累加时机：用户的问卷成功进入置顶池的那一刻（即广告看完、通过绿色通道或候场区后，系统将问卷写入置顶池的操作完成时）。
- 累加逻辑：用户的曝光资历字段值+1，此操作与问卷入池在同一事务或流程内完成，确保不会出现入池成功但资历未累加的情况。
- 注意：此处累加的是"入池成功"的次数，而非"看完广告"的次数。用户在候场区看广告加速但尚未入池时，资历不增加。只有最终进入置顶池的那一刻，资历才+1。
与问卷的关系：
- 每次入池的问卷会记录该时刻用户的曝光资历快照值，作为后续权重计算的依据。
- 同一用户在短时间内依次置顶多份问卷时，每份问卷携带的资历快照不同（后入池的资历更深），因此权重也不同。
---
### 3.3 资历分档
为了便于算法设计和运营调整，曝光资历被映射到四个档位。各档位的数值边界如下（开发期占位值，上线前调优 ⚠️）：
|档位|含义|占位边界值|说明|
|-|-|-|-|
|Lv.0|新人/稀客|exposureCount === 0|几乎未使用过置顶功能，享受最强反向补偿|
|Lv.1|偶发者|exposureCount ∈ [1, 5]|偶尔使用，享受中等偏上的反向补偿|
|Lv.2|常客|exposureCount ∈ [6, 20]|定期使用，作为权重计算的基准锚点|
|Lv.3|老面孔|exposureCount ≥ 21|频繁使用，反向补偿力度最弱|

分档的作用范围：
- 决定用户在他人屏幕上的权重系数（影响曝光概率和栏内排位）
- 决定用户是否享受绿色通道（跳过候场区直接入池）
- 决定用户在候场区的广告加速跳跃效率
- 决定战绩单数据的浮动系数
各档位的具体权重系数、跳跃比例等数值，统一在"全局参数配置"章节中定义，此处不展开。
---
### 3.4 查询接口需求
系统需提供查询用户曝光资历的能力，供各模块调用。
调用方：
- 置顶池入池流程（判断绿色通道资格）
- 权重算法（获取资历档位以计算权重系数）
- 候场区加速计算（获取资历档位以决定跳跃距离）
- 战绩单生成（获取资历档位以调整浮动系数）
入参：用户唯一标识
出参：
- 当前曝光资历数值
- 所属档位
- （可选）距离下一档位还需多少次
该接口为高频调用接口，需考虑缓存策略。注意 uniCloud 云函数为**无状态环境**，全局变量仅在单次实例生命周期内有效。建议的方案：
- **短时内存缓存**（当前请求内有效）：在单次云对象调用中，首查结果缓存在局部变量中，同次调用内复用。涉及资历查询的各模块（入池、权重、候场）在同一请求链中共享缓存
- **跨请求缓存**：需引入 uniCloud Redis（若服务已购买），或接受冷启动后首次调用查库的 1-2 秒延迟

MVP 阶段采用短时内存缓存即可，冷启动延迟由阶段 0.3.x 预热方案对冲。

## 4. 模块二：置顶池
### 4.1 概述
置顶池是整个系统的核心存储，存放所有当前有效的置顶问卷。它是一个无硬性容量上限的集合，问卷入池后获得15分钟生命周期（实际13分钟，详见 §4.3），到期自动移出。置顶栏展示和战绩单生成均依赖此模块提供数据。
置顶池在技术上可同时容纳海量问卷而不影响抽取性能。池满线和候场区是人为架设的体验层，与置顶池本身的技术能力无关。
---
### 4.2 数据模型

存储选型
置顶池采用 MongoDB 集合 `pin-pool` 作为主存储结构。选择理由：
- 与项目现有技术栈（uniCloud 支付宝云 + MongoDB）完全统一
- 每条问卷一个完整文档，所有附属字段（权重、资历快照、光环状态等）写在一起，无需多存储结构
- 通过 `expireAt` 字段配合定时云函数（每分钟一次）检测过期文档，到期同步生成战绩单，无需 TTL 索引
- 利用 `userId` 索引在抽取时高效过滤当前用户自己的问卷
- 加权随机采样在云函数内存中完成（查全量 → 累加概率 → Math.random()），同时活跃问卷数最多数百张，全量查询毫秒级

文档结构
每条置顶问卷在 `pin-pool` 集合中对应一个文档：
|字段|类型|说明|
|-|-|-|
|`_id`|String|自动生成，格式 `pin_{时间戳}_{4位随机数}`，确保同一问卷多次置顶时创建独立记录|
|`surveyId`|String|问卷唯一标识，关联问卷实际内容数据。与 `_id` 分离，支持同一问卷多次入池产生多条独立置顶记录|
|`userId`|String|所属用户标识，用于归属分层判断|
|`surveyTitle`|String|问卷标题，入池时从问卷数据冗余写入。`draw` 接口直接从此字段读取返回，无需额外 join 查询|
|`surveyCover`|String|问卷封面图片 URL，入池时冗余写入。配合 `surveyTitle` 用于置顶栏卡片渲染|
|`weight`|Number|当前综合权重值，由权重算法计算并更新。值越高在内存加权随机采样中被抽中的概率越大|
|`createdAt`|Timestamp|入池时间戳，精确到秒，用于15分钟生命周期判定和内部排序|
|`expireAt`|Timestamp|过期时间 = createdAt + 13分钟，定时云函数检测到期后处理（用户感知为15分钟）|
|`senioritySnapshot`|Number|入池瞬间用户的曝光资历快照值，固化用于后续权重计算|
|`haloActive`|Boolean|登场光环标记，true 表示光环生效中，权重走特殊逻辑。光环持续整个问卷生命周期（15分钟），随问卷到期出池自然终结|
|`isGreenChannel`|Boolean|是否通过绿色通道入池，用于数据分析和战绩单反向补偿参考|

索引
- `expireAt` — 普通索引，用于定时云函数查询过期文档
- `userId` — 普通索引，用于抽取时快速筛选当前用户自己的问卷

### 4.3 生命周期管理
入池
问卷完成入池条件判断（绿色通道 或 候场区冲线）后，系统执行以下操作：
1. 生成初始综合权重文档（含登场光环加成）：`db.collection('pin-pool').add(doc)`
2. 入池即写入完整文档，所有字段（createdAt、expireAt、userId、senioritySnapshot、haloActive=true 等）一次性写入
3. 累加用户的曝光资历值+1

在池期间
- 权重刷新：**入池时计算并一次性写入** MongoDB 的 weight 字段。抽取时仅读取 weight 字段做加权随机采样，**不触发全量重算**。登场光环权重在问卷的整个生命周期内维持极高值，不做衰减或提前退场。
- 权重更新时机：仅当用户有新问卷入池时，需遍历该用户在池中**已有问卷**，重新计算其内部排序顺序权重（仅更新该用户自己的问卷，他人问卷权重固定不变，不受影响）。**操作顺序**：先写入新文档（weight 基于已有文档的已知 createdAt 计算），再逐个更新旧文档的 weight。由于 uniCloud 云对象单实例串行处理请求，此窗口期内不会发生并发抽取。
- 光环问卷跳过规则：权重重算遍历用户已有问卷时，**跳过 `haloActive: true` 的文档**。光环中问卷的权重为固定极高值（如 10000），不应被重算覆盖。光环随问卷 15 分钟到期自然终结后，该问卷已从池中删除，不会产生"光环结束后未补算权重"的问题。

到期移出
- 生命周期固定为13分钟（实际时长），从入池时间戳（createdAt）起算。用户侧文案与感知保持"15分钟"。
- 移出方式：定时云函数（每60秒触发一次）查询 `pin-pool` 中 `expireAt < now` 的文档，对每条过期文档**同步**执行三件事：
  ① 生成战绩单档案 → 写入 `career-records` 集合
  ② 更新槽位状态 `active → claimable`，标记 `hasUnread = true`
  ③ 从 `pin-pool` 中删除该文档
- 不需要 TTL 索引、不需要 `career-pending` 待处理队列、不需要惰性消费。
- 定时函数每次处理使用条件删除（`deleteOne({ _id: ..., expireAt: { $lt: now } })`），确保同一文档不会重复处理。

### 4.4 权重算法
权重算法的核心目标是：为置顶池中每条问卷计算一个综合权重值，决定它在置顶栏抽取时的相对优先级。权重体系共四层，从高到低依次叠加。
层级一：登场光环
- 判定条件：问卷的"登场光环"标记（`haloActive`）为真。
- 规则：光环期间，问卷的综合权重被设置为一个极高的固定值（远大于正常权重区间），使得在加权随机采样时几乎必然以高概率被抽中。因权重极高，用户在前两次刷新中大概率看到自己光环中的问卷出现在前三——这是概率锚点描述，并非硬性保证，不做强制提位或替换操作。
- 持续与退场：光环覆盖问卷在置顶池的**整个生命周期**（15分钟）。光环随问卷到期出池自然终结，没有计数器、没有提前退场机制。光环期间权重始终维持极高值，不做衰减。
- 补充说明："两次刷新内大概率在前三"描述的是极高权重下的概率期望，不是规则。如果运气极差连续未抽中，不做服务端硬性干预——这反而让置顶栏的随机感更真实可信。
层级二：归属分层
- 判定条件：抽取请求携带当前用户标识，与池中问卷的所属用户标识进行比对。
- 规则：自己拥有的问卷，在归属分层中获得一个基础权重加成。该加成量级需确保自己的问卷在加权排序时，权重始终高于任何非自己的问卷（即使后者因反向补偿获得较高系数）。
- 实现思路：为"自己的问卷"和"他人的问卷"设置两个权重区间，两区间不重叠。自己的问卷权重落于高区间，他人的落于低区间。
层级三：内部排序——按问卷资历倒序（自己的问卷之间）
- 判定条件：当前用户在池中有多条问卷时生效。
- 规则：按问卷的入池时间先后排序，越晚进入池子的问卷权重加成越多。原因：对用户而言越晚入池的问卷越"新"，用户心理上天然认为新问卷理应获得更多曝光机会。
- 本质：此层与层级四均为资历排序。第3层锚点是**问卷资历**（越新越优先，倒序排列），第4层锚点是**用户资历**（资历越浅越优待，反向排列）。两个层级结构对称，仅作用对象和排序方向有细微区别。
- 例外：登场光环中的问卷因权重已设为极高固定值，不参与本层常规内部排序。光环随问卷15分钟到期自然终结，无需手动归入此层。
层级四：全局反向补偿（他人的问卷之间）
- 判定条件：所有非当前用户的问卷之间排序时生效。
- 规则：按问卷入池时记录的曝光资历快照值反向加权。资历越浅（数值越小），权重加成越多。同一用户的多份问卷因携带不同资历快照，权重各自独立计算。
- 锚点：以资历Lv.2（常客）的权重系数为基准1.0，Lv.0获得最高倍率，Lv.3获得最低倍率。具体倍率在全局参数中定义。
综合权重计算流程
每次需要计算一条问卷的权重时，按以下顺序执行：
1. 检查登场光环状态 → 若在光环中，返回光环固定高权重，结束。
2. 判断归属 → 确定基础权重区间（自己的高区间 / 他人的低区间）。
3. 若为自己的问卷 → 在基础区间内，根据入池先后顺序进行内部排序加成（越晚入池权重加成越多）。
4. 若为他人的问卷 → 在基础区间内，根据曝光资历快照进行反向补偿加成。
5. 返回最终权重值，更新 MongoDB 文档的 weight 字段：`db.collection('pin-pool').doc(id).update({ weight: finalWeight })`

### 4.5 入池逻辑
完整判断流程
用户点击"看广告置顶"后，系统按以下顺序依次判断（去重检查在广告播放之前执行）：
0. **去重检查**（最优先，广告播放之前执行）：检查同一 `surveyId` 是否已在置顶流程中流转。
   - 查询 `pin-pool`：`where({ surveyId, expireAt: db.command.gt(Date.now()) })` → 若存在，返回 `{ errCode: 'ALREADY_IN_POOL', errMsg: '该问卷已在置顶池中，无法重复置顶' }`，拦截。
   - 查询 `survey-queue`：`where({ surveyId })` → 若存在（候场区活跃记录），返回 `{ errCode: 'ALREADY_IN_QUEUE', errMsg: '该问卷已在候场区排队中，无法重复置顶' }`，拦截。
   - 均不存在 → 进入后继判断。
   - **设计理由**：去重检查必须在广告播放之前执行。如果在广告之后才做去重，用户看广告的 30 秒期间同一问卷可能被另一个设备操作入池，导致用户白看广告。前移到广告之前后，存在 TOCTOU 竞态残留风险（检查通过→看广告→入池的 30 秒窗口内可能被其他设备抢占），但概率极低，由后端入池时的最终去重检查兜底。此检查对所有资历等级一视同仁——即使是 Lv.0 新人，同一问卷已入池/入候场后也不可重复操作。前端三个入口（`pin-terminal-entry`、`ad-utils`、`queue-terminal`）统一处理 `errCode !== 0` → `uni.showToast({ title: res.errMsg })`，无需额外前端改动。
1. 绿色通道检查：查询用户当前的曝光资历档位。若为 Lv.0，跳过候场区，直接进入置顶池。入池时携带登场光环。
2. 池满线检查：获取当前置顶池的问卷数量，与池满线阈值比较。
    - 若池数量 < 池满线 → 直接进入置顶池，携带登场光环。
    - 若池数量 ≥ 池满线 → 进入候场区，启动"置顶之路"排队流程。
3. **候场区完成——两条路径**：候场区到达终点后（自然推进到达 ready 阶段，或第三次广告加速完成），进入置顶池，携带登场光环。两条路径的触发方不同：
   - **路径 A（自然完成）**：`getQueueStatus` 返回 `currentPhase === "ready"` 后，**后端在 `getQueueStatus` 内部检测到 ready 时直接自动调用 `queueToPool`**（兜底机制，即使前端未主动请求）。前端打开面板时触发查询，如已 ready 则后端自动完成入池，返回结果中直接携带入池成功确认，槽位锁定期限极短
   - **路径 B（第三次加速完成）**：`executeAccel` 内部检测到加速次数已达 3，**自动调用 `queueToPool`** 完成入池，返回结果中直接包含入池成功确认和置顶栏数据
4. **候场转置顶入口（queueToPool）**：由路径 A 前端调用或路径 B `executeAccel` 内部调用的独立入池入口，跳过绿色通道和池满线检查（候场区已保证入池资格）：
   - **入参**：用户标识、问卷标识、候场记录标识
   - **执行流程**：
     ① 检查 `survey-queue` 中 `_id === queueId` 的文档是否存在。不存在则直接返回成功（已由另一路径先入池，双调用安全跳过）
     ② 检查槽位状态（确认有闲置槽位可用）。无 `idle` 但存在 `claimable` 时，**自动回收为 `idle`** 后使用（同入池前置处理逻辑，战绩记录不受影响）
     ③ 写入 `pin-pool` 文档（含登场光环，`weight` 字段通过权重算法计算后一次性写入）
     ④ **条件累加资历**：使用条件更新 `db.collection('uni-id-users').where({ _id: userId, 'career.exposureCount': senioritySnapshot }).update({ 'career.exposureCount': db.command.inc(1) })`。如果资历在入池期间已被另一路径推高，条件不成立则不累加，避免双调用重复计数
     ⑤ 删除 `survey-queue` 中的对应候场记录（`_id: queueId`）
     ⑥ 更新槽位状态、写入 pinId
⑤ **定位槽位**：通过 `career.slots[i].queueId === queueId` 匹配（唯一，消除同一用户对同一问卷多次置顶时 surveyId 重复的歧义）。queuing 状态时 `queueId` 已写入槽位，入池后写入 `pinId` 并清空 `queueId`
   - **出参**：入池成功确认 + 登场光环信息 + 首次抽取的置顶栏数据（便于前端立即跳转展示）
池满线固定值（MVP阶段）
- MVP 阶段池满线写死为固定值（暂定 1000，待确认），作为全局可配参数存储在配置集合中。
- 理由：uniCloud 无法统计"当前在线用户数"；改用操作频率方案在 MVP 阶段感知不到效果差异（无人使用时操作频率同样为 0）。
- 后续扩展：待用户量上升后，可改为基于最近 N 分钟置顶池操作频率（入池次数/抽取次数）的动态计算版本，通过 MongoDB 日志聚合实现。
入池接口
该接口由前端在确认广告完整播放后（`onRewarded` 事件）调用云对象方法触发，执行完整的入池判断流程，并返回结果状态：
- 入参：用户标识、问卷标识
- 入池前置处理：**槽位二次确认**——检查当前是否有空闲槽位。用户看广告前已做一次前置检查（流程图 §2.1），但广告播放期间（1-2 分钟）槽位可能变动（另一条问卷到期变为 claimable），在此二次确认防止超额。
   - 有 `idle` 槽位 → 正常进入后续流程。
   - 无 `idle` 槽位但存在 `claimable`（待签收）槽位 → **自动将 `claimable` 回收为 `idle`**，然后使用该槽位正常入池。战绩记录已由 pin-expiry 写入 `career-records` 集合，回收槽位不影响战绩数据本身，仅清除"待签收"通知标记。
   - 三个槽位全部占满（queuing / active / claimable 均无可用空间）→ 返回"已达上限"错误
- 出参：
    - 结果状态码（`direct_entry` 直接入池 / `enter_queue` 进入候场区）
    - 若入池成功：返回登场光环生效的确认信息
    - 候场区初始状态由 `handleAdReward` 封装后以 `queueData` 字段返回（见 §8.4 返回结构）

### 4.6 抽取逻辑
置顶栏每次需要展示或刷新时，调用本模块的抽取接口，从置顶池中获取指定数量的问卷。
抽取方式
采用内存加权随机采样。池中每条问卷被选中的概率与其综合权重（MongoDB 文档的 weight 字段值）成正比。权重越高，被抽中的概率越大。实现流程：
1. 查询有效问卷：`db.collection('pin-pool').where({ expireAt: > now }).get()`
2. 在云函数内存中构建累计权重数组，计算总权重和 totalWeight
3. 生成随机数 `pick = Math.random() * totalWeight`，遍历数组累减命中
4. 选中后从数组中移除该项目，继续下一轮采样，确保不重复
5. 重复 5 次得到 5 份不重复的问卷结果
6. 对结果按 weight 从高到低排序确定栏内展示位置

抽取数量
每次抽取5份问卷，对应置顶栏5张卡片。若池中问卷数不足5份，则返回全部。
特殊处理
- 去重：内存采样时每次选中后从候选数组移除，天然无重复，无需额外去重逻辑。
- 兜底：极端情况下池中无任何问卷，返回空列表，置顶栏展示占位引导内容（如"还没有问卷在置顶，快来看广告抢占C位"）【空的情况下要注意测试】。
抽取接口
- 入参：当前用户标识、抽取数量（固定5）
- 出参：问卷列表（含 surveyId、surveyTitle、surveyCover、isMine、haloActive 等字段），按权重从高到低排序后返回。**标题和封面直接从 `pin-pool` 文档的 `surveyTitle`/`surveyCover` 冗余字段读取**，无需额外 join 查询问卷表。**列表的数组索引即是栏内展示顺序**（item[0]为第1位），前端直接按返回顺序渲染，无需额外传排序位置字段。
- **认证说明**：当前用户标识由 uni-id 上下文 `this.uid` 自动注入，前端入参中不传 `userId`
调用频率
该接口为高频接口，每次用户进入首页、或下拉刷新时都会调用。需注意云函数冷启动影响（首次调用约1-2秒），建议在首页加载时提前预热云对象。

### 4.7 过期清理（定时云函数）

清理策略
采用定时云函数（每分钟一次）主动检测并处理过期文档，无需 TTL 索引和惰性删除双保险。

定时函数运行流程：
1. 查询过期文档：`db.collection('pin-pool').where({ expireAt: { $lt: now } }).get()`
2. 对每条过期文档，**同步**执行：
   - 生成战绩单档案 → 写入 `career-records` 集合
   - 更新槽位状态 `active → claimable`，标记 `hasUnread = true`
   - 从 `pin-pool` 中删除该文档
3. 若无过期文档，直接返回（零开销）。

实现方式：
- uniCloud 支付宝云支持定时触发器（Timer Trigger），设置每 60 秒运行一次该云函数。
- 此函数只做一件简单的事（查过期 → 处理 → 删除），逻辑集中，易于调试。
- **冷启动与超时处理**：
  - 已通过阶段 0.3.x 预热方案降低冷启动影响
  - **将 `generateCareer` 的核心数据生成逻辑内联进 `pin-expiry` 云函数**（不通过 `importObject('pin-system')` 跨云函数调用），避免两层冷启动叠加和跨云函数网络延迟
  - `pin-system` 云对象中保留 `generateCareer` 方法供非定时场景调用（如未来可能的管理台手动生成），pin-expiry 直接内联实现避免依赖
- **批量处理与超时兜底**：
  - 每次定时触发最多处理 20 条过期文档，超出部分留待下个周期（60 秒后）。单文档含 3-4 次数据库写入，20 条 × 4 次写入 ≤ 2 秒，远低于云函数 10 秒超时限制
  - 每条文档独立 try-catch（见异常处理），失败文档保留 expireAt 下次重试

异常处理
- 幂等设计：每次处理使用条件更新 + 条件删除（`deleteOne({ _id: docId, expireAt: { $lt: now } })`），同一文档不会重复处理。
- 兜底：即使定时云函数偶发故障（延迟超过 1 分钟），抽取接口的 `where({ expireAt: { $gt: now } })` 仍可自然过滤过期文档，确保前端不展示过期内容。
- 单文档异常兜底：每条过期文档的处理**相互独立**，使用独立的 try-catch 包裹：
  - 处理成功 → 正常删除 `pin-pool` 文档，生成战绩单，更新槽位
  - 处理失败 → **不删除该文档**（保留 `expireAt` 不变），下一轮定时函数运行时重新处理
  - 同一文档连续失败 3 次 → 上报异常日志至错误监控平台，人工介入排查
  此设计确保一条文档的异常不会阻塞同批次其他文档的处理进度。
- 最多 1 分钟延迟：用户置顶到期后，最长等 1 分钟即可生成档案。为应对此延迟，实际有效时长设为 13 分钟，留 2 分钟作缓冲。

**候场区兜底清理**：pin-expiry 同样检测 `survey-queue` 中 `enterAt + 35 分钟 < now`（覆盖 L3 最大 25 分钟 + 10 分钟缓冲）的记录，对这些候场记录执行：
- 检查其对应槽位状态，若仍为 `queuing` 则调用 `queueToPool`（补偿"用户从未打开候场面板，ready 未被检测到"的死胡同情况）
- 若对应槽位已不是 `queuing`（已被另一路径处理），则直接删除该 `survey-queue` 记录
- 不使用 TTL 索引（uniCloud 对 TTL 支持不透明），统一由 pin-expiry 管理过期清理

## 5. 模块三：候场区（系统监控终端）
### 5.1 概述
候场区是用户无法立即进入置顶池时的中间等待层。它与置顶池的技术承载能力无关——置顶池本身可容纳海量问卷——而是为了制造仪式感、差异化优待和插队快感而主动架设的体验设计。
在叙事层，候场区被包装为一个虚构的"系统监控终端"界面。用户提交置顶请求后，不再是看到一条干巴巴的进度条，而是进入一个黑底绿字的等宽字体终端屏幕，旁观系统对自己的问卷进行"含梗量检测""舆情预测""推送分发"等一本正经的荒诞处理。每一行滚动的日志都是进度本身——日志滚完，意味着处理完毕，问卷进入置顶池。
对内，候场区是一个不维护全局真实队列顺序的"黑盒"表演系统。用户看到的排队人数、跳过人数、处理阶段均由算法基于其个人状态参数实时生成，不与任何真实队列精确挂钩。
与战绩单的叙事关系：候场区是"系统正在处理你"，战绩单是"系统已完成认证"。两者同属一个虚构世界观——监控中心负责处理问卷，名气管理局负责签发档案。候场区日志里的"含梗量检测"在战绩单里变成"含梗量宗师"荣誉称号，同一套语言体系，首尾呼应。

**交互入口变更（V2.0）**：候场内容不再作为独立全屏页面。用户通过**历史档案页（career-history）** 顶部三槽位管理台点击"候场"状态卡片，页面底部弹出半屏面板展示终端日志。详见 7.3 节。
### 5.2 数据模型
存储选型
规格书相关依据：后端为 uniCloud 支付宝云，数据库为 MongoDB 5.0 兼容的文档型数据库，云函数为 Node.js 环境。现有业务已大量使用云数据库存储状态（答题记录、收藏、点赞等）。
建议方案：使用云数据库新建一个集合（如 survey-queue）存储候场区状态。理由：
- 与现有技术栈完全统一，无需引入 Redis
- 候场区并非高频写入场景——用户每分钟自然前进更新一次、看广告时跳跃一次，MongoDB 完全能承载
- 文档型结构天然适合存储用户维度的候场状态（单文档包含所有字段）
- 可利用云数据库的 TTL 索引实现兜底清理（设置 expireAt 字段自动过期）
若后续用户量暴增需要更高性能，可再引入 Redis 缓存层，但 MVP 阶段直接用云数据库足够。
字段定义
候场区**允许多条候场记录同时存在**（同一用户的不同槽位问卷可同时处于候场状态），`survey-queue` 不再以 userId 为主键：
|字段|类型|说明|
|-|-|-|
|`_id`|String|自动生成，格式 `queue_{时间戳}_{4位随机数}`|
|`userId`|String|用户标识，建立普通索引用于查询当前用户的所有候场记录|
|`surveyId`|String|正在排队等待入池的问卷|
|`enterAt`|Timestamp|进入候场区的时间戳|
|`acceleratedCount`|Integer|已通过看广告加速的次数（0/1/2，最多3次）|
|`seniorityLevel`|Integer|进入候场区时用户的资历档位快照（Lv.0-Lv.3），用于后续加速计算|
|`currentPhase`|String|当前日志所处的处理阶段标识（如 queuing / inspecting / pushing / ready），用于判断日志展示位置和加速跨度|

生命周期
- 创建：用户看完广告，经判断不满足绿色通道且池满线已满时，创建候场记录。当前处理阶段初始值为排队阶段。
- 更新：用户每次看广告加速，更新已加速次数，并调大 `effectiveElapsed` 偏移量使更多日志行到期；自然推进随时间流逝自动推进，由 `calcVisibleSlots()` 遍历文本列表累加间隔判断到期行。
- 完成：所有日志行到期（`calcVisibleSlots()` 返回全部行，`currentPhase = "ready"`），或已加速次数达到 3 时在 `executeAccel` 中自动调用 `queueToPool` 完成入池。候场记录删除。
- 兜底清理：由 pin-expiry 定时云函数统一管理（每 60 秒检测 `enterAt + 35 分钟 < now` 的记录并清理或处理，见 §4.7）。不使用 TTL 索引。

### 5.3 终端日志机制（文本驱动）

候场区呈现为一个虚构的"系统监控终端"界面：黑底，等宽字体，日志逐行滚动。用户在此旁观系统对自己的问卷进行"含梗量检测""舆情预测"等一本正经的荒诞处理。日志的推进节奏本身就是等待进度，不需要额外进度条。

#### 5.3.1 总架构

**一个日志流 = 固定文本骨架 + 按资历动态展开的池文本序列**

- 固定文本（阶段标题、过渡节点）是骨架——每个用户每条日志流都出现，数量固定（10~12 条）
- 池文本（审核/质检/推送三条叙事线）受资历控制展开——资历越深，抽取条数越多
- 每条文本自带间隔（`interval`），总时间 = Σ 所有文本的间隔
- 前缀由文本类型决定（`[系统]`、`[审核]`、`[质检]`、`[推送]`），池文本不带前缀

用户看到的是：每次日志的叙事骨架一致（排队→审核→质检→推送→完成），但池文本的内容和总量随资历变化——新人唰一下过，老用户慢慢刷。

**个性化锚点砍掉**：不做 `{标题}`、`{标签名}` 等占位符替换。终端是纯后台视角。

#### 5.3.2 阶段结构与文本展开

核心原则：**固定文本定骨架，池文本按资历展开，时间由文本数量和间隔决定。**

**固定文本骨架（所有用户相同，10~12 条）**

| # | 前缀 | 内容 | 间隔 | 进度暗示 |
|---|------|------|------|---------|
| — | `[系统]` | "════ 排队等候 ════" | 2s | 刚开始 |
| — | `[系统]` | "你的问卷已进入处理队列" | 2s | |
| — | `[系统]` | "正在分配处理节点... 节点已就绪" | 2s | 排队结束 |
| — | `[审核]` | "════ 内容审核 ════" | 2s | ~20% |
| — | `[审核]` | "审核意见记录完毕" | 2s | 审核结束 |
| — | `[质检]` | "════ 质量检测 ════" | 2s | ~45% |
| — | `[质检]` | "传播潜力预估完毕" | 2s | 质检结束 |
| — | `[推送]` | "════ 推送分发 ════" | 2s | ~70% |
| — | `[推送]` | "分配初始曝光权重… ✓" | 2s | 推送结束 |
| — | `[系统]` | "════ 处理完成 ════" | 2s | 100% |

固定文本总贡献时间：10 × 2s = **20 秒**。

**池文本动态展开（受资历控制）**

三个阶段各自展开池文本：

```
骨架：
[排队标题] → 排队固定文本 → [审核标题] → [审核池展开 N 条] → 审核过渡文本
             → [质检标题] → [质检池展开 M 条] → 质检过渡文本
             → [推送标题] → [推送池展开 K 条] → 推送过渡文本
             → [特殊状态（若有）] → [完成标题] → 完成
```

N、M、K 由资历查表决定，见 §5.3.5 资历-时间对应表。

**各阶段文本间隔**

| 阶段 | 池 | 间隔 | 叙事理由 |
|------|-----|------|---------|
| 排队 | 无池（纯固定文本） | 2s | 一闪而过，起手式 |
| 审核 | 审核池 | 3s | 快节奏。像刷朋友圈，扫一眼一条。好奇、试探、随口点评 |
| 质检 | 质检池 | 5s | 慢节奏。在真正读题、在思考、在被戳中。慢 = 系统在认真品 |
| 推送 | 推送池 | 4s | 中节奏。监控模式，悠闲看后台数据一条条进来 |
| 固定文本 | — | 2s | 阶段路标，不需停留 |
| 特殊状态 | — | 4s | 与推送池同节奏 |
| 系统填充 | — | 2s | 低辨识度后台日志，快闪 |

#### 5.3.3 文本池定义

**三类主池**

| 池 | 前缀 | 间隔 | 叙事角色 | 最终需求 |
|----|------|------|---------|---------|
| 审核池 | `[审核]` | 3s | 扫标题、第一印象、随口点评。审核员的 quick scan | **100 条** |
| 质检池 | `[质检]` | 5s | 坐下来读题、深度吐槽、被戳中后的真实反应 | **145 条** |
| 推送池 | `[推送]` | 4s | 后台监控模式，看数据一条条进来，分配曝光 | **64 条** |

三个池的文本都是纯内容，不带前缀。前缀在阶段定义里绑定，程序拼接时加上。

**系统填充池**

为什么需要填充池：三个池的总容量覆盖 L3 最大需求，但 L2/L3 仍需额外时间填充来延长总时长。填充池提供低成本的系统日志文本。

| 属性 | 值 |
|------|-----|
| 容量 | **30 条** |
| 间隔 | 2s |
| 内容 | 低成本系统日志——"正在交叉比对第 N 题…""含梗量二次校准…""传播链路预计算…" |
| 特点 | 无个性、可循环使用、不需要 AI 精雕 |
| 适用 | L2+ 用户，每 3 条池文本插 1 条填充 |
| 插入位置 | 均分在对应阶段的池文本之间 |

为什么可循环：用户看 300+ 行终端日志时注意不到其中 30 条系统填充文本在循环——心理感知阈限远低于实际去重能力。

**其他池**

| 池 | 前缀 | 容量 | 触发 | 说明 |
|----|------|------|------|------|
| 固定文本 | 各阶段前缀 | 10~12 条 | 始终出现 | 阶段标题 + 过渡节点 |
| 特殊状态 | `[加速]`/`[新人]`/`[深夜]`/`[下班前]` | 4 子类 × 10+ 条 | 互斥四选一 | 插在完成标题之前，间隔 4s |

#### 5.3.4 抽取与拼接逻辑

**流程**

1. 用户提交问卷，触发日志流生成
2. 系统读 `exposureCount`，查资历表得 N、M、K
3. 构建日志流：
   - 依次插入固定文本（排队阶段 + 审核标题）
   - 审核阶段：从审核池随机抽取 N 条（去重），L2+ 按每 3 条池文本插 1 条填充（从填充池顺序取，用完从头循环）
   - 插入审核过渡文本 + 质检标题
   - 质检阶段：从质检池随机抽取 M 条（去重），L2+ 同上规则插入填充
   - 插入质检过渡文本 + 推送标题
   - 推送阶段：从推送池随机抽取 K 条（去重），L2+ 同上规则插入填充
   - 插入推送过渡文本
   - 特殊状态判定（互斥，四选一）
   - 插入完成标题
4. 返回完整日志流给前端，每条文本自带 `interval`

**填充插入逻辑**

填充的目的是**延长 L2/L3 的总时间**，与池容量无关。三个主池已扩至覆盖 L3 最大需求。

```
if (level >= 2) {
  // 每 3 条池文本插入 1 条填充（分阶段独立计算）
  reviewFillers  = Math.floor(N / 3)
  qualityFillers = Math.floor(M / 3)
  pushFillers    = Math.floor(K / 3)
  // 在对应阶段的池文本序列中，每 3 条后插 1 条填充
}
```

等效于：

| 级别 | 审核填充 | 质检填充 | 推送填充 | 填充总量 |
|------|---------|---------|---------|---------|
| L0 | 0 | 0 | 0 | 0 |
| L1 | 0 | 0 | 0 | 0 |
| L2 | floor(65/3)=21 | floor(95/3)=31 | floor(42/3)=14 | **~66** |
| L3 | floor(100/3)=33 | floor(145/3)=48 | floor(64/3)=21 | **~102** |

**去重逻辑**

- 每个池维护"本次已抽取"临时索引
- 同一用户同一次日志流内，同一池不重复抽取同一条
- 主池已扩至覆盖 L3 最大需求（审核 100、质检 145、推送 64），正常不会超额。若因配置错误或未来调整导致 N > 池容量：前 `池容量` 条不重复，超出部分从池头重新轮取（安全网）
- 填充池可循环：30 条一轮，用完从头开始

**特殊状态判定**

| 子类 | 前缀 | 触发条件 | 判断逻辑 |
|------|------|---------|---------|
| 加速 | `[加速]` | 候场记录有加速标记 | `acceleratedCount > 0` |
| 新人 | `[新人]` | 用户首次提交问卷 | `exposureCount === 0` |
| 深夜 | `[深夜]` | 北京时间 0:00-6:00 | `hour >= 0 && hour < 6` |
| 下班前 | `[下班前]` | 北京时间 17:00-19:00 | `hour >= 17 && hour < 19` |

四个条件互斥，优先级：加速 > 新人 > 深夜/下班前（时间段）。一次日志流最多触发一个特殊状态。

```javascript
// 特殊状态判定
const cnHour = new Date().getHours()
let specialLog = null
if (acceleratedCount > 0) {
  specialLog = pickRandomFrom(specialStatusPool.accelerate)
} else if (exposureCount === 0) {
  specialLog = pickRandomFrom(specialStatusPool.newcomer)
} else if (cnHour >= 0 && cnHour < 6) {
  specialLog = pickRandomFrom(specialStatusPool.lateNight)
} else if (cnHour >= 17 && cnHour < 19) {
  specialLog = pickRandomFrom(specialStatusPool.endOfDay)
}
if (specialLog) {
  // 插在完成标题之前，而非末尾
  const doneIndex = logLines.findIndex(l => l.text === '════ 处理完成 ════')
  if (doneIndex >= 0) {
    logLines.splice(doneIndex, 0, specialLog)
  } else {
    logLines.push(specialLog)
  }
}
```
#### 5.3.5 终端节奏控制（文本驱动）

**核心模型**

**时间不由计时器 `atSecond` 决定，由文本的间隔之和决定。**

```
总时长 = 固定文本 × 2s + 审核池 × 3s + 质检池 × 5s + 推送池 × 4s + 填充文本 × 2s + 特殊状态 × 4s
```

每条文本一个 `interval`（秒），前端按顺序展示，本行显示后等 `interval` 秒再推出下行。后端不再维护 `slotSchedule` 硬编码时间表，改为遍历文本列表累加间隔。

**前端 = 哑终端**

前端不计算时间。只做两件事：
1. 展示后端返回的行
2. 每 3 秒轮询 `getQueueStatus` 获取最新可展示行

**前后端协作模型**

```
前端（终端组件）                    后端（getQueueStatus）
    │                                      │
    ├─ 打开终端面板 ──────────────────────→│
    │                                      ├─ 根据 enterAt + 当前时间
    │                                      │  遍历文本列表，累计每条 interval
    │                                      │  返回所有已到期的行
    │←─ 返回当前所有应展示的行 ──────────┤
    │                                      │
    ├─ 逐行动画展示                         │
    │                                      │
    ├─ 3 秒后再次轮询 ───────────────────→│
    │                                      ├─ 遍历，如新增行到期则返回
    │←─ 返回新增的行（或空） ────────────┤
    │                                      │
    ├─ 继续 3 秒轮询...                    │
    │                                      │
    │←─ 某次返回 currentPhase: "ready" ──┤  ← 所有文本到期
    │                                      │
    └─ 触发入池                              │
```

**后端推进算法**

```javascript
function calcVisibleSlots(logLines, enterAt, now) {
  const elapsed = (now - enterAt) / 1000  // 已过秒数
  let accumulated = 0
  const visible = []

  for (const line of logLines) {
    accumulated += line.interval
    if (elapsed >= accumulated) {
      visible.push(line)
    } else {
      break  // 后面的都没到时间
    }
  }

  return visible
}
```

`logLines` 是已拼好的完整文本列表，每条自带 `interval` 字段。代码量远小于原来 16 槽位 `slotSchedule` 数组。

**资历-时间对应表**

| 级别 | exposureCount | 审核(N) | 质检(M) | 推送(K) | 池文本 | 填充 | 总文本 | 等待时间 |
|------|--------------|---------|---------|---------|--------|------|--------|---------|
| L0 | 0 | 3 | 4 | 3 | 10 | 0 | ~21 | **~1 分钟** |
| L1 | 1-5 | 18 | 26 | 12 | 56 | 0 | ~67 | **~4.5 分钟** |
| L2 | 6-20 | 65 | 95 | 42 | 202 | ~66 | ~279 | **~17 分钟** |
| L3 | ≥21 | 100 | 145 | 64 | 309 | ~102 | ~422 | **~25 分钟** |

**计时验证：**

- L0：20 + 3×3 + 4×5 + 3×4 + 0×2 + 4 = 20 + 9 + 20 + 12 + 4 = **65s ≈ 1 分钟**
- L1：20 + 18×3 + 26×5 + 12×4 + 0 + 4 = 20 + 54 + 130 + 48 + 4 = **256s ≈ 4.3 分钟** → **~4.5 分钟**
- L2：20 + 65×3 + 95×5 + 42×4 + 66×2 + 4 = 20 + 195 + 475 + 168 + 132 + 4 = **994s ≈ 16.6 分钟** → **~17 分钟**
- L3：20 + 100×3 + 145×5 + 64×4 + 102×2 + 4 = 20 + 300 + 725 + 256 + 204 + 4 = **1509s ≈ 25.2 分钟** → **~25 分钟**

#### 5.3.6 广告加速

广告加速不再跳跃槽位索引。新方案：

- 后端 `executeAccel` 中按资历档位调大 `effectiveElapsed` 偏移量
- 等效于瞬间推进一段累计间隔，让更多文本"到期"
- 第三次加速直接将所有文本标记为到期（`currentPhase = 'ready'`）
第三次加速必定完成：
- 判定：已加速次数当前为 2，且用户再次触发广告加速（调用 executeAccel）
- 规则：executeAccel 内部检测到加速次数将达 3 时，**自动调用 queueToPool** 完成入池，不再依赖前端再次请求
新人绿色通道（入池闪屏效果）：
- 曝光资历为 Lv.0 的用户看完广告后，由于跳过候场区直接入池，需展示约 1-2 秒的绿色通道动画作为入池确认反馈
- 占位组件路径：`components/green-channel-splash/green-channel-splash.vue`

#### 5.3.8 语料库存储方案

**存储位置**

语料库**不存数据库**，**不塞 config.json**，作为独立 JS 模块放在云函数目录下：

```
uniCloud-alipay/cloudfunctions/pin-system/text-pools.js
```

云函数启动时 `require` 进来，直接挂在内存，零查询延迟。

**理由**

| 存储位置 | 为什么不选 |
|---------|-----------|
| 数据库 | 语料是静态内容资产，运行时不会增删改。多一次查询 = 无意义的延迟 |
| `config.json` | config.json 定位是**运行时可调参数**（资历阈值、生命周期、权重系数等）。语料预估 ~12.5KB，塞进去让 config 臃肿到不可维护 |
| 独立 JS 模块 ✓ | 改文案不动配置，调参数不动文案。云函数冷启动时随代码一起加载，零额外开销 |

### 5.4 候场区接口
接口一：查询候场状态
- 调用时机：用户进入候场终端界面或返回查看时调用。
- 入参：用户标识、候场记录标识（`queueId`，即 `survey-queue` 集合的 `_id` 值，格式 `queue_{时间戳}_{4位随机数}`；指定查询哪条候场记录；若为空则返回该用户当前所有候场记录列表）
- 出参：

    - `logLines`：完整日志流（文本数组，每条含 `text`、`interval`、`prefix` 字段）

    - `currentPhase`：当前处理阶段（queuing / inspecting / pushing / ready）
    - `effectiveElapsed`：当前有效流逝秒数（含加速偏移量），供前端显示进度参考

- 调用时机：前端确认用户完整看完激励视频广告后（`onRewarded` 事件），调用云对象方法触发。
- 入参：用户标识、候场记录标识（`queueId`，指定对哪条候场记录执行加速）
- 出参：
    - 加速结果状态码（正常推进 / 已完成入池）
    - 本次加速后新增可见的行（相比加速前的 visibleLines 增量）
    - 加速后的 `effectiveElapsed` 和 `currentPhase`
    - 若已完成入池（第三次加速时自动调用 queueToPool）：返回登场光环确认信息，以及入池后首次抽取的置顶栏数据

## 6. 模块四：置顶栏（首页展示）
### 6.1 概述
置顶栏是首页顶部的核心展示区，也是整个置顶系统对用户唯一可见的"舞台"。它由5张问卷卡片组成，数据来源于置顶池的加权随机抽取。置顶栏承载了视角诡计的落地——每个用户看到的置顶栏内容因归属分层而不同，自己的问卷总是以极高概率出现在显眼位置。
置顶栏的交互包括首页回访自动刷新和登场光环期间的强保证展示。
---
### 6.2 展示规则
卡片数量
固定展示5张问卷卡片。若置顶池中问卷总数不足5张，则展示全部可用问卷，剩余位置显示占位引导卡片（如"虚位以待，看广告抢占C位"）。
自动轮播（首页回访刷新）
- 置顶栏移除定时自动刷新机制，改为**每次用户返回首页时自动刷新一次**。
- 触发时机：小程序页面 `onShow` 生命周期（包括从其他 tab 切换回来、从二级页面返回、从后台切回前台等）。每次用户重新看到首页，置顶栏都重新抽取一批新卡片。
- 理由：用户在首页单次停留时间通常很短，定时轮询浪费服务端资源，且每次回访都有新内容比定时变化体验更好——每次回来都有"新发现"的惊喜感。
手动刷新（已取消）
- MVP阶段取消手动"换一批"按钮。用户仅通过回访首页（onShow）和下拉刷新触发置顶栏更新。
- 理由：取消手动刷新后，每次抽取调用均不涉及高频率重复请求，权重无需在每次抽取前全量重算，大幅降低数据库写入压力。
抽取接口调用时机
以下时机均触发抽取接口：
|触发时机|说明|
|-|-|
|用户返回首页（onShow）|每次从其他页面/tab/后台回到首页时自动刷新|
|用户下拉刷新首页|整体页面刷新，置顶栏同步更新|
|用户刚看完广告入池后|入池成功后前端主动刷新一次，确保登场光环效果立即可见|


---
### 6.3 视角诡计实现
视角诡计是整个置顶系统的核心体验设计。其实现原理是：抽取接口接收当前用户标识作为入参，服务端在权重计算时执行归属分层，确保用户自己的问卷获得压倒性权重。前端仅需做展示层面的辅助处理。
前端区分"自己的问卷"与"他人问卷"
- 抽取接口返回的问卷列表中，每条问卷附带一个"是否为当前用户所有"的布尔标记字段。
- 前端根据此标记，对自己的问卷卡片应用差异化视觉样式（如边框微光、右上角"我的"角标、卡片底色微暖等）。视觉差异需克制，以"暗示这是我的"而非"强行高亮"为度。【动画效果再说】
- 此标记仅用于前端展示区分，不参与排序逻辑——排序已由服务端权重决定。
刷新时自己问卷的展示逻辑
- 服务端保证：因归属分层的权重区间设计，自己的问卷在任何一次抽取中，权重均碾压他人问卷。在5张卡片的加权随机采样中，自己的问卷被选中的概率极高（接近但不等同于必然）。
- 前端不强制固定位置：自己的问卷不锁定在第一位。每次抽取结果中，它可能出现在第1-3位的任何位置，偶尔甚至排到第4-5位。这种"几乎总在前面但不绝对钉死"的表现，比强制第一位更显真实。
- 前端辅助逻辑：在极少数情况下，若抽取结果中自己的问卷未被选中（归属分层的权重优势使其概率极低但非零），前端不做补偿插入。让这种"偶尔不在"自然发生，反而增强了系统的可信度。用户会想"刚才还在的，刷新一下又回来了"，这种动态感比永远死钉在第一位更有生命力。
登场光环期间的视觉特效
登场光环的本质是极高的权重值，而非服务端硬性干预。光环期间问卷权重被拉至极高值，加权随机采样下自然以极大概率出现在抽取结果中，"两次刷新内大概率在前三"是概率锚点描述，不做任何强制提位或替换操作。
服务端职责：
- 无需特殊处理。权重算法已保证光环期间权重极高，自然高概率选中。
- 返回结果中附带光环标记字段（`haloActive`），供前端做视觉特效。
前端职责：
- 完全按服务端返回的顺序渲染，不做任何二次排序。
- 检测光环标记，对对应卡片施加纯视觉特效（发光边框、登场角标等）。
- 特效作为纯视觉组件，异常时不影响核心展示，顶多特效不显示。
实现评估：
- 服务端无需新增提位/替换逻辑，比原方案更简洁。
- 光环随问卷15分钟到期自然终结，无需计数器、无需提前退场。
- 前端刷新动效统一使用卡片飞入飞出动画（见6.4节）。
---
### 6.4 视觉反馈【动画效果再说】
自己的问卷卡片样式
- 与其他卡片有细微视觉区分：如微弱的金色描边、卡片左上角或右上角一个轻量角标。
- 登场光环期间，该卡片可增加更明显的登场特效（如光晕扫过、短暂放大动画），光环退场后特效消失，回归常规"我的问卷"样式。
- 视觉设计原则：让用户一眼能认出"这是我的"，但不至于在5张卡片中显得突兀或喧宾夺主。
卡片刷新动效
- 5张卡片同步执行飞入飞出动画：旧卡片向上滑出并淡出，新卡片从下方滑入并淡入。
- 用户的问卷卡片（若在新结果中）在切换动画中保持位置不动或仅轻微缩放，强化"我的稳固"心理暗示。
- 动画时长控制在0.3-0.5秒，流畅不拖沓。
空状态与加载状态
- 置顶池无任何问卷时：展示占位引导卡片，文案引导用户"看广告，让你的问卷抢占C位"，点击跳转广告入口。
- 抽取接口响应延迟时：展示骨架屏或加载动画，避免白屏。抽取结果返回后平滑过渡。

### 7.2 即时档案
#### 7.2.1 触发时机

**服务端处理**

问卷生命周期结束时（实际 13 分钟，用户感知 15 分钟），由定时云函数主动触发处理：

1. 定时云函数检测到 `pin-pool` 中有 `expireAt < now` 的文档。
2. **同步生成**战绩单档案：将整条过期 `pin-pool` 文档作为 `pinDoc` 参数传入 `generateCareer(userId, pinDoc)`，`generateCareer` 从中读取 `surveyId`、`surveyTitle`、`senioritySnapshot`、`haloActive`、`isGreenChannel` 等字段用于数据生成
3. 同步更新用户记录中的未读标记：
   ```javascript
   // 注意：uniCloud 不兼容原生 MongoDB $push/$pull，使用 db.command 封装
   await db.collection('uni-id-users').doc(userId).update({
     'career.hasUnread': true,
     'career.unreadCareerIds': db.command.push(newCareerId)
   })
   ```
4. 同步将对应槽位状态更新为 `claimable`（待签收）。
5. 从 `pin-pool` 中删除该文档。

无需 `career-pending` 待处理队列，无需惰性消费。档案在问卷到期后 1 分钟内自动生成完毕。

**前端通知方式**

1. 用户进入问卷工具首页时，首页 `onShow` 生命周期调用云对象方法 `checkCareerStatus()`。
2. 云对象检查用户 `career.hasUnread` 是否为 true，若有则返回 `unreadCareerIds`（String[]）和对应的档案摘要信息（含荣誉称号、核心数据精简版）。
3. 前端检测到有未读档案时，遍历 `unreadCareerIds` 列表，逐一弹出档案弹窗（全屏弹窗或底部 ActionSheet）展示：
   - 弹窗标题："15分钟名气管理局"
   - 档案摘要：荣誉称号 + 核心数据精简版
   - 操作按钮：
     - **「签收」**（次按钮，灰底）→ 确认收到这份档案，关闭弹窗。不跳转任何页面，直接签收 + 释放槽位。
     - **「广播出去！」**（主按钮，深色底）→ 拉起微信分享面板（`<button open-type="share">`），同时签收 + 释放槽位。分享页面的文案/路径由 `onShareAppMessage` 读取标志位后返回。（分享页设计待补充）
   - 两个按钮均触发 `markCareerAsRead(careerId)` + 关闭弹窗，均不跳转档案详情页。
   - **多未读时**：当前档案关闭后自动弹出下一条，直至全部处理完毕
4. 用户点击「签收」或「广播出去！」后，前端调用云对象方法 `markCareerAsRead(careerId)`。后端使用 uniCloud 的 `db.command.pull` 原子移除该 ID：`db.collection('uni-id-users').doc(userId).update({ 'career.unreadCareerIds': db.command.pull(careerId) })`。移除后检查数组是否为空，若为空则置 `hasUnread = false`。此操作同时触发对应槽位释放（见下方"槽位释放机制"）。

**关键设计**：不走服务端主动推送。用户自然回流首页时弹窗，效果等价于"系统在用户面前弹出档案"。

**性能提示**：`onShow` 在微信小程序中触发频繁（从后台切回、从二级页返回等均触发），建议前端在本地缓存 `hasUnread` 状态做快速判断：`const cached = uni.getStorageSync('_hasUnreadCareer'); if (cached === false) return;`，仅当缓存为 `true` 或不存在时才调用 `checkCareerStatus()`。缓存刷新时机为用户关闭档案弹窗时。

**槽位释放机制（三路径）**：用户置顶到期后，槽位状态变为 `claimable`（待签收）。该槽位可通过以下三条路径恢复为 `idle`（闲置），先到先得：

1. **首页弹窗路径（已阅释放）**：用户进入首页时弹出档案弹窗，弹窗展示本身即视为"已阅"。用户点击「签收」或「广播出去！」后，前端调用云对象方法通知后端"已阅"，后端检查并置该槽位为闲置。用户无需进入历史页即可释放槽位。
2. **历史页槽位路径（签收释放）**：用户在历史档案页的槽位管理台中看到 `claimable` 状态的卡片，点击跳转档案详情页，查看完成后返回时槽位恢复闲置。
3. **新置顶自动回收路径（替代释放）**：用户未查看战绩单，但发起新的置顶请求时，系统在入池前置处理或 queueToPool 的槽位检查阶段发现 `claimable` 槽位，**自动将其回收为 `idle`** 后供新问卷使用。战绩记录不受影响——pin-expiry 已在过期时写入 `career-records`，用户随时可在历史档案页查阅。

**竞争处理**：三路释放由后端做原子化处理。云对象方法使用条件更新 `updateOne({ status: 'claimable' }, { status: 'idle' })`，确保多条路径不会同时释放同一个槽位。重复操作时第二条请求会被条件匹配挡住，不做任何修改。

**切后台/杀进程边界**：弹窗展示后用户未操作直接切后台或杀进程时，后端未收到已阅通知，`hasUnread` 保持 true，槽位仍为 `claimable`。下次 onShow 时 `checkCareerStatus()` 会再次弹出同一档案。**此行为是允许的**——弹窗是幂等的，同一档案的弹窗不会导致重复生成数据。用户无论是否操作，最终都会在下次回流时看到档案，不影响系统状态。
#### 7.2.1.x careerNumber 生成规则
- `careerNumber` = `pinDoc.senioritySnapshot + 1`
- 逻辑：`senioritySnapshot` 记录的是入池瞬间用户的 `exposureCount` 快照值（当时尚未 +1），是"入池前的资历"。+1 即得到"这是用户第几次被认证"。**必须使用 snapshot 而非实时 `exposureCount`**，原因：用户可能有多条问卷同时在池中流转，实时 `exposureCount` 会在每次新入池时递增，导致先入池的档案拿到错误的 careerNumber（被后续入池操作推高）
- `careerNumber === 1` 即为"首次认证"，对应档案子标签上的"首秀"角标（见 §7.3.6）

#### 7.2.2 数据生成算法
所有数据均基于置顶期间的实际表现，经放大和修饰后呈现。生成的每个数值都需经过一致性校验，避免逻辑错误。档案中的数值被替换为更文绉绉的表述（见文案映射表）。
文案映射表
|原术语|档案用词|
|-|-|
|曝光量|驻足注视|
|点击量|好奇打开|
|收藏量|决定存档|
|趣味头衔|荣誉称号|
|一句话评价|档案附注（系统点评）|
|数据暴击|破格授予（罕见荣誉）|

驻足注视（原曝光量）
- 基础值：取问卷在池期间，每个抽取周期被呈现在他人屏幕上的理论次数。可由活跃用户数 × 该问卷的全局权重占比估算。
  - **MVP 开发期注意**："活跃用户数"在项目中没有现成的统计接口可获取。建议开发期先固定一个模拟基数（如 1000），待上线后获取真实用户量数据后再替换为实际值。
- 浮动系数：在基础值上乘以一个浮动系数，使数字更好看。系数值在全局参数中定义，预设范围如1.5～3.0。
- 反向补偿融入：曝光资历越浅的用户，浮动系数取上限的概率越大。
- 零头修饰：将最终数值加上或减去一个微小随机数，使结果有零有整（如2847而非2800），增强真实感。
好奇打开（原点击量）
- 换算逻辑：好奇打开 = 驻足注视 × 点开率。
- 点开率：在预设范围内随机浮动（如5%～15%）。反向补偿可暗中提高新人的点开率浮动下限。
- 修饰：同样进行零头修饰。
决定存档（原收藏量）
- 换算逻辑：决定存档 = 好奇打开 × 存档转化率。
- 存档转化率：预设范围（如5%～20%），反向补偿影响浮动。
- 保底：不设强制保底，可低至 0。追求真实仿真，不做"假装有人收藏"的修饰。
数据暴击（破格授予）
- 触发概率：每次生成档案时，以一定概率（建议10%～20%）触发。
- 暴击效果：选中一个数据维度（优先驻足注视，其次好奇打开），将该数值乘以暴击倍数（如1.5～2倍）。
- 联动：暴击触发后，荣誉称号和档案附注需对应升级。荣誉称号变为更夸张的版本，附注包含"本局特此破格授予"等措辞。
- 注意事项：暴击后仍需通过一致性校验。
数据一致性校验
生成全部数值后，强制检查：
- 好奇打开 ≤ 驻足注视。
- 决定存档 ≤ 好奇打开。
- 所有数值为正整数。
- 无逻辑矛盾。
    若校验失败，回退调整参数重新生成，或直接向下修正异常数值。
#### 7.2.3 荣誉称号与档案附注
荣誉称号（原头衔）匹配规则
- 系统预置一个荣誉称号池，每个称号与数据特征挂钩。
- 匹配逻辑：根据本次档案的驻足注视、好奇打开、决定存档的相对高低组合，映射到一个称号。
- 规则表结构示意（具体称号和阈值在全局参数/配置表中定义）：
    - 驻足注视极高而点开率低 → "人群中的灯塔"（被很多人看到但少有人点开）
    - 点开率高 → "万众瞩目者"
    - 存档率高 → "档案馆宠儿"
    - 驻足注视较低但点开率极高 → "冷门黑马"
    - 数据暴击触发 → 专属暴击称号（如"破格流量获得者"）
    - 新人首秀 → 可包含"首次认证"类特殊称号
- 反向补偿融入：新人等弱势用户，匹配到稀有或高价值称号的概率暗中提高。
档案附注（原评价语料库）设计
- 档案附注由系统从语料库中抽取并组合生成，以"本局鉴定"或"系统点评"的口吻呈现。
- 语料库设计原则：
    - 按场景分类（如驻足型、点开型、存档型、暴击型、时段型、新手首秀型）。
    - 每个场景包含多条候选句子，随机或轮选使用。
    - 支持变量插入，如时段、数值（"数据表明：该问卷在深夜23点至凌晨1点之间的社交价值达到峰值"）。
    - 所有附注必须保持档案的公文语气，冷峻中带着荒诞，无负面暗示。
    - 档案末尾统一附上免责声明："本档案由 15分钟名气管理局 自动生成。数据在真实基础上做了微量艺术加工。如有疑问，请勿联系，因为我们不存在。"
- 【待讨论】语料库规模与存储方式：初期建议预设30-50条覆盖主要场景，存储为配置文件或数据库表均可，便于运营随时补充。后续若量级增大，可迁移至独立内容管理系统。
#### 7.2.4 分享长图
生成方案
- 采用客户端 Canvas 实时绘制。理由：团队已有 Canvas 2D 经验（项目结果页已使用 Canvas 绘制雷达图），长图内容结构固定，绘制逻辑简单。服务端预渲染会增加云函数开销和运维复杂度。
长图视觉风格
- 模拟"终端打印出来的红头文件"的感觉：白底或暖白底，黑色正文，红色公章，等宽字体标题。
- 纸质纹理/轻微做旧感，像一份真的档案被扫描了。
- 与候场区黑底绿字的终端界面形成视觉反差：候场是"屏幕里的监控系统"，档案是"从屏幕里吐出来的纸质文件"。
长图布局与必要字段
长图采用竖版公文档案式布局，自上而下包含：
1. 机构抬头："15分钟名气管理局 · 临时名人档案"（红头文件风格）
2. 档案编号（`archiveNumber`）：ZW-年份-序号（如 ZW-2026-01847），展示用字符串编码。序号在 `generateCareer` 中生成并写入 `career-records`，由服务端计数器集合 `counter` 中的 `careerArchiveSeq` 字段提供**全局自增值**。**注意 uniCloud 没有 `findOneAndUpdate` API**，实现方式：先用 `db.collection('counter').doc('careerArchiveSeq').update({ seq: db.command.inc(1) })` 自增，再 `get()` 读取新值拼装 `archiveNumber`。这两步非原子操作，但对于展示用编码（非业务关键值）可接受。需在阶段零新建 `counter` 集合并初始化 `{ _id: 'careerArchiveSeq', seq: 0 }`。与 `careerNumber`（用户维度的第几条档案，整数，用于判断首秀等逻辑）分离——`careerNumber === 1` 即表示"首次认证"。
3. 发证日期与有效期："发证日期：2026年5月16日 23:14" / "有效期：本档案自签发之日起永久有效"
4. 档案主体信息：用户昵称、本次身份（如"纯正淀粉肠"）、身份照片位（emoji展示位）
5. 鉴定正文："经本局鉴定，上述人员在 [时间段] 期间，因发布问卷《[问卷标题]》而获得以下注视："
6. 三项核心数据："驻足注视 XXXX 人次 / 好奇打开 XXXX 人次 / 决定存档 XX 人次"
7. 荣誉称号："基于以上数据，本局授予以下荣誉：🏅 [荣誉称号]"
8. 授予理由（简短一句话）
9. 档案附注（系统点评）
10. 底部公章："15分钟名气管理局 档案专用"
11. 小程序码 + 引导文案："扫码生成你的15分钟名人档案"
    所有元素需留出安全边距，适配朋友圈分享比例。

### 7.3 历史档案页（含三槽位管理台）
#### 7.3.1 概述
历史档案页是用户所有"被认证"记录的归档之处，同时也兼任**置顶系统的实时控制台**。

页面上半部分为三槽位管理台，展示当前正在流转中的问卷状态（候场/置顶/待签收）；下半部分为历史档案手风琴列表，展示所有已归档的战绩记录。

**核心约束**：用户同时最多 **3 条问卷** 可在置顶系统中流转（覆盖候场→置顶→待签收全生命周期）。三条满时不可发起新的置顶，需等其中一条走完腾出空位。

#### 7.3.2 上半部分：三槽位管理台
固定展示 3 个状态卡片（槽位），各自独立运行完整生命周期。每个槽位的状态流转和用户交互如下：

| 槽位状态 | 卡片展示内容 | 用户交互 | 说明 |
|---------|------------|---------|------|
| `idle`（闲置） | 文案"闲置"，灰态 | 不可点击 | 空槽位，等待新的置顶任务进入 |
| `queuing`（候场中） | "候场" + 问卷标题简称 | 点击弹出底部半屏面板 | 面板展示黑底绿字终端日志 + 加速按钮 |
| `active`（置顶中） | "置顶中" + 问卷标题 + 剩余倒计时 | 点击弹出半屏面板 | 面板展示置顶状态、剩余时间、实时数据预览 |
| `claimable`（待签收） | "查看战绩单" + 问卷标题 | 点击跳转档案详情页（`career-detail`），可查看完整数据并长图分享 | 释放方式有三种：① 首页弹窗点击「签收」或「广播出去！」→ 已阅释放；② 本槽位点击跳转 `career-detail.vue`，返回后槽位闲置；③ 发起新置顶时自动回收→槽位闲置。三路后端原子化处理，不冲突。战绩记录不受影响 |

**槽位占用规则**：
- 用户发起置顶时，系统从槽位1到槽位3依次查找第一个空闲槽位，填入新的问卷
- 三个槽位全部占满时，系统拒绝新的置顶请求，提示"你的三个置顶名额已满，请等待其中一条完成"
- 问卷生命周期结束（待签收状态被签收或被自动回收）→ 该槽位恢复闲置 → 可接受新的置顶任务
- 槽位定位方式：
  - **queuing 状态**：`pinId` 为 `null`（pin-pool 文档尚未创建）。直接通过 `career.slots[i].queueId === queueId` 匹配定位（唯一，避免同一用户对同一问卷多次置顶时 surveyId 重复的歧义）
  - **active/claimable 状态**：`pinId` 已写入（入池时设置），通过 `career.slots[i].pinId === doc._id` 遍历匹配定位（如 `generateCareer` 处理过期文档后更新槽位状态）。同一用户的 `pinId` 在数组中是唯一的，不会匹配到多个槽位

**视觉风格**：
- 三个槽位卡片横向排列，位于页面顶部固定区域
- 历史手风琴列表滚到时，槽位区保持在页面顶部（fixed 或 sticky）
- 纯功能Mock阶段使用原生组件默认样式，仅做布局区分

#### 7.3.3 下半部分：历史档案列表（手风琴结构）
（以下内容与原设计一致，未改动）

以手风琴结构组织，以问卷标题为主标签，每次置顶产生的档案为子标签。

#### 7.3.4 页面视觉风格
延续名气管理局的公文档案美学，但偏向"档案室查阅"的体验：
- 整体色调沉稳，暖白底，深色文字。
- 列表项模拟档案盒标签或卷宗封面的样式。
- 主标签展示问卷标题 + 累计置顶次数，像档案盒脊背上的标签。
- 子标签展示每次档案的签发日期 + 荣誉称号 + 核心数据精简版，像卷宗目录。

#### 7.3.5 组织结构
- 主标签：被置顶过至少一次的问卷标题。显示累计置顶次数，以及最近一次档案的精简摘要（如"最近档案：驻足注视 2847 人次 · 含梗量宗师"）。
- 子标签：该问卷的每一次置顶档案，按时间倒序排列。每条子标签显示签发日期、荣誉称号、驻足注视数。点击进入该次完整档案详情页。
- 同一时间只展开一个主标签。

#### 7.3.6 特殊标记
- 首秀标记：用户第一次置顶的档案子标签上，自动带一个微弱的"首秀"角标或金色小圆点。对应叙事："首次认证档案"。
- 暴击高亮：触发了数据暴击的档案子标签，底色微亮或标题加粗，附"破格授予"标注。
- 槽位关联标记（可选）：每个历史档案子标签可标注"第N槽位"识别，便于用户回忆是哪次置顶走的是哪个槽位。

#### 7.3.7 置顶生涯综述卡片（列表顶部，固定）
以"名气管理局档案室"的口吻呈现用户的整体数据：
- 本档案室共收录置顶记录：XX 次
- 累计驻足注视：XX 人次
- 累计好奇打开：XX 人次
- 累计决定存档：XX 人次
- 获得最多荣誉称号类型：XX（如"你是个万众瞩目者，共获得 8 次人气类称号"）
- 档案室一句话综述："你的问卷累计被世界注视过 XX 次，相当于一场小型演唱会的观众人数。本局对此表示认可。"

#### 7.3.8 空状态
用户从未置顶过任何问卷时：
- 上半部分三槽位全部显示"闲置"
- 下半部分显示："本档案室暂无你的记录。看个广告，让你的问卷被世界看见，生成第一份名人档案。" 点击引导至广告入口。

### 8.2 可调常量分类
所有参数按功能域归类如下：
时间与周期类

反作弊与风控类

### 8.4 广告观看流程（客户端驱动）

微信小程序激励视频广告**不存在服务端回调接口**。广告播放完毕后，通过客户端事件 `wx.createRewardedVideoAd().onRewarded()` 触发，前端确认后调用云对象方法执行业务逻辑。以下为完整流程。

广告组件声明
在小程序页面中声明激励视频广告组件：
```javascript
// 前端代码示例
let videoAd = null
if (wx.createRewardedVideoAd) {
  videoAd = wx.createRewardedVideoAd({ adUnitId: 'xxxx' })
  videoAd.onLoad(() => { /* 广告加载完成 */ })
  videoAd.onError(err => { /* 广告加载失败，降级处理 */ })
  videoAd.onClose(res => {
    // res.isEnded 表示广告是否在完整播放后关闭
    if (res && res.isEnded) {
      // 用户完整看完广告，调云对象执行业务
      this._onAdRewarded(sceneCode, bizData)
    } else {
      // 用户提前关闭，不给奖励
      uni.showToast({ title: '看完广告才能获得奖励哦', icon: 'none' })
    }
  })
}
```

业务处理入口
前端确认广告完整播放后，调用云对象方法，**不是调用 HTTP 端点**：
```javascript
async _onAdRewarded(sceneCode, bizData) {
  const pinSystem = uniCloud.importObject('pin-system')
  const result = await pinSystem.handleAdReward({
    scene: sceneCode,          // "first_pin" | "queue_accel"
    surveyId: bizData.surveyId,
    queueId: bizData.queueId,  // 候场区加速场景必传，指定加速哪条候场记录
    // 注意：无广告平台凭证可传，微信不提供此能力
  })
  // 根据 result.action 指引后续 UI 行为
}
```

云对象入参
|字段|类型|说明|
|-|-|-|
|`scene`|String|业务场景编码：`"first_pin"` / `"queue_accel"`。**常量说明**：`"first_pin"` 含义为"调用入池接口"，不限制用户的置顶次数（第 N 次置顶同样走此 scene），非字面意义上的"第一次置顶"。`"queue_accel"` 含义为"候场区加速"。两个场景值由 `pin-system` 云对象管理，前端和后端代码统一使用此字符串常量，大小写必须完全一致|
|`surveyId`|String|正在操作的问卷标识|
|`queueId`|String|可选，候场区加速场景传入候场记录标识|

云对象处理流程
1. 校验用户标识（从 uni-id 上下文的 `this.uid` 获取，无需前端传入。**与项目现有模式一致**——参考 `survey` 云对象的 `_before` 实现，所有方法入参中不再包含 `userId` 参数）
2. 查询用户当前状态（冷却时间、每日置顶次数、候场状态等）
3. 根据 scene 路由至对应业务逻辑：
   - `first_pin` → 调用置顶池入池逻辑（绿色通道判断 → 池满线判断 → 入池或候场区）
   - `queue_accel` → 调用候场区加速逻辑（跳跃进度 → 入池或继续候场）
4. 记录广告观看日志（用于数据分析）
5. 返回结果，包含后续动作指示

返回结构
- `code`：状态码（`success` / `fail` / `retry` 等）
- `message`：结果描述（用户可读提示，如"置顶成功！""已加速，还差一步即可登场"）
- `action`：前端据此决定 UI 行为（`"refresh"` 刷新置顶栏 / `"enter_queue"` 进入候场区 / `"none"` 无需操作）
- `greenChannel`：Boolean，是否触发了绿色通道（`action === "refresh"` 且 `greenChannel === true` 时前端展示闪屏动画）。仅 `scene === "first_pin"` 时有意义
- `queueData`：Object，可选。`action === "enter_queue"` 时返回候场区初始状态：
  - `queueId`：候场记录 _id
  - `currentPhase`：初始处理阶段
  - `logLines`：完整日志流（文本数组，每条含 `text`、`interval`、`prefix`），前端每 3s 轮询获取已到期行
  - `visibleLines`：初始已到期的行（供前端立即渲染）
- `pinData`：Object，可选。`action === "refresh"` 时返回，包含最新置顶栏数据 + 登场光环信息

### 8.5 广告观看次数的防刷与风控策略
> 【待讨论】 由于小程序广告收入依赖真实观看，防刷是商业健康的关键。目前尚未深入讨论具体策略，仅列出设计要点供后续专项讨论：
需要防范的风险
- 脚本自动播放广告并伪造回调
- 用户使用插件或外挂快速批量完成广告观看
- 同一用户短时间内异常高频置顶（非正常娱乐需求）
- 通过切换账号或设备伪造新用户身份套取绿色通道福利
可供选择的技术手段
- 客户端时长校验：广告关闭时检查 onClose(res) 的 res.isEnded 字段，仅当完整播放后才视为有效（微信 SDK 原生能力，无法伪造）
- 服务端请求频率限制：按用户/设备/IP 限制短时间内的提交次数，防止批量自动化调用
- 广告观看最短时长兜底（服务端侧校验）：记录请求的客户端时间戳，调用间隔低于阈值（如少于 15 秒）则视为无效
- 广告观看最短时长限制（客户端侧计时，低于阈值视为无效）
- 单用户每日置顶次数软帽（超过后强制冷却或降低权重，而非硬拒绝）
- 基于行为序列的异常检测（如观看间隔、操作轨迹）
- 设备指纹与账号关联分析，识别批量注册
建议
此部分需与广告平台技术对接人、后端开发及运营共同制定详细规则。初期可先上线基础频率限制，上线后根据数据逐步完善。

### 8.6 广告环节已知风险（待广告接入后处理）

以下风险在广告实装之前已识别，记录于此供接入时逐项解决。

**风险一：`isEnded` 不可靠**

微信激励视频广告没有独立的 `onReward` 回调，只有一个 `onClose`。是否完整观看依赖 `res.isEnded` 字段判断。该字段在某些场景下不准确——用户快到结尾时关闭但 `isEnded` 仍为 `true`，或完整看完但 `isEnded` 为 `false`。

**风险二：`offLoad` 解绑写法有 bug**

`common/ad-utils.js` 中的 10 秒超时逻辑调用了 `videoAd.offLoad()` / `videoAd.offError()` / `videoAd.offClose()` 但不传回调函数引用。微信的 `offLoad(callback)` 必须传入原来注册的那个回调函数才能正确解绑，不传等同于没解绑。后果：10 秒超时后弹 toast "广告加载超时"，但如果广告在 15 秒后加载成功，`onLoad` 仍然触发 → `videoAd.show()` 在后台播放 → `onClose` 触发 → `callHandleAdReward` 被调用。用户没看广告但被判定为完成观看。

**风险三：广告实例全局复用冲突**

`ad-utils.js` 用模块级变量 `let videoAd = null` 缓存实例，但 `pin-terminal-entry.vue` 和 `queue-terminal.vue` 的注释代码是各自 `wx.createRewardedVideoAd()` 创建新实例。如果统一使用缓存方案，需确保一个实例正在播放时不会收到重复的 `show()` 调用（微信会报错）。如果各自创建新实例，需确保旧实例被正确销毁。多个入口同时触发时，第二个入口可能静默失败。

**风险四：`onClose` → 云函数调用非原子**

广告 `onClose(isEnded: true)` 触发后，前端调用 `callHandleAdReward` → 云函数 `handleAdReward`。中间存在网络断连/超时导致 `catch` 返回 `null`、用户切后台导致 uni-app 异步请求被挂起等。目前 `catch` 里只弹 toast "网络异常，请重试"，没有重试机制。后果：广告费赚了（广告被完整观看），用户什么都得不到。需要加入至少一次自动重试。

**风险五：入池时的 TOCTOU 竞态**

去重检查前移到广告之前后，仍存在理论上的竞态窗口：前端检查返回"不在池中" → 用户看 30 秒广告 → 调用入池。30 秒内同一问卷可能被另一个设备操作入池。概率极低，由后端入池时的最终去重检查兜底。

### 10.2 核心架构变化

```
旧架构（阶段跳跃）：
  时间流逝 → calcPhaseImpl（min边界）→ 阶段索引 → LOG_TEMPLATES[阶段]
  加速 → accelJumpMap * acceleratedCount → 跳N个阶段

新架构（文本驱动）：
  入候场 → buildLogStream(exposureCount) → 完整 logLines 写入DB
  轮询 → calcVisibleSlots(logLines, enterAt, effectiveOffset, now) → visibleLines
  加速 → effectiveOffset += totalDuration * 0.4
```

### 12.3 pin-topbar uid 存储字段修复

**Bug**：pin-topbar 从 `uni.getStorageSync('uni-id-pages-userInfo')` 读 `info?.uid`，但 uni-id-pages 的 store.js 存入的字段是 `_id`（`setUserInfo({_id})`），导致 `currentUid` 永远为空，pin-topbar 静默跳过所有 refresh。

**修复**：

### 12.5 入池去重检查

**背景**：同一问卷在置顶流程中（置顶池或候场区）没有任何拦截，用户可重复调用 `handleAdReward`，导致同一条问卷在池中产生多条重复记录。

**改动**：`enterPoolImpl` 方法中，在槽位检查之前新增去重检查（step 0）：

| 检查维度 | 查询条件 | 拦截后的 errCode |
|---------|---------|-----------------|
| 置顶池 | `pin-pool` 中 `surveyId` 匹配 + `expireAt > now` | `ALREADY_IN_POOL` |
| 候场区 | `survey-queue` 中 `surveyId` 匹配 | `ALREADY_IN_QUEUE` |

**设计要点**：
- 去重检查在所有其他判断（绿色通道、池满线、槽位）之前执行，因为重复入池在任何情况下都不应该被允许
- `pin-pool` 检查带上 `expireAt > now` 条件：已过期的记录不算「在流程中」，允许再入
- `survey-queue` 不需要 `expireAt` 判断：候场区记录由 `pin-expiry` 兜底清理（35 分钟超时），活跃记录即代表「在排队」
- 前端零改动：三个入口组件已统一处理 `res.errCode !== 0` → `uni.showToast({ title: res.errMsg })`，云函数返回错误码即可自动弹窗拦截

### 12.6 用户操作流程：去重检查前移至广告之前

**背景**：原设计为「看广告 → 去重检查 → 入池」。如果用户在 30 秒广告期间同一问卷被另一设备入池，去重检查会拦截，用户白看广告。

**改动**：
- §2.1 流程图：「去重检查」与「观看激励视频广告」位置互换，去重检查现在在广告播放之前执行
- §4.5 入池逻辑：「完整判断流程」描述从"用户看完广告后"改为"用户点击'看广告置顶'后"，去重检查标注为"广告播放之前执行"
