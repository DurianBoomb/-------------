# 问卷置顶系统二期——助力功能

## 1. 概述

二期在现有置顶系统基础上，为问卷引入"身份"概念，实现问卷身份的差异化处理：官方问卷不可被置顶、用户对他人问卷的置顶操作称为"助力推广"（而非"置顶"）。

### 核心改动一览

| 改动项 | 说明 |
|--------|------|
| 问卷身份判断 | 通过 `creatorId` 是否为 `null` 区分官方问卷与用户问卷 |
| 禁止官方问卷置顶 | 前端隐藏按钮 + 后端拒绝，双重确认 |
| 助力推广 | 用户置顶他人问卷时，叙事层面称为"助力推广"，数据库记录 `pinType` |
| surveyAuthor 修复 | 助力场景下取问卷真实创建者昵称，而非推广者昵称 |
| 助力版战绩单 | 结构与普通战绩单相同，文案不同 |
| 归属分层权重 | 无需修改，天然适配助力场景 |

---

## 2. 问卷身份体系

### 2.1 身份划分

问卷分为三种身份，由 `surveys` 集合已有字段 `creatorId` 判定：

| 身份 | 判定条件 | 举例 |
|------|---------|------|
| **官方问卷** | `creatorId === null` 或 `creatorId === undefined` | 小程序开发者预置的启动问卷 |
| **自己的问卷** | `creatorId === currentUserId` | 用户自己创建的问卷 |
| **他人的问卷** | `creatorId !== currentUserId` | 其他用户创建的问卷 |

### 2.2 设计决策

**不新增 `isOfficial` 字段。** 理由：

- `creatorId === null` 本身语义等价于"这是系统自带的，不是任何人创建的"
- 加独立字段会导致两个字段之间存在不一致风险（如 `creatorId = "张三"` 但 `isOfficial = true`），需额外校验约束
- **零迁移成本**：已有官方问卷的 `creatorId` 均为空，已有用户问卷的 `creatorId` 均有值，无需清库、无需改已有数据

## 3. 禁止置顶官方问卷

### 3.1 双重确认拦截策略

| 层次 | 拦截方式 | 涉及文件 |
|------|---------|---------|
| **前端 UI** | 获取 `survey.creatorId` 后判断，若为空则不显示置顶入口 | `result.vue`、`my-surveys.vue` |
| **后端云对象** | `enterPoolImpl()` 第一行检查 `survey.creatorId`，为空则抛出错误 | `pin-system/index.obj.js` |

### 3.2 前端 UI 层

- 在结果页（`result.vue`）和我的问卷页（`my-surveys.vue`）中，渲染置顶按钮前判断 `survey.creatorId`：
  - `!creatorId`（即 `creatorId === null` 或 `undefined`）→ **不显示按钮**（官方问卷不可置顶）
  - `creatorId === currentUserId` → 显示"看广告置顶"
  - `creatorId !== currentUserId` → 显示"助力推广"

### 3.3 后端云对象层

在 `enterPoolImpl()` （或 `handleAdReward` 路由至 `first_pin` 后的核心逻辑）最顶部加入防护：

```javascript
// 在查询问卷信息后
if (!survey.creatorId) {
  throw new Error('官方问卷不可置顶')
}
```

## 4. 助力推广功能

### 4.1 数据库改动

#### `pin-pool` 集合新增字段

| 新字段 | 类型 | 说明 |
|--------|------|------|
| `pinType` | String | `"self"`（自己置顶自己）或 `"promote"`（助力推广他人） |
| `pinnerId` | String | 实际执行入池操作的用户 ID。对于 `"self"` 类型，等于 `userId` |
| `surveyCreatorId` | String | 问卷原始创建者 ID。用于所有权判定和权重归属。旧数据无此字段时回退到 `userId` |

> `surveyCreatorId` 的引入是为了解决权重归属问题：原代码用 `userId`（操作者）判定所有权，但推广场景下操作者不是问卷所有者，导致权重计算错误。新增 `surveyCreatorId` 后，所有权判定切换为 `(pinDoc.surveyCreatorId || pinDoc.userId) === currentUserId`。

#### `career-records` 集合新增字段

| 新字段 | 类型 | 说明 |
|--------|------|------|
| `pinType` | String | 同上，区分战绩单类型："自己置顶" or "助力推广" |

战绩单结构不变，仅文案因 `pinType` 不同而变化（详见 §4.4）。

#### `survey-queue` 集合新增字段

| 新字段 | 类型 | 说明 |
|--------|------|------|
| `pinType` | String | 同 `pin-pool`，候场记录携带入池时的 `pinType`，供候场状态返回使用 |
| `pinnerId` | String | 实际执行入池操作的用户 ID |

### 4.2 surveyAuthor 修复（Bug Fix）

**现有问题：**

`pin-system/index.obj.js` 中入池时取 `surveyAuthor` 的代码：

```javascript
const surveyAuthor = user.nickname || ''  // user = 当前执行操作的用户
```

这个逻辑在"自己置顶自己"时正确，但在**助力推广**场景下错误——置顶栏卡片会显示推广者的昵称，看起来像推广者冒领了问卷。

**修复方案：**

入池时，如果 `pinType === "promote"`，直接复用入口处已查到的 `survey` 对象里的 `creatorId`（无需再查一次 `surveys`），再通过 `creatorId` 获取该用户的 `nickname` 作为 `surveyAuthor`：

```javascript
let surveyAuthor
if (pinType === 'promote') {
  // creatorId 从入口处已查到的 survey 对象中直接取，无需重复查 surveys
  const creatorId = survey.creatorId
  const { data: creatorUser } = await db.collection('uni-id-users').doc(creatorId).get()
  surveyAuthor = creatorUser.nickname || ''
} else {
  surveyAuthor = user.nickname || ''
}
```

### 4.3 归属分层权重——需要修改

原设计文档声称"无需修改"，但实际上需要修改。原因：

现有代码中，所有权判定使用 `pinDoc.userId === currentUserId`。推广场景下，`userId` 记录的是**推广者**（执行入池操作的人），而非问卷所有者。直接使用 `userId` 会导致：

- B 的问卷被 A 推广 → 池中记录的 `userId = A`（推广者）
- B 看自己的首页 → `userId(A) !== B` → 被判定为"他人问卷"，B 无法获得自己的高权重区间
- **这是错误的**——B 应该看到自己的问卷获得高权重

**实际修改**：

所有权判定从 `pinDoc.userId` 切换为 `pinDoc.surveyCreatorId`（新字段），旧数据兼容回退到 `userId`：

```javascript
// 修改前
if (pinDoc.userId === currentUserId) { ... }

// 修改后
if ((pinDoc.surveyCreatorId || pinDoc.userId) === currentUserId) { ... }
```

涉及三处：
| 位置 | 改动 |
|------|------|
| `calculateWeightImpl` | 所有权判定切换 |
| `drawImpl` 中的 `isOwn` 判定 | `(p.surveyCreatorId \|\| p.userId) === uid` |
| `recalcOwnWeights` 查询条件 | 使用 `$or: [{ surveyCreatorId: uid }, { userId: uid, surveyCreatorId: { $exists: false } }]` |

适配后的权重表现：

| 场景 | 权重表现 |
|------|---------|
| **B 看自己首页** → B 的问卷被 A 推广 | `surveyCreatorId=B === uid=B` → 自己高权重区间 → **合理** |
| **A 看自己首页** → A 推广了 B 的问卷 | `surveyCreatorId=B !== uid=A` → 他人低权重区间 + 反向补偿 → **合理** |

### 4.4 叙事层改动

#### 按钮文案

| 场景 | 当前文案 | 改为 |
|------|---------|------|
| 自己的问卷 | "看广告置顶" | 不变 |

### 5.1 入池位置一致性

二期有三个入池点，均做了同样的改动链：

| 入池点 | 触发方式 | 文件 |
|--------|---------|------|
| `enterPoolImpl` | 点击"看广告置顶"或"助力推广"后 | `pin-system/index.obj.js` |
| `queueToPoolImpl` | 候场区自然完成或第三次加速触发 | `pin-system/index.obj.js` |
| `inlineQueueToPool` | 定时云函数超时兜底自动入池 | `pin-expiry/index.js` |

三个入池点均执行：**读取 `creatorId` → 判定 `pinType` → 修复 `surveyAuthor` → 写入 `pinType/pinnerId/surveyCreatorId`**。

## 6. 边界情况说明

| 场景 | 处理方式 |
|------|---------|
| 用户对自己问卷点击"看广告置顶" | `pinType = "self"`，走现有逻辑 |
| 用户对他人问卷点击"助力推广" | `pinType = "promote"`，`pinnerId` 记录推广者，`surveyAuthor` 取问卷所有者昵称 |
| 用户尝试置顶官方问卷 | 前端不显示按钮，后端 `enterPoolImpl` 拒绝，双层防护 |
| 推广者和问卷所有者为同一人（正常不应出现） | 前端按钮文案按 `creatorId === currentUserId` 判断，走"置顶"而非"推广" |
| 推广战绩单被分享 | 战绩单内容不变，文案按 `pinType` 切换，底部引导文案不变 |
| 已有的 `pin-pool` 数据 | 不迁移。旧文档没有 `pinType`/`pinnerId`/`surveyCreatorId`，代码中按 `undefined` 处理，视为 `"self"` 类型兼容。所有权判定回退到 `userId` |
| 已有的 `career-records` 数据 | 同上，无 `pinType` → 前端不显示"推广"标签 |
| 被推广的问卷在池中，所有者查看首页 | `surveyCreatorId === uid` → `isMine = true`，自己高权重区间 |
| 被推广的问卷在池中，推广者查看首页 | `surveyCreatorId !== uid` → `isMine = false`，他人低权重区间 |
| promote 场景 + 问卷创建者已注销 | `surveyAuthor = ''`，置顶栏卡片显示"匿名" |

## 7. pinData 返回扩展

`enterPoolImpl` 和 `queueToPoolImpl` 返回的 `pinData` 对象在二期中原有字段（`_id`/`surveyId`/`surveyTitle`/`expireAt`/`haloActive`）基础上，新增以下字段供前端和测试页使用：

| 新增字段 | 说明 |
|---------|------|
| `pinType` | `"self"` 或 `"promote"` |
| `pinnerId` | 实际执行入池操作的用户 ID |
| `surveyCreatorId` | 问卷创建者 ID |
| `surveyAuthor` | 问卷创建者昵称 |

```javascript
// 修改前
pinData: { _id, surveyId, surveyTitle, expireAt, haloActive: true }

// 修改后
pinData: { _id, surveyId, surveyTitle, surveyAuthor, expireAt, haloActive: true, pinType, pinnerId, surveyCreatorId }
```
