# 问卷置顶系统二期——助力功能

## 1. 概述

二期在现有置顶系统基础上，为问卷引入"身份"概念，实现问卷身份的差异化处理：官方问卷不可被置顶、用户对他人问卷的置顶操作称为"助力推广"（而非"置顶"）。

### 核心改动一览

| 改动项 | 说明 |
|--------|------|
| 问卷身份判断 | 通过 `creatorId` 是否为 `null` 区分官方问卷与用户问卷 |
| 禁止官方问卷置顶 | 前端隐藏按钮 + 后端拒绝，双重确认 |
| 助力推广 | 用户置顶他人问卷时，叙事层面称为"助力推广"，数据库记录 `pinType` |
| surveyAuthor 修复 | 助力场景下取问卷真实创建者昵称，而非推广者昵称 |
| 助力版战绩单 | 结构与普通战绩单相同，文案不同 |
| 归属分层权重 | 无需修改，天然适配助力场景 |

---

## 2. 问卷身份体系

### 2.1 身份划分

问卷分为三种身份，由 `surveys` 集合已有字段 `creatorId` 判定：

| 身份 | 判定条件 | 举例 |
|------|---------|------|
| **官方问卷** | `creatorId === null` 或 `creatorId === undefined` | 小程序开发者预置的启动问卷 |
| **自己的问卷** | `creatorId === currentUserId` | 用户自己创建的问卷 |
| **他人的问卷** | `creatorId !== currentUserId` | 其他用户创建的问卷 |

### 2.2 设计决策

**不新增 `isOfficial` 字段。** 理由：

- `creatorId === null` 本身语义等价于"这是系统自带的，不是任何人创建的"
- 加独立字段会导致两个字段之间存在不一致风险（如 `creatorId = "张三"` 但 `isOfficial = true`），需额外校验约束
- **零迁移成本**：已有官方问卷的 `creatorId` 均为空，已有用户问卷的 `creatorId` 均有值，无需清库、无需改已有数据

---

## 3. 禁止置顶官方问卷

### 3.1 双重确认拦截策略

| 层次 | 拦截方式 | 涉及文件 |
|------|---------|---------|
| **前端 UI** | 获取 `survey.creatorId` 后判断，若为空则不显示置顶入口 | `result.vue`、`my-surveys.vue` |
| **后端云对象** | `enterPoolImpl()` 第一行检查 `survey.creatorId`，为空则抛出错误 | `pin-system/index.obj.js` |

### 3.2 前端 UI 层

- 在结果页（`result.vue`）和我的问卷页（`my-surveys.vue`）中，渲染置顶按钮前判断 `survey.creatorId`：
  - `!creatorId`（即 `creatorId === null` 或 `undefined`）→ **不显示按钮**（官方问卷不可置顶）
  - `creatorId === currentUserId` → 显示"看广告置顶"
  - `creatorId !== currentUserId` → 显示"助力推广"

### 3.3 后端云对象层

在 `enterPoolImpl()` （或 `handleAdReward` 路由至 `first_pin` 后的核心逻辑）最顶部加入防护：

```javascript
// 在查询问卷信息后
if (!survey.creatorId) {
  throw new Error('官方问卷不可置顶')
}
```

## 4. 助力推广功能

### 4.1 数据库改动

#### `pin-pool` 集合新增字段

| 新字段 | 类型 | 说明 |
|--------|------|------|
| `pinType` | String | `"self"`（自己置顶自己）或 `"promote"`（助力推广他人） |
| `pinnerId` | String | 实际执行入池操作的用户 ID。对于 `"self"` 类型，等于 `userId` |

#### `career-records` 集合新增字段

| 新字段 | 类型 | 说明 |
|--------|------|------|
| `pinType` | String | 同上，区分战绩单类型："自己置顶" or "助力推广" |

战绩单结构不变，仅文案因 `pinType` 不同而变化（详见 §4.4）。

### 4.2 surveyAuthor 修复（Bug Fix）

**现有问题：**

`pin-system/index.obj.js` 中入池时取 `surveyAuthor` 的代码：

```javascript
const surveyAuthor = user.nickname || ''  // user = 当前执行操作的用户
```

这个逻辑在"自己置顶自己"时正确，但在**助力推广**场景下错误——置顶栏卡片会显示推广者的昵称，看起来像推广者冒领了问卷。

**修复方案：**

入池时，如果 `pinType === "promote"`，直接复用入口处已查到的 `survey` 对象里的 `creatorId`（无需再查一次 `surveys`），再通过 `creatorId` 获取该用户的 `nickname` 作为 `surveyAuthor`：

```javascript
let surveyAuthor
if (pinType === 'promote') {
  // creatorId 从入口处已查到的 survey 对象中直接取，无需重复查 surveys
  const creatorId = survey.creatorId
  const { data: creatorUser } = await db.collection('uni-id-users').doc(creatorId).get()
  surveyAuthor = creatorUser.nickname || ''
} else {
  surveyAuthor = user.nickname || ''
}
```

### 4.3 归属分层权重无需修改

现有规则天然适配助力场景：

| 场景 | 权重表现 |
|------|---------|
| **B 看自己首页** → B 的问卷被 A 推广 | 因归属分层，B 的问卷在 B 自己屏幕上获得高权重区间 → **合理** |
| **A 看自己首页** → A 推广了 B 的问卷 | 被推广的问卷在 A 看来是"他人的问卷"，走低权重区间 + 反向补偿 → **合理** |

无需修改权重算法。唯一可讨论的扩展：是否给推广者一定的"优先展示"权益，MVP 阶段暂不实现。

### 4.4 叙事层改动

#### 按钮文案

| 场景 | 当前文案 | 改为 |
|------|---------|------|
| 自己的问卷 | "看广告置顶" | 不变 |
| 他人的问卷 | "看广告置顶" | **"助力推广"** |
| 官方问卷 | "看广告置顶" | **不显示** |

#### 候场区提示文案

| 视角 | 场景 | 当前 | 改为 |
|------|------|------|------|
| **推广者** | 自己置顶 | "你的问卷正在排队..." | 不变 |
| **推广者** | 助力推广 | "你的问卷正在排队..." | **"你推广的问卷正在排队..."** |
| **问卷所有者** | 问卷被他人推广 | — | **"你的问卷正在排队..."**（文案不变，与主动置顶一致。所有者无需感知具体是谁推广的，只需知道自己的问卷正在展示即可） |

#### 战绩单

| 场景 | 当前 | 改为 |
|------|------|------|
| 自己置顶 | "你的置顶战绩" | 不变 |
| 助力推广 | "你的置顶战绩" | **"你的推广战绩"** |

#### 置顶栏卡片

| 场景 | 当前 | 改为 |
|------|------|------|
| 自己置顶 | 无标识 | 不变（卡片上已有"我的"角标） |
| 助力推广 | 无标识 | **加小标签"你推广的"** |

## 6. 边界情况说明

| 场景 | 处理方式 |
|------|---------|
| 用户对自己问卷点击"看广告置顶" | `pinType = "self"`，走现有逻辑 |
| 用户对他人问卷点击"助力推广" | `pinType = "promote"`，`pinnerId` 记录推广者，`surveyAuthor` 取问卷所有者昵称 |
| 用户尝试置顶官方问卷 | 前端不显示按钮，后端 `enterPoolImpl` 拒绝，双层防护 |
| 推广者和问卷所有者为同一人（正常不应出现） | 前端按钮文案按 `creatorId === currentUserId` 判断，走"置顶"而非"推广" |
| 推广战绩单被分享 | 战绩单内容不变，文案按 `pinType` 切换，底部引导文案不变 |
| 已有的 `pin-pool` 数据 | 不迁移。旧文档没有 `pinType` 和 `pinnerId`，代码中按 `undefined` 处理，视为 `"self"` 类型兼容 |
| 已有的 `career-records` 数据 | 同上，兼容旧数据 |

## 7. 工作优先级

1. **数据库 schema 改动**（`pin-pool` + `career-records`）— 改动后上传生效
2. **云对象逻辑**（拦截 + surveyAuthor 修复 + 入池写入新字段）
3. **前端文案 + 按钮条件**（官方问卷隐藏 + 文案区分）
4. **候场区战绩单文案**（统一文案切换）
5. **置顶栏标签**（助力推广卡片标识）
