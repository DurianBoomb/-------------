# 问卷置顶系统 · 开发工作计划

> 本文档基于《问卷置顶系统——设计文档.md》的技术设计，将开发过程按依赖关系重组为 **7 个阶段**，其中阶段零拆为 **3 个子阶段并行推进**。每阶段完成后需回归测试前置功能。
>
> **核心思路**：先跑通最小闭环（0A→0B→入池→抽取→置顶栏），再追加候场区、权重算法、战绩单等增强模块。

## 阶段零：基础搭建（无上游依赖，可并行）

阶段零拆为三个并行的子阶段，互不阻塞：

### 阶段零A：数据库 + 配置 + 迁移

**内容**：4 个 schema + config + counter 初始化 + 用户扩展 + 迁移脚本。全做完，无阻塞。

#### 0A.1 数据库集合 Schema
新建 4 个 MongoDB 集合 schema 文件（含自增计数器），统一放在 `uniCloud-alipay/database/`：

| Schema 文件 | 用途 | 核心字段 |
|------------|------|---------|
| `pin-pool.schema.json` | 置顶池主存储 | `_id, userId, surveyTitle, surveyCover, weight, createdAt, expireAt, senioritySnapshot, haloActive, isGreenChannel` |
| `survey-queue.schema.json` | 候场区状态（允许多条同时候场） | `_id(auto), userId(indexed), surveyId, enterAt, acceleratedCount, seniorityLevel, currentPhase` |
| `career-records.schema.json` | 战绩单档案 | `_id, userId, surveyId, careerNumber(用户第N条), archiveNumber(ZW展示编码), createdAt, stats:{views,clicks,favorites}, bonusTriggered, bonusMultiplier, honor, comment, surveyTitle` |
| `counter.schema.json` | 自增计数器（archiveNumber 全局序号） | `_id(固定值 'careerArchiveSeq'), seq(Number)` |

每个 schema 需要定义 `permission`（权限控制）和必要的索引（expireAt 索引、userId 索引等）。

#### 0A.2 全局配置
在 `uni-config-center/` 下新建 `pin-system/config.json`，所有可调参数及开发期占位值**以设计文档 §8.2.5 为准**（权威来源），此处不重复列出。关键说明：
- 开发期占位值标注 `⚠️` 的参数需在 **阶段七（全局参数调优）** 逐项核定
- 所有参数集中在 config.json 中管理，调整后通过发版或云函数热更新生效

## 阶段一：置顶池核心 —— 入池（依赖阶段零B资历查询）

**原计划阶段二拆出**。这是真正的分水岭，先实现纯入池逻辑，暂时不涉及权重计算。

### 1.1 系统容量限制（入池前检查）

- **单人同时在系统中的问卷上限：3 条**（覆盖候场、置顶、待签收全生命周期）
- 槽位对应 `uni-id-users` 扩展字段 `career.slots`，存储一个长度为 3 的数组，每个元素为对象：
  ```javascript
  career.slots = [
    { status: 'idle',      surveyId: null,   pinId: null,  queueId: null },
    { status: 'active',    surveyId: 'xxx',  pinId: 'pin_yyy', queueId: null },
    { status: 'queuing',   surveyId: 'zzz',  pinId: null,  queueId: 'queue_xxx_1234' }
  ]
  ```
  - `status`：枚举值 `idle | queuing | active | claimable`
  - `surveyId`：关联的问卷标识（用于展示问卷标题、点击跳转问卷页）
  - `pinId`：关联的 pin-pool 文档标识
  - `queueId`：关联的 survey-queue 候场记录 _id
- 槽位状态流转：`idle`（闲置）→ `queuing`（候场中）→ `active`（置顶中）→ `claimable`（待签收）→ `idle`
- 三条满时用户不可发起新的置顶，需等其中一条走完腾出空位

### 1.2 入池接口
> **实际业务入口为 `handleAdReward`（设计文档 §8.4），内部根据 scene 路由：`first_pin` → `enterPool`（首次置顶），`queue_accel` → `executeAccel`（候场加速）。以下方法为内部路由的落地实现。**

`enterPool(userId, surveyId)`：
0. **槽位二次确认**：检查用户当前是否有空闲槽位（少于 3 条）。用户看广告前已前置检查一次，但广告播放期间（1-2 分钟）槽位可能变动，此处再次确认。无空闲槽位时返回"已达上限"错误
1. 查资历 → 绿色通道判断（Lv.0 跳过池满线）
2. 查池满线 → 比较 `pin-pool` 当前数量与阈值
3. 直接入池：写入 `pin-pool` 文档（含登场光环）
4. 进入候场区：写入 `survey-queue` 文档，返回候场状态
5. 资历累加（直接入池时）：`exposureCount + 1`

`queueToPool(userId, surveyId, queueId)`：
- **调用时机**：候场区自然前进到达终点（前端调用）或第三次广告加速完成时（`executeAccel` 内部调用）
- **跳过**绿色通道检查和池满线检查（候场区已保证入池资格）
- **执行流程**：
  1. 检查槽位状态（确认有闲置槽位可用）
  2. 写入 `pin-pool` 文档（含登场光环，weight 按算法计算后一次性写入。本阶段先用固定随机权重占位，阶段二替换为真实算法）
  3. 累加用户曝光资历 +1
  4. 删除 `survey-queue` 中的对应候场记录（`_id: queueId`）
  5. **定位槽位**：通过 `career.slots[i].queueId === queueId` 匹配，写入 `pinId` = 新 `pin-pool._id` 并清空 `queueId`，更新 `status` 为 `active`

## 阶段二：置顶池核心 —— 权重与抽取（依赖阶段零B + 阶段一）

### 2.1 权重算法
`calculateWeight(survey, currentUserId)`：
1. 登场光环检查 → 光环中返回极高固定值
2. 归属分层 → 自己的问卷 / 他人问卷
3. 内部排序（自己的多份问卷之间按入池时间倒序加权，越新越高）
4. 反向补偿（他人的问卷之间按资历快照反向加权）

### 2.2 抽取接口
`draw(currentUserId, count = 5)`：
1. 查询 `pin-pool` 有效问卷（`expireAt > now`）
2. 内存加权随机采样
3. 排序（按 weight 降序）
4. 返回问卷列表 + 光环标记 + `isMine` 标记（供前端视角诡计使用）

## 阶段三：定时云函数 —— 过期清理（依赖阶段零A，可与阶段二并行）

`pin-expiry/index.js`（在 `uniCloud-alipay/cloudfunctions/` 下，普通云函数，带定时触发器），配置每分钟触发一次。

## 阶段四：候场区系统（依赖阶段一入池接口）

### 4.1 后端：候场区状态管理
云对象方法：
- `getQueueStatus(userId, queueId?)` → 返回指定候场记录的状态（阶段、日志文本段、加速次数）。queueId 为空时返回该用户所有候场记录列表
- `executeAccel(userId, queueId)` → 对指定候场记录执行广告加速跳跃

### 4.2 日志推进逻辑（后端主导）
**后端计算主导**：服务端在 `getQueueStatus` 中根据 `enterAt`、`acceleratedCount`、`seniorityLevel` 计算出 `currentPhase` 和对应的日志文本段，直接返回给前端。
- 前端仅负责渲染滚动动画，不参与阶段推进逻辑的计算
- 阶段推进曲线的所有参数仅存在于服务端配置文件 `pin-system/config.json` 中，不向客户端暴露

### 4.3 前端：候场区交互（底部半屏弹出面板）
候场内容**不再作为独立页面**，而是嵌入 `career-history.vue` 的槽位交互中：
- 用户在历史战绩单页面点击"候场"状态的槽位卡片
- 页面底部向上弹出半屏面板（黑底绿字终端风格）
- 日志逐行滚动展示当前处理进度
- 面板内包含"加速"按钮，触发激励视频广告
- 关闭面板后回到历史战绩单页面，槽位状态实时更新
- 候场完成时（自然或加速），槽位切换为"置顶中"状态

### 4.4 绿色通道闪屏【占位 mock】
- 入池时绿色通道触发时，在当前页面以 overlay 形式展示 1-2 秒的闪屏动画
- 占位 UI：亮绿色虚线框，居中文字"🟢 小绿人进场动画 · 待设计"

## 建议的"最小闭环"策略

**不要按模块一个个做完再连**，优先跑通一个端到端闭环，再往里面加东西。

### 最小闭环路径（建议前阶段首先完成）：

```
阶段零A（4个DB schema + config + 用户扩展 + 迁移）
       │
       ▼
阶段零B（云对象骨架，只实现 enterPool + getSeniority）
       │
       ▼
阶段零C（置顶栏组件骨架，pages.json 注册，首页占位）
       │
       ▼
阶段一（入池核心 enterPool，跳过绿色通道/池满线复杂逻辑，一律直接入池）
       │
       ▼
阶段二（draw 用简单随机抽取替代完整的四层权重算法）
       │
       ▼
阶段五（置顶栏组件调 draw 接口展示 5 张卡片）
```

**这条路径约 60 行核心代码**就能跑通"看广告→入池→置顶栏展示"的完整闭环。在此之后再追加：
1. 候场区（阶段四）
2. 权重算法（阶段二完整版）
3. 定时云函数（阶段三）
4. 战绩单（阶段六）

## 并行开发建议

| 批次 | 功能 | 建议分配 |
|------|------|---------|
| **第一批** | 阶段零A + 阶段零C | 可并行给两个人同时开工 |
| **第二批** | 阶段零B + 最小闭环剩余部分 | 阶段零A完成后即可启动 |
| **第三批** | 阶段一 + 阶段四后端（阶段4.1） | 依赖阶段零B，两个后端逻辑可串行做 |
| **第四批** | 阶段二 + 阶段五 | `draw` 一好即接置顶栏 |
| **第五批** | 阶段三 + 阶段六 | 过期清理好了就能生成战绩单 |
| **第六批** | 阶段七 | 所有模块就绪后统一收尾 |
