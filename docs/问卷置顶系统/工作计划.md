## 阶段零：基础搭建（无上游依赖）

### 0.1 数据库集合 Schema
新建 4 个 MongoDB 集合 schema 文件（含自增计数器），统一放在 `uniCloud-alipay/database/`：

| Schema 文件 | 用途 | 核心字段 |
|------------|------|---------|
| `pin-pool.schema.json` | 置顶池主存储 | `_id, userId, surveyTitle, surveyCover, weight, createdAt, expireAt, senioritySnapshot, haloActive, isGreenChannel` |
| `survey-queue.schema.json` | 候场区状态（允许多条同时候场） | `_id(auto), userId(indexed), surveyId, enterAt, acceleratedCount, seniorityLevel, currentPhase` |
| `career-records.schema.json` | 战绩单档案 | `_id, userId, surveyId, careerNumber(用户第N条), archiveNumber(ZW展示编码), createdAt, stats:{views,clicks,favorites}, bonusTriggered, bonusMultiplier, honor, comment, surveyTitle` |
| `counter.schema.json` | 自增计数器（archiveNumber 全局序号） | `_id(固定值 'careerArchiveSeq'), seq(Number)` |

每个 schema 需要定义 `permission`（权限控制）和必要的索引（expireAt 索引、userId 索引等）。

### 0.6 系统容量限制
- **单人同时在系统中的问卷上限：3 条**（覆盖候场、置顶、待签收全生命周期）
- 槽位对应 `uni-id-users` 扩展字段 `career.slots`，存储一个长度为 3 的数组，每个元素为对象：
  ```javascript
  // 示例：用户有一个槽位正在置顶，一个在候场，一个闲置
  career.slots = [
    { status: 'idle',      surveyId: null,   pinId: null,  queueId: null },
    { status: 'active',    surveyId: 'xxx',  pinId: 'pin_yyy', queueId: null },
    { status: 'queuing',   surveyId: 'zzz',  pinId: null,  queueId: 'queue_xxx_1234' }
  ]
  ```
  - `status`：枚举值 `idle | queuing | active | claimable`
  - `surveyId`：关联的问卷标识（用于展示问卷标题、点击跳转问卷页）
  - `pinId`：关联的 pin-pool 文档标识。queuing 状态下为 null（尚未创建），入池后写入
  - `queueId`：关联的 survey-queue 候场记录 _id。仅在 queuing 状态下有值，用于准确定位槽位（避免同一用户对同一问卷多次置顶时 surveyId 重复导致匹配歧义）。入池成功后 pinId 写入，queueId 清空
- 槽位状态枚举：`idle`（闲置）/ `queuing`（候场中）/ `active`（置顶中）/ `claimable`（待签收）
- **queuing 状态定位方式**：通过 `slots[i].queueId === queueId` 匹配（唯一，消除 surveyId 重复歧义）。`pinId` 为 null（pin-pool 文档尚未创建），入池后写入 `pinId` 并清空 `queueId`
- 三条满时用户不可发起新的置顶，需等其中一条走完腾出空位

## 阶段一：曝光资历系统（依赖 0.1, 0.2, 0.3）

### 前置说明：为什么要有这东西？

这套系统的核心机制叫 **反向补偿（Reverse Compensation）**，说直白点就是一种 **"杀熟"**——但咱们不是为了坑用户，恰恰相反，是为了**公平**。

**现实问题**：如果不加干预，一个没有机制的置顶池会天然被少数"老玩家"垄断。做得多的人越来越容易露脸，新人永远排不上，池子变成死水。

**解决方案**：让系统对"老面孔"越来越苛刻，对"新人"越来越偏袒。具体来说——

| 资历档位 | 能接受的代价 |
|---------|------------|
| **Lv.0 · 新人**（一次没上过） | 绿色通道直接插队，别人看到的权重也最高 |
| **Lv.1 · 偶发者**（上过几次） | 正常排，但权重仍然偏高 |
| **Lv.2 · 常客**（经常上） | 正常排，权重中性 |
| **Lv.3 · 老面孔**（天天上） | 正常排，但权重被压低 |

翻译成人话：**你上得越多，系统就越牺牲你的利益去喂新人。**

这不是因为你做得不够好，而是因为**轮着来比天天让同一个人上，对所有人都更好**。类似于"地主家也要让佃户吃上饭"的逻辑——你家有余粮，机会分给别人一点，池子才活得起来。

当然，这不是毫无回报的牺牲。系统会在**战绩单**里给老用户荣誉上的补偿（排行榜、特殊称号、数据暴击）——名气我给你，排位机会你让一让。

### 1.1 用户表扩展
在项目的 `uniCloud-alipay/database/` 下创建扩展 Schema 文件 `uni-id-users.schema.ext.json`（**注意：必须是 `.json` 后缀，不是 `.js`**。`schema.ext.js` 用于定义数据库触发器，不支持 field 扩展属性）。此方式不修改 `uni_modules/uni-id-pages/` 下的原文件，避免更新被覆盖：

```json
{
  "properties": {
    "career": {
      "bsonType": "object",
      "description": "置顶系统用户扩展数据",
      "properties": {
        "exposureCount": { "bsonType": "int", "description": "累计置顶成功次数" },
        "hasUnread": { "bsonType": "bool", "description": "是否有未读档案" },
        "unreadCareerIds": { "bsonType": "array", "description": "未读档案ID列表" },
        "slots": {
          "bsonType": "array",
          "description": "三槽位状态",
          "properties": {
            "status": { "bsonType": "string" },
            "surveyId": { "bsonType": "string" },
            "pinId": { "bsonType": "string" },
            "queueId": { "bsonType": "string" }
          }
        }
      }
    }
  }
}
```

**老用户迁移**：`schema.ext.json` 的 schema 定义仅对写入操作做校验，已有用户文档不会自动获得 `career` 字段。在阶段零需执行迁移脚本（放在 `uniCloud-alipay/cloudfunctions/common/pin-system-common/` 下或直接在 HBuilderX 的数据库控制台运行）：

```javascript
// 迁移脚本：为所有缺少 career 字段的老用户补全默认值
const db = uniCloud.database()
await db.collection('uni-id-users').where({
  career: { $exists: false }
}).update({
  career: {
    exposureCount: 0,
    hasUnread: false,
    unreadCareerIds: [],
    slots: [
      { status: 'idle', surveyId: null, pinId: null, queueId: null },
      { status: 'idle', surveyId: null, pinId: null, queueId: null },
      { status: 'idle', surveyId: null, pinId: null, queueId: null }
    ]
  }
})
```

**运行时兜底**：代码中读取 `user.career` 时仍建议做空值检查：`const slots = user.career?.slots || defaultSlots`

### 1.2 资历查询接口
云对象方法 `getSeniority(userId)`：
- 查询 `uni-id-users.career.exposureCount`
- 映射到档位 Lv.0~Lv.3
- 返回：当前数值、所属档位、距下一档还需次数
- 高频调用，需做内存级缓存

### 1.3 资历累加逻辑
入池成功时调用，在入池事务内执行 `exposureCount + 1`。
注意：与问卷入池在同一流程内完成，不可拆分。

## 阶段二：置顶池核心（依赖阶段一）

### 2.1 入池接口（云对象方法）
> **实际业务入口为 `handleAdReward`（设计文档 §8.4），内部根据 scene 路由：`first_pin` → `enterPool`（首次置顶），`queue_accel` → `executeAccel`（候场加速）。以下方法为内部路由的落地实现。**

`enterPool(userId, surveyId)`：
0. **槽位二次确认**：检查用户当前是否有空闲槽位（少于 3 条）。用户看广告前已前置检查一次，但广告播放期间（1-2 分钟）槽位可能变动，此处再次确认。无空闲槽位时返回"已达上限"错误
1. 查资历 → 绿色通道判断（Lv.0 跳过池满线）
2. 查池满线 → 比较 `pin-pool` 当前数量与阈值
3. 直接入池：写入 `pin-pool` 文档（含登场光环）
4. 进入候场区：写入 `survey-queue` 文档，返回候场状态
5. 资历累加（直接入池时）

`queueToPool(userId, surveyId, queueId)`：
- **调用时机**：候场区自然前进到达终点（前端调用）或第三次广告加速完成时（`executeAccel` 内部调用）
- **跳过**绿色通道检查和池满线检查（候场区已保证入池资格）
- **执行流程**：
  1. 检查槽位状态（确认有闲置槽位可用）
  2. 写入 `pin-pool` 文档（含登场光环，weight 按算法计算后一次性写入）
  3. 累加用户曝光资历 +1
  4. 删除 `survey-queue` 中的对应候场记录（`_id: queueId`）
  5. **定位槽位**：通过 `career.slots[i].queueId === queueId` 匹配（唯一；queuing 状态时 queueId 已写入槽位），写入 `pinId` = 新 `pin-pool._id` 并清空 `queueId`，更新 `status` 为 `active`

### 2.2 权重算法
`calculateWeight(survey, currentUserId)`：
1. 登场光环检查 → 光环中返回极高固定值
2. 归属分层 → 自己的问卷 / 他人问卷
3. 内部排序（自己的多份问卷之间按入池时间倒序加权，越新越高）
   - 注：第3层本质也是资历排序——按**问卷资历**倒序（越晚入池=越新=权重越高），与第4层的按**用户资历**反向排序结构类似但方向不同。
4. 反向补偿（他人的问卷之间按资历快照反向加权）

### 2.3 抽取接口
`draw(currentUserId, count = 5)`：
1. 查询 `pin-pool` 有效问卷（`expireAt > now`）
2. 内存加权随机采样
3. 排序（按 weight 降序）
4. 返回问卷列表 + 光环标记

### 2.4 过期清理（定时云函数 `pin-expiry`）
在 `uni-cloud\` 下新建 `pin-expiry/index.js`（普通云函数，带定时触发器），配置定时触发器（Trigger）：每分钟一次。**注意**：`generateCareer` 数据生成逻辑直接内联在此云函数内（见 §4.7），不通过 `importObject('pin-system')` 跨云函数调用，避免两层冷启动叠加。`pin-system` 云对象中保留 `generateCareer` 方法仅供管理台手动生成等非定时场景。

## 阶段三：候场区（依赖阶段二入池接口）

### 3.1 候场区状态管理
云对象方法：
- `getQueueStatus(userId, queueId?)` → 返回指定候场记录的状态（阶段、日志文本段、加速次数）。queueId 为空时返回该用户所有候场记录列表
- `executeAccel(userId, queueId)` → 对指定候场记录执行广告加速跳跃

### 3.2 日志推进逻辑（后端主导）
**后端计算主导**：服务端在 `getQueueStatus` 中根据 `enterAt`、`acceleratedCount`、`seniorityLevel` 计算出 `currentPhase` 和对应的日志文本段，直接返回给前端。
- 前端仅负责渲染滚动动画，不参与阶段推进逻辑的计算
- 阶段推进曲线的所有参数（自然前进速率、阶段停留时长、过渡条件等）仅存在于服务端配置文件 `pin-system/config.json` 中，不向客户端暴露

### 3.3 候场区交互（底部半屏弹出面板）
候场内容**不再作为独立页面**，而是嵌入 `career-history.vue` 的槽位交互中：
- 用户在历史战绩单页面点击"候场"状态的槽位卡片
- 页面底部向上弹出半屏面板（黑底绿字终端风格，纯功能Mock）
- 日志逐行滚动展示当前处理进度
- 面板内包含"加速"按钮，触发激励视频广告
- 关闭面板后回到历史战绩单页面，槽位状态实时更新
- 候场完成时（自然或加速），槽位切换为"置顶中"状态
- 日志滚动行为说明（**占位 mock**）：
  - 当前占位 mock 采用 **快速滚到最新** 策略：第二次打开半屏面板时，日志不从头逐行滚动，而是快速推进到当前最新位置。
  - 最终交互方式待视觉设计阶段确定，候选方案：
    · 从头逐行滚动：完整的观看体验，但等的时间长
    · 直接展示最新位置：省时但不一定有滚动感
    · 快速滚到最新：模拟"加急回放"到最新位置

### 3.4 绿色通道闪屏【占位 mock】
- 绿色通道闪屏为 Lv.0 用户入池成功后的转场动画，在当前页面以 overlay 形式展示 1-2 秒。
- **占位组件路径**：`components/green-channel-splash/green-channel-splash.vue`。
- 占位 UI：亮绿色虚线框，居中文字"🟢 小绿人进场动画 · 待设计"。
- 触发流程：`handleAdReward` 返回 `greenChannel: true` ⇒ 前端展示占位组件 1-2 秒 ⇒ 自动消失并刷新置顶栏。
- 视觉具体设计待确认后替换占位组件。

### 5.3 历史档案页（含三槽位管理台）
`pages-tools/career/career-history.vue`：

页面分为上下两部分：

**上半部分：三槽位管理台**
- 固定展示 3 个状态卡片（槽位），各自独立运行完整生命周期：
  | 槽位状态 | 卡片显示 | 用户交互 |
  |---------|---------|---------|
  | `idle`（闲置） | "闲置"文字，灰态 | 不可点击 |
  | `queuing`（候场中） | "候场" + 问卷标题简称 | 点击弹出半屏终端面板（见 3.3） |
  | `active`（置顶中） | "置顶中" + 问卷标题 + 倒计时 | 点击弹出半屏查看实时状态 |
  | `claimable`（待签收） | "查看战绩单" | 点击跳转 `career-detail.vue`，关闭后该槽位恢复闲置 |
- 用户同时最多 3 条问卷在系统中流转，三个槽位对应三个生命周期位置
- 最新发起置顶的问卷按顺序从槽位1开始依次填入空槽位，占满后无法发起新的置顶
