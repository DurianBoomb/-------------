## 一、合并「用户画像」与「历史」页

### 解决方案

### 开发须知

**1. 数据源 `getAnswerHistory` 确认存在且接口契约如下：**

定义位置：`uniCloud-alipay/cloudfunctions/survey/index.obj.js` 第 188 行  
调用方式：`uniCloud.importObject('survey').getAnswerHistory({ page, pageSize })`

```js
// 成功返回
{

    list: [
      {
        _id: string,          // 答题记录ID（删除时要用）

// 查询失败返回 { errCode: 'DB_ERROR', errMsg: '历史记录查询失败' }
```

对比现有 `getUserProfile()`（profile.vue 当前调用的）：
- `getUserProfile`：按 `tagName` 去重，每个标签只保留首次记录，返回数组 **无分页**。

- 改造后 profile.vue 的"已确诊 X 个标签"实际含义变为"有 X 条答题记录"。

**2. 删除单条记录：使用现有 `survey.removeAnswer()`**

签名：`removeAnswer({ answerId: string })`  
`_id` 来自 `getAnswerHistory` 返回列表中的 `_id` 字段。  
调用示例：`survey.removeAnswer({ answerId: item._id })`

**3. 时间格式化：复用现有 `fmtTime`**

`answer-history.vue` 中有现成的 `fmtTime` 方法，应提取为公共工具函数（或直接复制逻辑到 profile.vue）。格式建议：`"5月15日 14:30"` 或 `"2026-05-15"`，确认当前 answer-history.vue 中的具体格式后保持一致。

**4. 空状态处理**

当 `getAnswerHistory` 返回 `data.list` 为空数组时：
- 顶部文案显示"还没有答题记录"
- 中间显示空白占位提示，而不是空白页面
- 可参考当前 profile.vue 空数据的默认占位文案（如有）

**5. 卡片点击逻辑**

当前 profile.vue 的卡片点击后跳转到 `answer-quiz` 页面。改造后 `getAnswerHistory` 返回的每条记录有 `surveyId`，继续复用此跳转即可。

## 三、结果页新增「看广告推广」按钮

### 问题

当前「看广告推广问卷」的入口（`pin-terminal-entry` 组件）仅放在首页，且必须手动输入 surveyId。用户做完问卷看到结果后，如果想推广该问卷，需要记住或抄写问卷 ID 再回到首页输入，操作路径断裂，体验不流畅。

### 需求

- 在问卷结果页（`result.vue`）底部操作区新增一个"看广告推广本问卷"按钮
- 由于结果页在 `onLoad` 时已拿到 `surveyId`（`o.surveyId`），无需用户再手动输入
- 直接复用 `pin-terminal-entry` 组件的逻辑——将当前页面的 `surveyId` 作为 props 传入即可跳过输入环节
- 用户体验：做完问卷 → 看结果 → 点击推广 → 看广告 → 推广成功，全流程在一个页面闭环

### 关于推广权限的确认

用户可以不限于推广自己的问卷。从 `pin-system` 后端代码（`enterPoolImpl(uid, surveyId)`）可见，入池逻辑只接收 `uid` 和 `surveyId`，从 `surveys` 集合读取问卷信息时**不校验该问卷的创建者是否为当前用户**。`surveyAuthor` 字段取的是当前用户的昵称而非问卷真实创建者。所以不管是不是自己的问卷，用户都可以通过输入任意 surveyId 来推广。

### 解决方案

| 修改对象 | 改动内容 |
|---------|---------|
| `result.vue` | 在底部 footer 区新增一个"推广"按钮（样式与"再来一次""分享给朋友"一致或略小一号）；点击后调用 `pin-terminal-entry` 的逻辑，传入当前页面的 `surveyId`；可复用 `pin-terminal-entry.vue` 现有方法或抽离为公用 mixin |

### 涉及文件

- `pages-tools/result/result.vue` — 新增推广按钮
- `components/pin-terminal-entry/pin-terminal-entry.vue` — 确认 props 接口兼容（已有 `surveyId` prop）

### 开发须知

**⚠️ 重要：`pin-terminal-entry` 不暴露外部调用方法，不能直接通过 props 复用**

实地检查结果：
- `pin-terminal-entry` 的 `surveyId` prop 确实存在，传入后不会弹出输入框——这部分是对的。
- **但广告播放只能通过用户点击组件本身触发**。组件没有 `expose` 任何方法，父组件无法通过 `ref` 调用。直接将组件放入 `result.vue` 渲染可以工作（用户点击组件触发广告），但样式上无法和结果页原有按钮（"再来一次""分享给朋友"）保持统一。

**建议做法：拆出公用广告播放函数**

将广告播放逻辑从 `pin-terminal-entry` 中提取为独立的工具函数，放在 `common/ad-utils.js`（或合适位置），暴露以下两个方法供各页面调用：

```js
// 播放激励视频广告，结束后调云对象的 handleAdReward
function playAndPromote(surveyId)  // 用于结果页、my-surveys 页

// 模拟广告播放（非微信环境调试用）
function simulateAdPlay(surveyId)  // 和组件内 _simulateAdPlay 逻辑一致
```

提取的内容（从 `pin-terminal-entry.vue` 复制）：
- `_playRealAd` → 创建 `wx.createRewardedVideoAd`，监听 onClose 后调云对象
- `_simulateAdPlay` → setTimeout 模拟，调云对象
- `_callHandleAdReward` → `uniCloud.importObject('pin-system').handleAdReward({ scene: 'first_pin', surveyId, adDuration })`

**云对象调用参考：**
```js
const ps = uniCloud.importObject('pin-system')
const res = await ps.handleAdReward({
  scene: 'first_pin',
  surveyId: sid,       // 从当前页面数据中获取
  adDuration: duration // 广告观看时长（毫秒），服务端校验 >= 15 秒
})
// res.action 可能为 'direct_entry'（直接置顶）或 'enter_queue'（进入候场区）
// res.action === 'enter_queue' 时，800ms 后跳转到 /pages-tools/career/career-history
```

**备选方案（不想拆公共函数）：**
直接把 `pin-terminal-entry` 组件用 `v-if` 条件渲染到 `result.vue` 底部，用 CSS 覆盖样式使其看起来像一个普通按钮。方案简单，但样式侵入性强，不推荐。

## 六、历史档案页统计数据来源加固

### 问题

`career-history.vue` 的 `loadCareers()` 使用客户端直连 DB 查询，`where({})` 中没有显式传入 `userId` 过滤条件。虽然 schema 的 `read` 权限已经配置了 `auth.uid == doc.userId` 作为兜底，但存在以下隐患：

- schema 规则依赖云端部署正确，未部署/部署失败时数据裸奔
- 当前 `summary` computed（累计注视/累计打开/累计存档）直接对 `careerRecords` 全量累加，如果 dataset 混入其他用户数据，统计就全歪了
- 前端直连 DB 的方式本身就有风险，schema 是唯一防线，缺少防御纵深

### 需求

- `loadCareers()` 中显式传入当前用户的 `uid` 作为查询条件，使数据过滤不依赖 schema 权限
- `uid` 来源：从 `career-history.vue` 现有的 `getSeniority()` 调用结果中获取，或从 `uni.getStorageSync('uni-id-pages-userInfo')` 中读取
- cursor: `career-records` 表上有 `idx_userId` 索引（已建），加了 userId 条件反而查询更快

### 解决方案

| 修改对象 | 改动内容 |
|---------|---------|
| `career-history.vue` | `loadCareers()` 中从 `uni.getStorageSync('uni-id-pages-userInfo').uid` 读取 userId，加到 `.where()` 条件中 |

### 涉及文件

- `pages-tools/career/career-history.vue` — 仅改动 `loadCareers`

### 开发须知

**1. Schema 权限现状确认**

`career-records.schema.json` 第 5 行：
```json
"read": "auth.uid == doc.userId"
```
此项配置正确，但如果后期修改 schema 或部署出现问题，前端没有兜底。加显式 userId 过滤是防御纵深的第一道加固，schema 权限是第二道。

**2. uid 来源**

前端可以通过以下方式获取当前用户的 uid：

```js
const uid = uni.getStorageSync('uni-id-pages-userInfo')?.uid
```

`uni-id-pages-userInfo` 在用户登录时由 uni-id 自动写入 storage，`career-history.vue` 的 `loadNickname()` 也已在其他页面中使用同样方式获取 uid，模式一致。

**3. 改动量**

仅修改 `loadCareers()` 方法中的 `.where()` 条件，从：

```js
const res = await db.collection('career-records').where({}).orderBy('createdAt', 'desc').get()
```

改为：

```js
const uid = uni.getStorageSync('uni-id-pages-userInfo')?.uid
const res = await db.collection('career-records').where({ userId: uid }).orderBy('createdAt', 'desc').get()
```

一行改动，零风险。`idx_userId` 索引已存在，加了 `userId` 条件反而查询更快。
