
## 一、总架构

**一个日志流 = 固定文本骨架 + 按资历动态展开的池文本序列**

- 固定文本（阶段标题、过渡节点）是骨架——每个用户每条日志流都出现，数量固定（10~12 条）
- 池文本（审核/质检/推送三条叙事线）受资历控制展开——资历越深，抽取条数越多
- 每条文本自带间隔（`interval`），总时间 = Σ 所有文本的间隔
- 前缀由文本类型决定（`[系统]`、`[审核]`、`[质检]`、`[推送]`），池文本不带前缀

用户看到的是：每次日志的叙事骨架一致（排队→审核→质检→推送→完成），但池文本的内容和总量随资历变化——新人唰一下过，老用户慢慢刷。

**个性化锚点砍掉**：不做 `{标题}`、`{标签名}` 等占位符替换。终端是纯后台视角。

## 二、阶段结构与文本展开

核心原则：**固定文本定骨架，池文本按资历展开，时间由文本数量和间隔决定。**

### 2.1 固定文本骨架（所有用户相同，10~12 条）

| # | 前缀 | 内容 | 间隔 | 进度暗示 |
|---|------|------|------|---------|
| — | `[系统]` | "════ 排队等候 ════" | 2s | 刚开始 |
| — | `[系统]` | "你的问卷已进入处理队列" | 2s | |
| — | `[系统]` | "正在分配处理节点... 节点已就绪" | 2s | 排队结束 |
| — | `[审核]` | "════ 内容审核 ════" | 2s | ~20% |
| — | `[审核]` | "审核意见记录完毕" | 2s | 审核结束 |
| — | `[质检]` | "════ 质量检测 ════" | 2s | ~45% |
| — | `[质检]` | "传播潜力预估完毕" | 2s | 质检结束 |
| — | `[推送]` | "════ 推送分发 ════" | 2s | ~70% |
| — | `[推送]` | "分配初始曝光权重… ✓" | 2s | 推送结束 |
| — | `[系统]` | "════ 处理完成 ════" | 2s | 100% |

固定文本总贡献时间：10 × 2s = **20 秒**。

### 2.2 池文本动态展开（受资历控制）

三个阶段各自展开池文本：

```
骨架：
[排队标题] → 排队固定文本 → [审核标题] → [审核池展开 N 条] → 审核过渡文本
             → [质检标题] → [质检池展开 M 条] → 质检过渡文本
             → [推送标题] → [推送池展开 K 条] → 推送过渡文本
             → [特殊状态（若有）] → [完成标题] → 完成
```

N、M、K 由资历查表决定，见第五节。

### 2.3 各阶段文本间隔

| 阶段 | 池 | 间隔 | 叙事理由 |
|------|-----|------|---------|
| 排队 | 无池（纯固定文本） | 2s | 一闪而过，起手式 |
| 审核 | 审核池 | 3s | 快节奏。像刷朋友圈，扫一眼一条。好奇、试探、随口点评 |
| 质检 | 质检池 | 5s | 慢节奏。在真正读题、在思考、在被戳中。慢 = 系统在认真品 |
| 推送 | 推送池 | 4s | 中节奏。监控模式，悠闲看后台数据一条条进来 |
| 固定文本 | — | 2s | 阶段路标，不需停留 |
| 特殊状态 | — | 4s | 与推送池同节奏 |
| 系统填充 | — | 2s | 低辨识度后台日志，快闪 |

## 三、文本池定义

### 3.1 三类主池

| 池 | 前缀 | 间隔 | 叙事角色 | 当前容量 | 最终需求 |
|----|------|------|---------|---------|---------|
| 审核池 | `[审核]` | 3s | 扫标题、第一印象、随口点评。审核员的 quick scan | 36 条 | **100 条** |
| 质检池 | `[质检]` | 5s | 坐下来读题、深度吐槽、被戳中后的真实反应 | 63 条 | **145 条** |
| 推送池 | `[推送]` | 4s | 后台监控模式，看数据一条条进来，分配曝光 | 32 条 | **64 条** |

三个池的文本都是纯内容，不带前缀。前缀在阶段定义里绑定，程序拼接时加上。

### 3.2 系统填充池（新增）

**为什么需要填充池**：当前三个池总容量 131 条，最多撑约 10 分钟（覆盖 L0-L2）。L3（目标 16 分钟）、L4（目标 25 分钟）需要比现有池更多的文本量，但一次性扩池到 300+ 条质量文本成本过高。

**填充池策略**：

| 属性 | 值 |
|------|-----|
| 容量 | 30 条 |
| 间隔 | 2s |
| 内容 | 低成本系统日志——"正在交叉比对第 N 题…""含梗量二次校准…""传播链路预计算…" |
| 特点 | 无个性、可循环使用、不需要 AI 精雕 |
| 适用 | L2+ 用户，每 3 条池文本插 1 条填充 |
| 插入位置 | 均分在对应阶段的池文本之间 |

**为什么可循环**：用户看 300+ 行终端日志时注意不到其中 30 条系统填充文本在循环——心理感知阈限远低于实际去重能力。

### 3.3 其他池

| 池 | 前缀 | 容量 | 触发 | 说明 |
|----|------|------|------|------|
| 固定文本 | 各阶段前缀 | 10~12 条 | 始终出现 | 阶段标题 + 过渡节点 |
| 特殊状态 | `[加速]`/`[新人]`/`[深夜]`/`[下班前]` | 4 子类 × 10+ 条 | 互斥四选一 | 插在完成标题之前，间隔 4s |

## 四、抽取与拼接逻辑

### 4.1 流程

1. 用户提交问卷，触发日志流生成
2. 系统读 `exposureCount`，查资历表得 N、M、K
3. 构建日志流：
   - 依次插入固定文本（排队阶段 + 审核标题）
   - 审核阶段：从审核池随机抽取 N 条（去重），L2+ 按每 3 条池文本插 1 条填充（从填充池顺序取，用完从头循环）
   - 插入审核过渡文本 + 质检标题
   - 质检阶段：从质检池随机抽取 M 条（去重），L2+ 同上规则插入填充
   - 插入质检过渡文本 + 推送标题
   - 推送阶段：从推送池随机抽取 K 条（去重），L2+ 同上规则插入填充
   - 插入推送过渡文本
   - 特殊状态判定（互斥，四选一）
   - 插入完成标题
4. 返回完整日志流给前端，每条文本自带 `interval`

### 4.2 填充插入逻辑

填充的目的是**延长 L2/L3 的总时间**，与池容量无关。三个主池已扩至覆盖 L3 最大需求（审核 100、质检 145、推送 64），不会因为容量不足触发填充。

```
if (level >= 2) {
  // 每 3 条池文本插入 1 条填充（分阶段独立计算）
  reviewFillers  = Math.floor(N / 3)
  qualityFillers = Math.floor(M / 3)
  pushFillers    = Math.floor(K / 3)
  // 在对应阶段的池文本序列中，每 3 条后插 1 条填充
}
```

等效于：

| 级别 | 审核填充 | 质检填充 | 推送填充 | 填充总量 |
|------|---------|---------|---------|---------|
| L0 | 0 | 0 | 0 | 0 |
| L1 | 0 | 0 | 0 | 0 |
| L2 | floor(65/3)=21 | floor(95/3)=31 | floor(42/3)=14 | **~66** |
| L3 | floor(100/3)=33 | floor(145/3)=48 | floor(64/3)=21 | **~102** |

### 4.3 去重逻辑

- 每个池维护"本次已抽取"临时索引
- 同一用户同一次日志流内，同一池不重复抽取同一条
- **主池已扩至覆盖 L3 最大需求**（审核 100、质检 145、推送 64），正常不会超额。若因配置错误或未来调整导致 N > 池容量：前 `池容量` 条不重复，超出部分从池头重新轮取（安全网）
- **填充池可循环**：30 条一轮，用完从头开始

### 4.4 特殊状态判定

| 子类 | 前缀 | 触发条件 | 判断逻辑 |
|------|------|---------|---------|
| 加速 | `[加速]` | 候场记录有加速标记 | `acceleratedCount > 0` |
| 新人 | `[新人]` | 用户首次提交问卷 | `exposureCount === 0` |
| 深夜 | `[深夜]` | 北京时间 0:00-6:00 | `hour >= 0 && hour < 6` |
| 下班前 | `[下班前]` | 北京时间 17:00-19:00 | `hour >= 17 && hour < 19` |

四个条件互斥，优先级：加速 > 新人 > 深夜/下班前（时间段）。一次日志流最多触发一个特殊状态。

```javascript
// 特殊状态判定
const cnHour = new Date().getHours()
let specialLog = null
if (acceleratedCount > 0) {
  specialLog = pickRandomFrom(specialStatusPool.accelerate)
} else if (exposureCount === 0) {
  specialLog = pickRandomFrom(specialStatusPool.newcomer)
} else if (cnHour >= 0 && cnHour < 6) {
  specialLog = pickRandomFrom(specialStatusPool.lateNight)
} else if (cnHour >= 17 && cnHour < 19) {
  specialLog = pickRandomFrom(specialStatusPool.endOfDay)
}
if (specialLog) {
  // 插在完成标题之前，而非末尾
  const doneIndex = logLines.findIndex(l => l.text === '════ 处理完成 ════')
  if (doneIndex >= 0) {
    logLines.splice(doneIndex, 0, specialLog)
  } else {
    logLines.push(specialLog)
  }
}
```

## 五、终端节奏控制（文本驱动）

### 5.1 核心模型

**时间不由计时器 `atSecond` 决定，由文本的间隔之和决定。**

```
总时长 = 固定文本 × 2s + 审核池 × 3s + 质检池 × 5s + 推送池 × 4s + 填充文本 × 2s + 特殊状态 × 4s
```

每条文本一个 `interval`（秒），前端按顺序展示，本行显示后等 `interval` 秒再推出下行。后端不再维护 `slotSchedule` 硬编码时间表，改为遍历文本列表累加间隔。

### 5.2 前端 = 哑终端

前端不计算时间。只做两件事：
1. 展示后端返回的行
2. 每 3 秒轮询 `getQueueStatus` 获取最新可展示行

### 5.3 前后端协作模型

```
前端（终端组件）                    后端（getQueueStatus）
    │                                      │
    ├─ 打开终端面板 ──────────────────────→│
    │                                      ├─ 根据 enterAt + 当前时间
    │                                      │  遍历文本列表，累计每条 interval
    │                                      │  返回所有已到期的行
    │←─ 返回当前所有应展示的行 ──────────┤
    │                                      │
    ├─ 逐行动画展示                         │
    │                                      │
    ├─ 3 秒后再次轮询 ───────────────────→│
    │                                      ├─ 遍历，如新增行到期则返回
    │←─ 返回新增的行（或空） ────────────┤
    │                                      │
    ├─ 继续 3 秒轮询...                    │
    │                                      │
    │←─ 某次返回 currentPhase: "ready" ──┤  ← 所有文本到期
    │                                      │
    └─ 触发入池                              │
```

### 5.4 后端推进算法

```javascript
function calcVisibleSlots(logLines, enterAt, now) {
  const elapsed = (now - enterAt) / 1000  // 已过秒数
  let accumulated = 0
  const visible = []

  for (const line of logLines) {
    accumulated += line.interval
    if (elapsed >= accumulated) {
      visible.push(line)
    } else {
      break  // 后面的都没到时间
    }
  }

  return visible
}
```

`logLines` 是已拼好的完整文本列表，每条自带 `interval` 字段。代码量远小于原来 16 槽位 `slotSchedule` 数组。

### 5.5 资历-时间对应表

| 级别 | exposureCount | 审核(N) | 质检(M) | 推送(K) | 池文本 | 填充 | 总文本 | 等待时间 |
|------|--------------|---------|---------|---------|--------|------|--------|---------|
| L0 | 0 | 3 | 4 | 3 | 10 | 0 | ~21 | **~1 分钟** |
| L1 | 1-5 | 18 | 26 | 12 | 56 | 0 | ~67 | **~4.5 分钟** |
| L2 | 6-20 | 65 | 95 | 42 | 202 | ~66 | ~279 | **~17 分钟** |
| L3 | ≥21 | 100 | 145 | 64 | 309 | ~102 | ~422 | **~25 分钟** |

**计时验证：**

- L0：20 + 3×3 + 4×5 + 3×4 + 0×2 + 4 = 20 + 9 + 20 + 12 + 4 = **65s ≈ 1 分钟**
- L1：20 + 18×3 + 26×5 + 12×4 + 0 + 4 = 20 + 54 + 130 + 48 + 4 = **256s ≈ 4.3 分钟** → **~4.5 分钟**
- L2：20 + 65×3 + 95×5 + 42×4 + 66×2 + 4 = 20 + 195 + 475 + 168 + 132 + 4 = **994s ≈ 16.6 分钟** → **~17 分钟**
- L3：20 + 100×3 + 145×5 + 64×4 + 102×2 + 4 = 20 + 300 + 725 + 256 + 204 + 4 = **1509s ≈ 25.2 分钟** → **~25 分钟**

### 5.6 广告加速

广告加速不再跳跃槽位索引。新方案：

- 后端 `executeAccel` 中按资历档位调大 `effectiveElapsed` 偏移量
- 等效于瞬间推进一段累计间隔，让更多文本"到期"
- 第三次加速直接将所有文本标记为到期（`currentPhase = 'ready'`）

## 六、数据流总览

```
用户提交问卷
    ↓
读取 exposureCount → 查资历表 → 得 N、M、K
    ↓
构建日志流：
    1. 插入固定文本骨架（排队阶段 + 审核标题）
    2. 审核阶段：随机抽 N 条审核池文本（去重，interval: 3s）
       L2+ → 每 3 条池文本插 1 条填充文本（interval: 2s）
    3. 插入审核过渡文本 + 质检标题
    4. 质检阶段：随机抽 M 条质检池文本（去重，interval: 5s）
       L2+ → 同上规则插入填充
    5. 插入质检过渡文本 + 推送标题
    6. 推送阶段：随机抽 K 条推送池文本（去重，interval: 4s）
       L2+ → 同上规则插入填充
    7. 插入推送过渡文本
    8. 特殊状态判定（互斥四选一，interval: 4s）
    9. 插入完成标题
    ↓
返回完整日志流（文本数组，每条带 interval 字段）
    ↓
前端每 3 秒轮询 getQueueStatus
后端遍历文本列表，累加 interval，判断每行是否到期
    ↓
逐行展示（模拟终端滚动效果）
    ↓
所有文本到期 → currentPhase = 'ready' → 触发入池
```

## 八、语料库存储方案

### 8.1 存储位置

语料库**不存数据库**，**不塞 config.json**，作为独立 JS 模块放在云函数目录下：

```
uniCloud-alipay/cloudfunctions/pin-system/text-pools.js
```

云函数启动时 `require` 进来，直接挂在内存，零查询延迟。

### 8.2 理由

| 存储位置 | 为什么不选 |
|---------|-----------|
| 数据库 | 语料是静态内容资产，运行时不会增删改。多一次查询 = 无意义的延迟 |
| `config.json` | config.json 定位是**运行时可调参数**（资历阈值、生命周期、权重系数等）。语料预估 15-20KB，塞进去让 config 臃肿到不可维护 |
| 独立 JS 模块 ✓ | 改文案不动配置，调参数不动文案。云函数冷启动时随代码一起加载，零额外开销 |

### 8.3 模块结构


### 8.6 语料清洗流程（实施时执行）
