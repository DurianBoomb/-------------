# Coze 使用复盘与协作策略优化

> 记录时间：2026-05-11 凌晨
> 背景：完成了一批标签生成 + 一次问卷生成尝试后，总结 Coze 的能力边界与最优协作方式。

---

## 一、问题回顾

### 问题 1：Coze 吃积分严重

| 操作 | 消耗积分 | 备注 |
|------|---------|------|
| 标签批量生成（一次） | 约 300+ | 主要消耗在 LLM 调用 |
| 问卷生成（一次） | 约 400+ | 维度 + 15题 + 结果全部生成 |
| 加两个变量节点 | 277 | 纯属浪费，变量配置不用 LLM 也扣钱 |
| **一次完整跑通** | **约 1000+** | 积分消耗不可忽视 |

### 问题 2：Coze 输出质量不稳定

| 任务 | 质量 | 说明 |
|------|------|------|
| 标签生成 | ✅ 可用 | 48 个标签大部分能打，description 也在线 |
| 问卷生成 | ❌ 翻车 | "确诊为烤肠"生成了一套"摸鱼"的题，标签和内容完全对不上 |

### 问题 3：变量机制坑多

- 配变量也要吃积分（纯属 Coze 平台的收费陷阱）
- 每次跑完清空输出，不能增量
- 不支持动态传入现有数据（要额外加代码节点或数据库节点）

---

## 二、核心结论：Coze 的能力边界

```
Coze 擅长：                   Coze 不擅长：
  脑暴、发散、起名字              精确的 JSON 结构输出
  写有趣的文案片段                 多字段一致性约束
  给出灵感方向                    tag→dim→qs 三层逻辑关联
  有生活感的描述                   格式合规的完整产品
```

说白了：**Coze 是个很好的创作搭档，是个很差的质量管理员。**

---

## 三、优化后的分工策略

### 原则

> **Coze 出框架（灵感/创意/骨架），我们填细节（结构化/格式化/质检入库）。**

Coze 负责"想什么"，我们负责"怎么存"。

### 标签生成 → Coze 全做

标签够轻量（name + category + emoji + description，4 个字段互相独立），Coze 完全能搞定。**维持现状**。

流程：
```
我写提示词 → 你去 Coze 跑 → Coze 出 JSON → 你发我 → 我转 init_data
```

已有改进点：
- 系统提示词一次性配置好
- 每次跑之前只手动替换两处：创作方向 + 已有标签列表
- 不做任何变量节点配置（省积分）

### 问卷生成 → 分两步

Coze 不直接生成完整问卷 JSON，而是：

**第一步：Coze 出框架（人+Coze配合）**

Coze 只输出一个"创意 brief"：
```
标签名：确诊为烤肠
title建议：你是一根什么肠？
dims建议：淀粉含量、社交媒体活跃度、夜宵频率、性价比、抗压能力
每题灵感：
  淀粉含量：周末躺沙发不动的画面
  社交媒体活跃度：发完朋友圈频繁刷点赞的画面
  夜宵频率：半夜点外卖的画面
  ……
结果风格：每个维度对应一个有趣的结果身份
```

**第二步：我们填细节（我来干）**

我根据 Coze 的框架，手工写成完整 JSON：
- 每个 dim 展开成 3 道题
- 写 resultTypes 的 name/emoji/emojiBg/desc
- 校对 match 字段一致性
- 输出标准 init_data 格式

### 为什么这样分？

| | Coze 全部自己写 | 分两步走（Coze 出框架→我们填细节） |
|--|---------------|----------------------------------|
| 积分消耗 | 400+/次 | 约 150/次（只出框架，不生成完整 JSON） |
| 质量 | 可能翻车（如烤肠→摸鱼） | 框架由 Coze 脑暴 + 内容由我们把控 |
| 灵活性 | 一次生成，改起来麻烦 | 随时手动优化结果描述、题目质量 |
| 你的工作量 | 很少，但质量没保障 | 只是审一个框架（5 分钟）+ 发给我填 |
| 我的工作量 | — | 我填完整 JSON，出 init_data |

### 单个标签的完整生产流程（定稿）

```
你的操作                             我的操作
─────────────────────────────────────────────
① 在 Coze 跑标签工作流（替换 seed）
    → 拿到 JSON                          ② 转 init_data + 合并入库
③ 上传数据库                              
④ 挑一个标签去 Coze 跑问卷框架           
    → 拿到 creative brief                ⑤ 根据 brief 写完整问卷 JSON
                                         ⑥ 出 init_data 给先生
⑦ 上传数据库                              
```

## 四、Coze 的工作流配置优化方向

### 当前最优配置（省积分版）

```
┌─────────────────────────────────┐
│         一个 LLM 节点            │
│                                 │
│  系统提示词：一次性写好的全部规则  │
│  用户提示词：手动替换两处文字后发送 │
│                                 │
│  不配变量 → 不配节点 → 无多余消耗 │
└─────────────────────────────────┘
```

每跑一次消耗约 300 积分（只有 LLM 调用费）。

### 不需要做的事

| 不要做 | 原因 |
|--------|------|
| 不要配置输入变量 | 模版中用文字占位，手动替换即可 |
| 不要加代码节点 | 纯 LLM 节点已够用 |
| 不要加数据库节点 | 省积分，数据我们手动传 |
| 不要配置 Bot | 跑 Bot 比跑工作流贵 |

### 需要做的事（减到最少）

**标签跑之前**：
1. 打开系统提示词，找到 `【创作方向：xxx】`，改成你这次想的
2. 找到 `【已有标签：xxx】`，问我要最新列表，复制进去
3. 点击运行

**问卷跑之前**：
1. 打开系统提示词，找到 `【标签名：xxx】`，改成你要出题的标签名
2. 点击运行

## 五、理解 Coze 工作流（调试用）

### 5.1 一个 Coze 工作流由什么构成

```
一个 Coze 工作流 = 一个或多个节点 + 节点之间的连线

最简单的配置（我们当前用的）：
  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ 开始节点  │ ──→ │ LLM 节点  │ ──→ │ 结束节点  │
  │ (Start)  │     │ (核心)   │     │ (End)    │
  └──────────┘     └──────────┘     └──────────┘
```

其中 **LLM 节点** 是我们打交道最多的东西：

| 组成部分 | 我们放什么 | 示例 |
|---------|-----------|------|
| **系统提示词** | 角色定义 + 全部规则 + 格式要求 | "你是一个被朋友拉起来出题的人……" |
| **用户提示词** | 当前要处理的具体任务，引用变量 | "tagName：{{tag_name}}，生成问卷" |
| **输入变量** | 从上游节点传过来的参数 | tag_name, tag_desc |
| **输出变量** | 这个节点产出的结果 | questionnaire |

### 5.2 数据流：输入的起点和终点

```
                     输入变量（在工作流开始节点定义）
                          │
                          ▼
  系统提示词 ──────┐
                   ├──→ LLM 模型 ──→ 原始输出文本
  用户提示词 ──────┘
                          │
                          ▼
                     输出变量（在工作流结束节点定义）
```

**关键认知**：

- 输入变量是在 **开始节点（Start）** 里配置的，不是在 LLM 节点里
- 输出变量是在 **结束节点（End）** 里配置的，同样不是在 LLM 节点里
- LLM 节点只管"收到提示词 → 生成文本 → 吐出来"，它不负责输入输出的变量定义
- 变量的引用方式：在提示词中用 `{{变量名}}` 语法

### 5.3 变量 vs 文字占位：本质区别

| | 变量（{{var}}） | 文字占位 |
|--|---------------|---------|
| 配置方式 | 在开始节点定义，提示词中引用 | 直接在提示词里写一段文字，跑之前手动改 |
| 动态性 | 运行时从上游传入，自动替换 | 每次手动改 |
| 积分 | 配置变量要消耗积分 | 零成本 |
| 适用场景 | 需要频繁换参数（如每天跑不同 seed） | 不常改的参数（如偶尔跑一次） |

**我们的选择：** 当前阶段用文字占位更省积分。如果以后每天高频跑，再考虑配变量。

### 5.4 输出格式的两个关键设置

Coze 对 LLM 输出的处理方式由两个设置决定：

**设置一：输出变量类型**

| 类型 | 效果 | 我们拿到的样子 |
|------|------|---------------|
| `string` | LLM 输出原样作为字符串 | `"{\"tag\":\"确诊为烤肠\"...}"`（需要手动 JSON.parse） |
| `object` | Coze 自动解析 JSON 为对象 | `{ tag: "确诊为烤肠", ... }`（直接可用） |
| `array` | Coze 自动解析 JSON 数组 | `[{ name: "...", ... }]`（直接可用） |

**教训：** 问卷的 `questionnaire` 一开始配成 `string`，导致每次拿到的是转义字符串。改成 `object` 就好了。

**设置二：输出内容**

系统提示词里必须写清楚"纯 JSON，不要 Markdown 包裹"。否则 Coze 可能在 JSON 外面加 ` ```json ` 和 ` ``` `，导致解析失败。

### 5.5 提示词模板的"行话"：给 AI 看的格式

Coze 的 LLM 节点本质上就是"你写一段话 → 发给大模型 → 大模型返回一段话"。所有系统提示词和用户提示词里的格式都是写给 AI 看的，Coze 平台本身不会去解析它们。

这意味着：
- 在提示词里写 `#` 标题 → 是给 AI 划分章节用的，不是给 Coze 看的
- 在提示词里写 Markdown 表格 → 是给 AI 理解规则的，不会被 Coze 渲染
- 在提示词里写 JSON 示例 → 是告诉 AI"按这个格式输出"，Coze 不校验

**所以我们可以在提示词里随意使用任何对 AI 有引导作用的格式。** 这一点不用顾虑。

### 5.6 常用调试方法

**问题 1：输出是字符串而不是对象**
→ 检查结束节点的输出变量类型是不是 `object`（或 `array`），不是 `string`

**问题 2：输出了 Markdown 代码块**
→ 在系统提示词中强调"纯 JSON，不要 Markdown 包裹"
→ 或在结束节点前加一个代码节点，用正则去掉 ` ```json ` 和 ` ``` `

**问题 3：积分消耗比预期高**
→ 检查是否配置了多余的节点（变量节点、代码节点等）
→ 纯 LLM 节点一次调用约 300-400 积分

**问题 4：内容跑题（如"烤肠变摸鱼"）**
→ 检查系统提示词是否强调了"铁律：所有内容必须从标签名出发"
→ 检查角色定义是否清晰（"被朋友拉起来出题的人"比"问卷生成专家"更有效）

**问题 5：维度数、题数不对**
→ 检查系统提示词中的约束规则是否明确（"总题数 = dims 数量 × 3"）
→ 给一个完整的 JSON 示例比文字描述更直观

### 5.7 总结：我们该怎么理解 Coze 工作流

```
Coze 工作流 = 一个容器
                │
                ├── 开始节点：配置输入变量（省积分可以不用）
                │
                ├── LLM 节点：提示词 → 大模型 → 输出
                │       └── 等于一个"有记忆的 AI 对话"，
                │           只是你代替了用户在打字
                │
                └── 结束节点：配置输出变量类型（必须配对）
```

本质上 Coze 工作流就是一个**有固定提示词的 AI 对话**，没有魔法，没有额外智能。提示词写得好它就干得好，提示词写不好它就胡来。我们的任务就是把这套提示词模板打磨好，然后用最省积分的方式反复调用它。这份文档会持续更新，当 Coze 平台政策或我们的流程变化时随时调整。
