## 阶段七：收尾与上线

基于前六个阶段代码已全部完成的现状，阶段七执行三块工作：

### 7.1 防刷与风控（四道防线）

1. **服务端 _before 频率限制**：云对象 `_before` 中按 `config.security.rateLimitPerMinute(5)` 限制每分钟请求次数
2. **handleAdReward 广告时长校验**：接收前端传递的 `adDuration` 参数，检查是否 >= `adMinDurationSeconds(15)`
3. **enterPoolImpl 每日次数软帽**：入池入口查询当日已入池次数，超过 `dailyPinSoftCap(10)` 时返回软帽提示
4. **前端 isEnded 校验**：`pin-terminal-entry` 接入真实 `wx.createRewardedVideoAd`，`onClose` 中校验 `res.isEnded`

## 技术方案

### 技术栈

不引入新技术栈，沿用 vue2 + uni-app + uniCloud（支付宝云），全部在现有文件上做增量修改。

### 实施思路

#### 7.1.1 _before 频率限制

- 利用 uniCloud 云对象 `this` 挂载 `_rateLimitTimestamps` Map 记录 uid 的请求时间戳数组
- `_before` 中：清理 60 秒前的旧戳 → 检查当前戳数量 >= `rateLimitPerMinute(5)` → 超限拦截
- **关键**：uniCloud 云对象的 `_before` 中 `return` 非 falsy 值会阻止后续方法执行，直接 `return { errCode: 'RATE_LIMIT', ... }` 即可
- **无状态限制**：`this._rateLimitTimestamps` 仅在单次云函数实例生命周期有效，冷启动后重置。MVP 阶段够用，后续可引入 Redis 做持久化

#### 7.1.2 广告时长校验

- `handleAdReward` 入参新增 `adDuration`（Number，客户端传递的广告播放毫秒数）
- 方法入口：`if (adDuration < PIN_CONFIG.security.adMinDurationSeconds * 1000) return ...`
- 微信不提供服务端广告验证 API，此校验防君子不防小人，真正防刷靠 `isEnded`（SDK 原生）+ 频率限制兜底

#### 7.1.3 每日次数软帽

- `enterPoolImpl` 中槽位检查后、绿色通道判断前插入每日次数检查
- `let todayStart = new Date(new Date().toLocaleDateString()).getTime()`
- `const countRes = await db.collection('pin-pool').where({ userId: uid, createdAt: { $gt: todayStart } }).count()`
- 注意 `count()` 在 uniCloud 中返回 `{ total: number }`，超限时软拒绝（不硬拒绝）

#### 7.1.4 前端 isEnded 校验

- 参考 `queue-terminal.vue` 第 178-188 行的已验证实现（项目中已有两次实践）
- 替换 `_simulateAdPlay()` 为真实 `wx.createRewardedVideoAd`
- 调用 `videoAd.show()` 时记录 `_adStartTime`，`onClose` 时计算 `adDuration`
- `onError` 降级：广告加载失败时直接调用 `handleAdReward`（adDuration=0），不阻塞用户

#### 7.1.5 配置文件

- 云对象 `index.obj.js` 行 83-87 已有内联 `security` 配置，与 `uni-config-center/pin-system/config.json` 一致
- `PIN_CONFIG.security`: `{ dailyPinSoftCap: 10, adMinDurationSeconds: 15, rateLimitPerMinute: 5 }`
- 修改云对象时同时更新 config.json 保持一致性

### 性能考量

- 频率限制内存结构：最大 5 条/分钟 × N 用户，内存开销可忽略
- 每日次数 `count()` 走 `userId + createdAt` 索引，毫秒级
- 所有新增逻辑同步执行，不引入额外网络调用
