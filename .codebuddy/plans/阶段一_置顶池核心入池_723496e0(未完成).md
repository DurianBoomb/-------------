## 阶段一：置顶池核心——入池逻辑

实现两个核心后端方法 + 统一路由入口 + 前端测试入口：

### enterPool

- 槽位二次确认（单人最多3条，查 `career.slots`）
- 资历查询 + 绿色通道判断（Lv.0 跳过池满线）
- 池满线检查（对比 `pin-pool` 数量与阈值）
- 直接入池：写入 `pin-pool`（含登场光环，weight 固定随机值占位）+ 资历累加 + 槽位状态更新
- 进入候场区：写入 `survey-queue` + 槽位状态更新（**不**累加资历）
- 返回结构化结果（action/direct_entry 或 enter_queue）

### queueToPool（候场转置顶入口）

- 跳过绿色通道和池满线检查
- 检查 `survey-queue` 记录是否存在（幂等）
- 写入 pin-pool + 资历累加 + 删除候场记录 + 槽位更新

### handleAdReward（统一路由入口）

- `scene === 'first_pin'` → 路由到 `enterPool`
- `scene === 'queue_accel'` → 路由到 `executeAccel`（本阶段先返回 NOT_IMPLEMENTED）

Mock 测试页新增上述方法的测试按钮，用于阶段一验收。

## 技术方案

### Tech Stack

- Node.js (uniCloud 支付宝云云对象)
- MongoDB (uniCloud 云数据库)
- uni-app Vue 2 (前端测试入口)

### Implementation Approach

**整体策略**：在现有 `pin-system/index.obj.js` 骨架基础上，将空壳方法 `enterPool`、`queueToPool`、`handleAdReward` 替换为完整实现。核心逻辑全部在服务端云对象中，前端只加按钮调用。

**关键设计决策**：

1. **PIN_CONFIG 内联配置**：阶段 0B 已把 `uni-config-center` 的配置内联为 `PIN_CONFIG` 常量，本阶段继续沿用。池满线阈值 `poolSizeThreshold: 1000`、生命周期 `poolLifecycleMinutes: 13` 均从 `PIN_CONFIG.pool` 读取。

2. **槽位定位方式**：从 `user.career.slots` 中找第一个 `status === 'idle'` 的索引。因为只要有一个空闲槽位即可入池，不需要用户指定用哪个。

3. **pin-pool._id 格式**：`pin_{Date.now()}_{4位随机数}`，用工具函数 `_randomSuffix()` 生成后缀。survey-queue.*id 同理用 `queue*` 前缀。

4. **资历累加时机**：只有问卷真正写入 `pin-pool` 后才 `exposureCount + 1`。进入候场区时不累加。使用 `db.command.inc(1)` 原子递增。

5. **weight 占位值**：阶段一使用固定随机值 `Math.floor(Math.random() * 200) + 300`（300~499，落在"自己的问卷"区间），阶段二才替换为完整权重算法。

6. **幂等保障**：`queueToPool` 第一步检查 `survey-queue` 中 queueId 是否存在，不存在直接返回成功。资历累加使用 `db.collection('uni-id-users').doc(uid).update({ 'career.exposureCount': db.command.inc(1) })` 原子操作确保不会重复累加。

7. **不依赖外部模块**：继续维持 `PIN_CONFIG` 内联的方式，不依赖 `uni-config-center` 公共模块（之前部署踩过坑）。

### Implementation Notes

- 所有方法通过 `this.uid` 获取当前用户，不允许前端传 userId
- 槽位文档更新使用 MongoDB 数组定位更新：`db.collection('uni-id-users').where({ _id: uid }).update({ 'career.slots.${idx}.status': 'active' })` — 注意字符串模板
- 方法返回统一使用 `{ errCode, errMsg, ... }` 格式
- Mock 页新增的测试调用统一 try-catch，对 NOT_IMPLEMENTED 做友好提示
