## 阶段六：战绩单系统

基于《问卷置顶系统——设计文档》第七章（战绩单）和《工作计划》阶段六的要求，实现完整的战绩单系统。

### 核心功能

1. **档案数据生成**：云对象方法 `generateCareer`（pin-expiry 已有内联实现，需提取为可复用方法）、战绩单数据计算（曝光量/点击量/收藏量、浮动系数、反向补偿、数据暴击、荣誉称号匹配、档案附注生成、一致性校验）、写入 career-records 并标记未读

2. **即时档案通知**：首页 `onShow` 调用 `checkCareerStatus()`，检测到未读档案弹出"15分钟名气管理局"风格弹窗，用户关闭时调用 `markCareerAsRead()` 释放槽位

3. **历史档案页（完整版）**：`career-history.vue` 下半部分补齐完整历史档案列表（手风琴结构、置顶生涯综述卡片、首秀标记、暴击高亮）

4. **档案详情页**：`career-detail.vue` 从骨架变为完整页面，接收 careerId 参数，从 career-records 拉取数据并渲染全部字段（档案编号、荣誉称号、三项核心数据、附注等）

5. **分享长图**：Canvas 2D 绘制红头文件风格分享图，包含所有必要字段

### 已知问题修复

- `career-records.schema.json` 中 `honor` 字段定义为 `string` 但 pin-expiry 实际写入对象 `{id, name, desc}`，需修复类型不匹配

## 技术方案

### 技术栈

- 前端：Vue 2 + uni-app（微信小程序）
- 后端：uniCloud 支付宝云云对象（Node.js）
- 数据库：MongoDB 5.0 兼容（uniCloud 云数据库）
- 长图生成：客户端 Canvas 2D（项目已有经验，结果页雷达图）
- 配置管理：uni-config-center（`uni_modules/uni-config-center/uniCloud/cloudfunctions/common/uni-config-center/pin-system/config.json`）

### 实现方案

#### 总体策略

**依赖链**：后端方法（`generateCareer`/`checkCareerStatus`/`markCareerAsRead`）无上游依赖 → 前端 `career-detail` 依赖后端 `checkCareerStatus`/数据查询 → 前端 `career-history` 列表依赖数据查询 → 首页弹窗依赖三者 → 分享长图无其他依赖但放在最后（纯展示层）

**开发顺序**：先 Schema 修复（避免写入崩溃）→ 后端三个空壳方法（前端所有页面依赖）→ 先实现 careertDetail（数据展示，最深层次）→ 再实现 career-history 列表（汇总展示，次深层）→ 首页弹窗整合（最表层，依赖前两者）→ 分享长图（纯客户端，独立）

#### 关键设计决策

**1. `checkCareerStatus()` 返回结构**

```
{
  hasUnread: Boolean,
  careers: [{
    careerId: String,
    surveyTitle: String,
    careerNumber: Integer,
    honor: { id, name, desc },
    stats: { views, clicks, favorites },
    archiveNumber: String,
    createdAt: Timestamp,
    bonusTriggered: Boolean,
    isGreenChannel: Boolean
  }]
}
```

设计思路：一次性返回所有未读档案的完整摘要信息，前端无需再逐个查询详情。走 `uni-id-users.career.unreadCareerIds` 查 ID 列表 → 查 `career-records` 获取完整摘要。

**2. `markCareerAsRead()` 原子化操作**

同一 `careerId` 通过两条路径触发（首页弹窗路径 + 历史页槽位路径），需保证原子性：

```
1. 从 uni-id-users.career.unreadCareerIds 中 pull(careerId)
2. 读取更新后的数组长度
3. 若为空则置 hasUnread = false
4. 定位该档案对应的槽位：通过 career-records 的 surveyId 和 createdAt 关联槽位的 pinId（或通过时间范围匹配槽位）
5. 条件更新槽位：仅当 status === 'claimable' 时置为 idle
```

条件更新确保两路不会同时释放同一个槽位。

**3. `generateCareer()` 方法**

pin-expiry 中的 `generateCareerRecord` 函数已完整实现了数据生成全流程（浮动系数、反向补偿、数据暴击、荣誉称号匹配、附注生成、一致性校验）。pin-system 云对象中实现同名方法时，将核心逻辑提取为独立函数，在两个文件中复用。注意配置引用方式不同（pin-expiry 用硬编码配置，pin-system 也可用统一配置中心）。

**4. 首页弹窗性能优化**

`onShow` 触发频繁，需本地缓存 `hasUnread`：`const cached = uni.getStorageSync('_hasUnreadCareer'); if (cached === false) return;`。缓存刷新时机为关闭弹窗时。

**5. 分享长图**

Canvas 2D 绘制红头文件风格，所有元素留有安全边距，适配朋友圈分享比例。使用项目已有的 Canvas 2D 经验（结果页雷达图）。

**6. 手风琴列表**

以 surveyTitle 为主键分组，按最近一次 createdAt 倒序排列。主标签显示累计置顶次数 + 最近档案摘要。同一时间只展开一个主标签。子标签显示每次档案的签发日期、荣誉称号、核心数据精简版。

### 架构设计

#### 数据流

```
pin-expiry 定时云函数 (每分钟执行)
  ↓ 检测过期 pin-pool 文档
  ↓ 内联调用 generateCareerRecord（阶段三已实现）
  ↓ 写入 career-records + 标记 hasUnread + 槽位 claimable
  ↓
pin-system 云对象
  ├── generateCareer() ← 非定时场景备用
  ├── checkCareerStatus() ← 首页 onShow 调用
  └── markCareerAsRead() ← 弹窗关闭/槽位点击调用
  ↓
前端页面
  ├── index.vue (onShow → check → 弹窗 → markAsRead)
  ├── career-history.vue (三槽位 + 历史档案列表 + 生涯综述)
  └── career-detail.vue (完整档案详情) → 分享长图 Canvas
```

#### 前端核心变更点

| 页面 | 当前状态 | 阶段六目标 |
| --- | --- | --- |
| `career-detail.vue` | 纯骨架，硬编码 | 接收 careerId，云函数查询+渲染全部字段 |
| `career-history.vue` | 三槽位已实现，列表占位 | 补齐手风琴列表+生涯综述卡片+特殊标记 |
| `index.vue` | 无未读检测 | onShow 弹窗 + markAsRead 联动 |

### 执行要点

1. **性能**：`checkCareerStatus` 是半低频率调用（仅在 onShow 时触发，且用本地缓存拦截），单次查询包括一次用户表读 + N 条 career-records 读，数据量极小（未读档案通常 1-3 条），对性能无影响
2. **幂等**：`markCareerAsRead` 使用 `db.command.pull` 原子操作移除 ID，重复调用不会产生副作用
3. **异常处理**：所有前端云函数调用统一 try-catch，失败时不影响首页正常展示
4. **兼容性**：不修改现有方法签名，新增方法遵循 `checkCareerStatus()`（无参，uid 从 _before 注入）、`markCareerAsRead({careerId})` 的命名规范
5. **Schema 兼容**：`honor` 字段改为 `object` 类型，原有 string 定义无法写入对象，必须在上线前修复
